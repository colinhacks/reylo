# Using Reylo

Reylo lets TypeScript import a `.sql` file as a typed query. The types come from the database itself: the parameters, the columns and their nullability, nested JSON and how many rows the query returns. Nothing is declared by hand, so a type is changed by changing the SQL or the schema, never by an annotation.

The docs are https://reylo.dev, with a page per database, https://reylo.dev/postgres, https://reylo.dev/mysql, https://reylo.dev/sqlite and https://reylo.dev/duckdb, all served as Markdown at https://reylo.dev/llms.txt. Read the section a task touches before writing SQL for it.

## Before changing anything

- Find the project file, `.reylo.yaml` or `.reylo.yml`, beside `package.json`. Its `direct_url`, or `DATABASE_URL` without one, is the dev database the type check reads the schema from, and its scheme names the database: `postgres://`, `mysql://`, `file:` for SQLite, `duckdb:` for DuckDB. A DuckDB project's statements are typed on its own `@duckdb/node-api`, which it installs. Reylo reads `.env.local` and `.env` as `dotenv` does, so a value there that holds a `#` is quoted.
- The type check is `tsc --noEmit --runExternalCode` on TypeScript 7.1, usually a `typecheck` script. Run it before and after a change.

## Writing a query

- One statement per `.sql` file, imported by a relative path: `import getUser from "./get_user.sql"`. The statement can be any one the database prepares: a query, an insert, an update, a delete. A file of several statements, such as a migration, is an error in the type check, and a migration's `create table` fails once the table exists; leave migrations out with `exclude` in `tsconfig.json`, as in `"exclude": ["db/**"]`.
- Parameters are `:name` on every database. Each appears once in a statement; to use a value twice, select it once, cast to its type, in a `with` and read it from there: `with input as (select :id::int as id) select … from input`. To let the caller pick the order, sort by a `case` on the parameter (`order by case when :sort = 'name' then name end`): a parameter alone as an `order by` or `group by` key is an error, since every row would sort by the same value (https://reylo.dev/#dynamic-sorting).
- On Postgres, a colon right after a subscript's `[` starts a slice, as Postgres reads it: `tags[:n]` is the first `n` elements, `n` a column. To subscript by a parameter, wrap it in parentheses: `tags[(:i)]`.
- A parameter the query does not type is an error that says to cast it: `:q::text`. Reylo writes each database's own cast (https://reylo.dev/#casts).
- A parameter accepts null only cast to `nullable(…)`, which keeps the type inside it and lets the caller leave the parameter out: `where user_id = coalesce(:user_id::nullable(int), user_id)`. A `coalesce` or a null test of a parameter alone does not make it nullable (https://reylo.dev/#nullable-parameters). A search form's or a list page's filters are one JSON parameter whose schema gives each filter its type, `enum` and default, read in a `with` (https://reylo.dev/#dynamic-filtering).
- A parameter written bare, with no cast, to a column that may hold null takes null too, and may be left out. Any other parameter takes no null: `.run()` throws before the query runs when one gets `null` or is left out, so pass every value its type asks for, even from an untyped request body. A JSON parameter there takes `null` as JSON's `null` instead, in a `coalesce` or a null test too: cast it to `nullable(…)` to pass SQL NULL, as `coalesce(:meta::nullable(jsonb), meta)` needs to keep `meta`.
- A list is one parameter: `= any(:ids::int[])` on Postgres, `list_contains(:ids::int[], id)` on DuckDB, and a JSON parameter read with `json_table` on MySQL or `json_each` on SQLite. Copy each database's form from https://reylo.dev/#filtering-by-a-list.
- Many rows to insert are one JSON parameter whose cast carries their JSON Schema (https://reylo.dev/#bulk-inserts, https://reylo.dev/#typed-json).
- A statement whose one column is an expression with no `as` returns the column's values rather than rows: `select count(*) from users` is a `bigint`, and `select lower(name) from users` a `string[]`. An `as`, or a column read as it is (`select id`), keeps the rows. Where that value may be null and the query may match no row, `null` stands for both, so name the column to tell them apart. Among several columns, an expression whose database-given name isn't an identifier, like `count(*)` or `?column?`, is a type error: name it with `as`.
- A column is nullable or not as the schema and the query make it: `not null`, a left join, `coalesce`. Change those to change the type. On Postgres a stored array's elements are nullable unless a `CHECK` keeps them out: `check (array_position(tags, null) is null)`.
- On Postgres, a JSON column a JSON Schema `CHECK` holds is typed by that schema, and so is a key read from it with a literal key, `payload -> 'x'` or `payload ->> 'x'`. Any other JSON value, such as a column with no schema or a value read out of a document, is `Json`, any JSON value, which `reylo` exports (`import type { Json } from "reylo"`). Narrow it or validate it before reading it as a shape; `x as Settings` compiles only where `Settings` is a `type`, not an `interface`. Cast a `->>` read to type it (https://reylo.dev/postgres#json).
- To reuse a query, write it as a `language sql` function on Postgres or a table macro on DuckDB: Reylo reads the body as the query it is, so a call keeps its columns' nullability and its key (https://reylo.dev/postgres#nullability). A PL/pgSQL function, a body of several statements and a name with several overloads keep the declared `returns`, every column nullable. On Postgres, mark a function that only reads `stable`, so that a filter on its rows can use an index.
- To see how Reylo types a query before writing it into the project, ask the playground's API: `GET https://reylo.dev/play/api/analyze?q=<sql>` answers with its Params, Returns and diagnostics as JSON (`POST` with `{"sql": "<sql>"}` works too). It runs on Postgres, against the docs' example schema of `users`, `posts` and `events`, which `GET https://reylo.dev/play/api/schema` lists; the project's own database is what decides.
- To read a type in the project, hover it or assign a wrong literal to it, as in `const x: "bogus" = row.status`. TypeScript 7 widens a union of literals in its errors, so assigning it to `number` reports `string | null` for an enum column.
- To read how the project's own database types a query, run `npx reylo analyze <file.sql>`: it prints the statement's parameters, columns, types, nullability, cardinality and diagnostics as YAML, in Reylo Type Defs, and `--format json` prints one line of JSON per statement instead. In a script, `analyze({ sql })` from `reylo` returns the same, reading the database the project names; pass `url` to read another. Reylo Type Defs is in preview, at version 0.1.0, and each descriptor names its version in `$schema` (https://reylo.dev/#analyze).

## Moving from Prisma

- To evaluate, plan or carry out a move from Prisma Client, read https://reylo.dev/prisma first. It answers the usual concerns (relations, queries built at run time, dates as strings, the build's database) with what Reylo does about each, and gives each Prisma Client call as SQL.
- Change the schema before converting a query, in migrations of their own: every `timestamp(3)` to `timestamptz` under `set time zone 'UTC'`, one table per migration; `cuid()` and `uuid()` ids to a database default; `@updatedAt` to a default and a `BEFORE UPDATE` trigger. Prisma Migrate stays.
- A relation Prisma read with `include` is an `array(select r from (select … where …) r)` subquery in the same statement on Postgres and DuckDB, typed field by field with each value as its column gives it (a `jsonb_agg` subquery on Postgres's JSON keeps less: a `bigint` past 2^53 rounds; `json_arrayagg` and `json_group_array` on MySQL and SQLite), and a page's counts are one `select` of scalar subqueries with no `from` around them, one typed row in one round trip.
- Give the new `pg` pool an `'error'` listener, on the pool and on each connection a transaction takes: Prisma's adapter had both, and Node exits on an unhandled one.
- Before calling the move done, check the converted code for what the type check can't see: `if (!rows)` where `.run()` returns an array (a write that joins and matches no key does); instants compared as strings with a `Date`'s `toISOString()`, whose three fraction digits misorder against the six `.run()` returns (compare their `Date.parse`); instants passed back through a `Date`, which drops microseconds; an enum `order by` that lost or gained a `::text`; `Promise.all` on a transaction's client; and any folder `tsconfig.json` skips, which needs a `tsconfig` of its own to be type-checked.

## Running a query

- Pass the project's own database client to `.run()`: a pool, a client, a transaction or connection taken from one, or a Drizzle database or Knex instance over one (https://reylo.dev/#run shows each driver's client, https://reylo.dev/#transactions its transaction). At run time Reylo opens no connection of its own. On Postgres, pass the driver's own object, never a hand-written wrapper with a `query()` or `unsafe()` that calls the pool: `.run()` refuses a client that is none of the drivers', since a wrapper returns values the driver already converted. Keep a wrapper a `Pool`, as a subclass or a proxy. A Postgres `date`, `timestamp` or `timestamptz` is read in the ISO style alone, so under another `DateStyle` (set on the session, the role or the database) `.run()` throws: set it to ISO. On DuckDB the client is a `DuckDBConnection` of `@duckdb/node-api`; its `.runSync()` does not exist, since node-api answers through a promise. On postgres.js, Reylo prepares each query as postgres.js prepares its own; behind a pooler in transaction mode, such as PgBouncer's, create the client with `prepare: false`, which Reylo's queries follow too.
- `.readOnly` on a query says Reylo found nothing in it that could write, which a wrapper that retries after a lost connection can test; a write, a locking read and a query that may call a volatile function are `false`, and a user's function counts by its declared volatility.
- `.runSync()` returns the result itself on a synchronous SQLite client (`better-sqlite3`, `node:sqlite`, `bun:sqlite`, the `Database` of `@tursodatabase/database/compat`, an `oo1` database of `@sqlite.org/sqlite-wasm`, a Durable Object's `ctx.storage.sql`), so it works inside their synchronous transactions. `.with(client)` binds the query to a client.
- To trace or log queries, subscribe to the tracing channel `reylo:query` from `node:diagnostics_channel`, on which Reylo publishes every query it runs; type its events as `QueryTrace` from `reylo`. Each carries the `query` (its `.source` is the file, its `.sql` the statement), `params`, `client`, `sync`, and the `result` or `error`; a `.runSync()` or `.trySync()` call ends on `end`, any other on `asyncEnd` (https://reylo.dev/#tracing). Don't wrap the driver or every call for this.
- The result's shape follows the row count Reylo infers: an array, one row, a row or `null`, or nothing for a write without `returning`. On Postgres, a write whose table has a `BEFORE` row trigger is a row or `null` unless every `return` of the trigger's PL/pgSQL returns the row, so look there when a write is unexpectedly nullable. A subquery, a `with` query or a view that selects a table's key unchanged is matched on that key like the table.
- To compare two results of the same Postgres query, as when telling which rows changed, match rows by `query["~standard"].query.key`: the output columns that identify each row of the result, such as `["id"]` for a selected primary key. It is absent for a query of one row at most and where Reylo infers no key (https://reylo.dev/postgres#cardinality). A driver that decodes each value once as it reads it, rather than handing raw rows to `decode`, takes each column's decoder from `query["~standard"].query.columns` (in order, each `{ name, decode }`, typed column by column, never called for NULL) and passes the rows it builds, keyed by the columns' names, to `query["~standard"].query.output(rows)`, which returns what `decode` would. To compare results by position, as a list does, sort by a key of the rows (`order by placed_at desc, id`): the query's `query["~standard"].query.ordered` is then `true`, in its type too, and is absent where rows can tie.
- Every driver gives the same types: a 64-bit integer is a `bigint`, a decimal its exact text, an instant its ISO 8601 text in UTC with six fraction digits, a pgvector `vector` a `number[]`, an `hstore` an object of its keys, a Postgres row value of a table or composite type and a geometric type (`point` is `{ x, y }`) an object of its fields, a range an object of its bounds (`{ lower: 1, upper: 5, bounds: "[)" }`, `{ empty: true }`) and a multirange an array of them, a MySQL `ENUM` the union of its labels and a `SET` a `Set` of them (which `JSON.stringify` writes as `{}`), and no value is a `Date`; a DuckDB `STRUCT` is an object of its fields (one without field names, as `(1, 'a')` makes, is an error: name its fields), a `LIST` an array, a `MAP` its entries as `{ key, value }`, a `UNION` `{ tag, value }`, a `VARIANT` the value it holds and a `GEOMETRY` its WKB bytes, a `Uint8Array` (a MySQL `GEOMETRY` is a `Uint8Array` too, its WKB after a 4-byte SRID). Pass a parameter in the form `.run()` returns for its type (https://reylo.dev/#data-types); on DuckDB a list parameter takes no `null` element and a `UNION` no `null` value (https://reylo.dev/duckdb#what-a-parameter-takes).
- On SQLite, a table that is not `STRICT` can hold a value of another kind than its column's declared type, such as the text `'abc'` in an `INTEGER` column; `.run()` throws an error naming the column rather than return it. Replace the value, or read the column with `cast(col as text)` (https://reylo.dev/sqlite#declared-types-and-strict-tables).
- On SQLite, write a string in single quotes. The type check refuses `select "hello"`, as `better-sqlite3`, `node:sqlite`, libSQL, Turso and SQLite Wasm do, since a double-quoted word is a name (https://reylo.dev/sqlite#limits).
- On Postgres, an array column is typed with one dimension, though Postgres lets it hold any number: `.run()` throws an error naming the column on a value of more. Inside JSON a query builds, `.run()` returns such a value as it is, and without `allow_nested_arrays` its type has one dimension. Read such a column with `to_jsonb(col)`, typed `Json`, or set `allow_nested_arrays: true` in `.reylo.yaml` to type every array column at any depth, as `NestedArray<T>` (https://reylo.dev/postgres#arrays).
- `.run()` throws the driver's own error. `.try()` returns `{ value }`, or `{ error }` for an error the database raised, read into one shape per database whichever driver ran the query: Postgres's `code` and `condition` (`unique_violation`) with the `constraint`, `table` and `column` it names; MySQL's `code` (`ER_DUP_ENTRY`), `errno` and `key`; SQLite's `code` (`SQLITE_CONSTRAINT_UNIQUE`), `table` and `columns`. The codes are typed, so a misspelled one is a type error, and where the query runs none of the project's own code (a trigger, a function it wrote), each error is narrowed to the constraints, keys and columns of the tables the query writes; any other error, such as a refused connection, still throws. `.trySync()` is the same on a synchronous SQLite client, and each `.sql` module exports the error's type as `QueryError` (https://reylo.dev/#try).

## After a change

- Run the type check. An error in a `.sql` file shows at its line and column, and `tsc` holds back the TypeScript errors while one remains, so fix the SQL first (https://reylo.dev/#errors).
- After a migration, the type check reads the new schema: a dropped column is an error in each `.sql` file that names it and in the code that reads it.
- `reylo/.cache/` is Reylo's cache of each query's analysis. Never edit it or commit it. A type check or a build that can't reach the database reads its types from there and says so, in one `reylo: cannot connect to …; building from reylo/.cache/, analyzed <date>` line per build and in each query's hover: the types are then as old as that date, so start the database and check again before trusting them after a migration.
- A query checks the schema it was typed against on its first run in a process (on a Durable Object, in each object), then once a minute, and logs a warning ("reylo: users.email has changed since …") when a column it names is gone, retyped or nullable where it was not, and still runs. A query the database can no longer run fails with the database's error, and a table the database lacks entirely, as in a Durable Object whose migrations have not run, gives no warning, only that error. Only a default that an insert of `rows(…)` copied, changed, throws "The database changed after …". Build again against the migrated database, and add before you remove (https://reylo.dev/#deploying).

## Migrations

A project starts with `reylo migrate init`, run beside its `package.json` (never in the home directory, which it refuses), which writes its files from the database. It keeps its schema in `reylo/schema.sql` and each change to it in `reylo/migrations/<YYYYMMDDHHMMSS>_<name>.sql`, in the order `reylo/reylo-lock.yaml` lists (https://reylo.dev/migrations). Commit all three. Every command shows the same help (`reylo migrate --help`), and a flag only ever modifies a command.

- To change the schema, edit `reylo/schema.sql`, then `reylo migrate new <name>`: Reylo writes the migration from what the migrations make to `schema.sql`, checked in a shadow database, never reading the database's schema. Read the file it writes, and add the data changes a schema can't say. Never write a migration's DDL by hand where `new` can write it. With nothing to change, the file is empty, for a data change.
- `new` refuses a change that drops a table or a column, or changes a column's type so that values are lost, until `--drop <table or table.column>` names it. Name only what the change is meant to lose. A column or table that goes while one identical but for its name comes is renamed, keeping its rows. One that also changes is refused, with one command for a rename (`--rename <table.old>=<new>`) and one for a drop: read the two names, and pick by what they mean.
- In development, `reylo migrate dev` runs the new migrations and adds them to the lock; until then a migration is a draft, free to edit. It refuses a change on the database that neither `schema.sql` nor a pending migration makes, and prints three fixes: add it to `schema.sql` and run `reylo migrate new <name>`, undo it with the `reylo run '<sql>'` it prints, or `reylo db reset`. `reylo db push` makes what `schema.sql` adds without a migration, to try a change; it refuses until `reylo migrate dev` has run. After a branch switch or a lock conflict (keep main's lines), run `reylo migrate dev` again. `reylo db reset` drops everything but a platform's own objects, with its rows, and runs every migration again; `reylo db wipe` deletes every row and keeps the schema and the history.
- `reylo migrate status` checks a database against the migrations: what it ran, what's pending, whether it was changed by hand since its last migration (with the change), and every check of the files (their names, git's conflict markers, the lock's chain, and `schema.sql` against the checksum the lock holds). It reads only and needs no shadow database. It exits 1 where the database and the files aren't in step, and 0 where they are: check it before acting on a database. A `schema.sql` edited since the lock was written needs `reylo migrate new <name>`, then `reylo migrate dev`; formatting or comments alone need only `reylo migrate dev`.
- Never edit a migration the lock lists, which another database may have run: write a new one. The exception is one that failed on production, which records nothing of a failed migration: fix the file, run `reylo migrate dev` to lock it again, and deploy the fix. Never edit `reylo/reylo-lock.yaml` by hand but to keep main's side of a conflict; `reylo migrate lock` writes it again from a database's history.
- The migration files and a database's history table are two copies of one list, and its tables say which is right. Where the files are right (a change made by hand, then written into `schema.sql` and a migration), `reylo migrate history push --url <that database>` records what its schema has, running nothing. Where the database is right (a file edited or deleted, a lock lost), `reylo migrate history pull --url <that database>` writes them back as it ran them; it refuses a database changed by hand. `reylo db introspect` prints a database's schema as SQL, for a change made by hand: copy it into `schema.sql`, then `reylo migrate new <name>` writes the migration.
- On DuckDB, the migrations run on the DuckDB the project's `@duckdb/node-api` installs, which it needs installed. A change DuckDB's `alter table` can't make (a check or a foreign key added, a column an index covers changed, a macro or an enum a check calls changed) is written as a rebuild, which copies the table's rows, and those of the tables that reference it: read the migration before running it on a large table. A changed sequence starts again where `schema.sql` starts it, and the migration says so. DuckDB refuses an `update` of a table followed by `set not null` or a new index on it in one migration: put a backfill in a migration of its own (https://reylo.dev/duckdb#migrations).
- In CI, and before a deploy, `reylo migrate deploy --dry-run` replays the migrations in shadow databases against `schema.sql` and the database, running nothing. In production, `reylo migrate deploy` runs what the lock lists and needs no shadow database. It refuses a database changed by hand, an added index too, showing the change: write it as a migration and record it with `reylo migrate history push`. Read a refusal, which names the fix. The development commands (`migrate dev`, `db push`, `db reset`, `db wipe`) refuse to run where `CI` is set.
- Without `reylo/schema.sql`, the migrations are the schema: write them by hand, or change the development database and run `reylo migrate new <name>`, which writes what the database has that the migrations don't make, and refuses until every migration has run there. Without `reylo/reylo-lock.yaml`, migrations run in name order and `reylo migrate status` says so; a migration that sorts before one a database already ran is replayed in both orders, and refused where they end differently: give it a later name. Keep both files unless the project chose otherwise.
- Pass `--json` to every migration command an agent or a script runs: it prints one object with `ok`, `exit`, `result` (a status lists each migration's `state`), and `problems`, each with a stable `code` (`database-changed`, `schema-sql-changed`, `unexplained-change`, `late-migration-differs`, `merge-conflict-markers`) and `fixes` as `{ what, commands }`. Branch on the `code`, never on the wording (https://reylo.dev/migrations#json-output).
