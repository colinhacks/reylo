# Reylo Type Defs

Reylo Type Defs (RTD), in preview until 1.0.0: the result of introspecting one SQL statement, and the type descriptor of each parameter and column in it: which values the slot can hold, across relational databases. A descriptor is data, written as JSON, YAML or anything else that carries objects, lists, strings, numbers and booleans.

- [`typedefs.schema.json`](./typedefs.schema.json) is the format, as a JSON Schema (2020-12), and its source of truth. Each version is published at `https://reylo.dev/typedefs/<version>.json`, the URL every descriptor names in `$schema`.
- [`index.ts`](./index.ts) is the same format as TypeScript types, generated from the schema by `nub run typedefs`.
- [`examples.ts`](./examples.ts) holds descriptors from each database, each with the schema and statement it describes, checked against both. Those of Postgres, MySQL and SQLite are what Reylo's engine writes for their statements, which a test holds them to; those of SQL Server, Oracle and DuckDB are written by hand. [`examples.json`](./examples.json) is the same examples as JSON, generated by `nub run typedefs`.

The spec is a living document, and every part of it was weighed against the databases it covers. A change to it is a design decision: agree it with a maintainer before writing it, and where implementing it shows a limitation, raise the limitation rather than working around it.

## Dates and times

One kind per class every language has, as Temporal draws them: a date, a time of day, a wall-clock date and time, an instant, a date and time with its zone, and a duration. Each but the time of day may hold infinity and -infinity too, as Postgres's do. Wall-clock time is never an instant: a time with no zone cannot be read as UTC. An `instant` is the moment alone, so a `timestamptz`, which keeps no offset, is one; a `zoned_datetime` keeps the zone each value was written in, a region or an offset, as SQL Server's `datetimeoffset` keeps its offset. `tick` is the smallest step, in seconds, in lowest terms: `"1/1000000"` (microseconds), `"1/300"` (SQL Server `datetime`), `"60"` (`smalldatetime`). A date-bearing kind's range is 0001-01-01 to 9999-12-31, and a time's 00:00:00 up to 24:00:00, unless its bounds say otherwise.

## Text

Text with no `encoding` is any valid Unicode text. An `encoding` is one of a closed list of character sets, and each name stands for one mapping table, so that its characters are a fixed set:

| Names | Characters |
| --- | --- |
| `UTF-8`, `UTF-16`, `UTF-32`, `CESU-8`, `GB18030` | Every Unicode scalar value |
| `US-ASCII`, `ISO-8859-1` | U+0000 to U+007F, and U+0000 to U+00FF |
| `ISO-8859-2` to `ISO-8859-16` | Unicode's mapping files of those names (`MAPPINGS/ISO8859`) |
| The `windows-` pages, `IBM866`, `KOI8-R`, `KOI8-U`, `macintosh`, `Shift_JIS`, `EUC-JP`, `ISO-2022-JP`, `EUC-KR`, `GBK`, `Big5` | The WHATWG Encoding Standard's index of the name, whose `windows-1252` holds 256 code points |
| `Windows-31J`, `Big5-HKSCS` | WHATWG's `Shift_JIS` and `Big5` indexes, which are theirs |
| `IBM437`, `IBM850`, `IBM852` | Unicode's `VENDORS/MICSFT/PC` tables (`CP437.TXT`) |
| `TIS-620` | Unicode's `ISO8859-11` file, less 0xA0 |
| `GB2312` | Unicode's `EASTASIA/GB/GB2312.TXT`, in EUC-CN |
| `DEC-MCS`, `hp-roman8`, `SEN_850200_B` | RFC 1345's charts of those names |

Where vendors' tables for a name differ, it stands for the widest of them, so a value any of them writes is one of its characters. `code_points` narrows the characters further, by Unicode code point, whatever the encoding: Postgres's text holds every character but NUL, `[[1, 1114111]]`, and MySQL's `utf8mb3` only the Basic Multilingual Plane. A pattern is an I-Regexp (RFC 9485), matched against the whole value. A `format` names what the text is, by JSON Schema's format names (`email`, `uri`, `hostname`) or a source's own, and a consumer that does not know one ignores it.

## Rules

1. **A consumer reads `kind`, the fields its kind requires (an integer's `bits`, a float's widths, a time's `tick`, a duration's `max`, an enum's `type` and `values`, a table's `cardinality` and `columns`) and the widening fields, and may ignore the rest.** That is enough to pick a representation that holds every value it can receive. A field either widens the type or narrows it, on its own, so any combination is valid, and a text's `size` is read with its `unit`, which says what it counts. A flag is a boolean written only when true: its default is false. The widening fields are a closed list, and a new one means a new major version, while a narrowing one may come in a minor version, since a consumer that ignores it stays sound:
     - `nullable` on a slot, and `optional` on a field and a parameter;
     - a tuple's `optional_elements` and `rest`;
     - `unsigned` on an integer;
     - `infinity` and `nan`;
     - `offset` on a time;
     - `ill_formed` on text;
     - `extra` on a struct, and `fragment` on XML;
     - the parts a duration's `max` writes, each a part its values may carry;
     - a date-bearing kind's bounds beyond 0001-01-01 to 9999-12-31, and a time's reaching 24:00:00.

   A new kind may come in a minor version too, since a consumer that does not know it reads it as rule 6 says.

   Some fields neither widen nor narrow: a type's `title` and `comment`, and a field's `title`, `comment`, `read_only` and `write_only` describe the type or say which way a value travels, never which values it holds. They may come in a minor version too.

2. **A type is what the database guarantees**, never only what was declared: a SQLite column that is not STRICT is the union of what its affinity stores. A bound or a list of values appears only when it is true of every finite value, the `infinity` and `nan` flags speaking for the rest: from a type modifier, a validated CHECK on a column read straight from its table, a domain's check, or a constant the statement writes, which makes the column an `enum` of the constants it holds. A constraint that is not validated is not reported, and neither is a domain's NOT NULL, which an outer join defeats. A value a database stores only under a lax setting its default refuses is not typed, and a client that meets one refuses it: MySQL's zero and partial dates (`0000-00-00`, `2026-00-15`) and the empty error value of its enums. So is a Postgres array deeper than the one dimension its type is written with: Postgres keeps any number of dimensions in an array column, and the format writes the array flat, as almost every column holds it.

3. **A value is what the type denotes, never its encoding.** A decimal is a number, so `1.5` and `1.50` are one value; a `timestamptz` is one instant however a session prints it; a duration is its months, days and time, so `1 mon` and `30 days` are two values though Postgres finds them equal; an array is its elements, wherever its index starts. Two values are equal, for `distinct` and a table's `unique`, as the database's own equality finds them, and its `order` is the database's own sort, under the column's collation: two strings a collation finds equal may be different text, and the format names no collation. The format says nothing about how a driver or protocol encodes a value: decoding is the driver's.

4. **One spelling per meaning.** A modifier goes in the type's fields, the database's name for it in `label`, nullability on the slot. Defaults are omitted, and so is a bound other fields imply. A fixed list of values is one `enum` over its type, never a union of enums, and a value that is always null is the `null` kind in a nullable slot. Unions and intersections are flat, of two members or more, none of them `null`; an intersection one struct can write is written as that struct. A union lists its members in the order `Type` lists the kinds, and members of one kind in the order the database declares them (an object type before its subtypes; an `inet`'s IPv4 struct before its IPv6 one).

5. **Values inside the format are strings** in the kind's canonical text, so a 64-bit bound or a date survives any serialization; counts (`bits`, a size, a precision or scale), versions and code points are numbers. A boolean's text is `true` or `false`, a number's is decimal with no exponent and no zero it needs not (`1.5`, `-0.25`), and bytes' is base64 (RFC 4648, padded). Dates and times are ISO 8601, with a sign and more than four digits where a year needs them (`-4713-11-24`, `+5874897-12-31`), which RFC 3339 cannot write. Durations are ISO 8601 durations, with a sign on each part where the parts' signs differ, as Postgres writes them (`P1M-1D`).

6. **A consumer that meets an unknown kind** reads it as `opaque` at a SQL slot and as any JSON inside JSON content, and reads an unknown value of a known field the same way. It ignores a field it does not know, which can only narrow, since a widening field comes with a new major version.

7. **Validity rules**, for what no shape can rule out, each a check a validator runs:
     - a side of a range takes one of `min` and `exclusive_min` (or `max` and `exclusive_max`), and a minimum is at most its maximum (bounds, sizes, scales);
     - a size's `exact` never sits beside its `min` or `max`, and its `min` never equals its `max`;
     - a text's `ill_formed` and its size's `unit` appear only beside its `encoding`, and a Unicode encoding appears only beside one of them; its code points are sorted, disjoint, never adjacent, and at most 1114111;
     - a tick is positive, and so are a float's widths;
     - an enum's type is a kind whose values have canonical text, and no enum; its values are one or more distinct values of that type, and never both booleans;
     - the `null` kind stands only in a nullable slot;
     - a struct with `extra` has a field, since one with none is a map;
     - a tuple has an element or an optional one;
     - a table of capabilities names each table it lists;
     - a table's columns are never optional, and `unique` and `order` appear only where its cardinality is `many`, each naming its columns, and `order` each once;
     - a UUID's versions are 1 to 8, in order, each once;
     - a field's `default` appears only beside `optional`;
     - a field's `read_only` never sits beside its `write_only`;
     - a duration's `max` writes each part above zero, with no leading zero, and its minutes and seconds below 60, and the duration has a `tick` exactly when that `max` has a time part.

8. **Versions are semantic**, and a descriptor names its own in `$schema`. A patch version changes no descriptor; a minor version may add a kind or a narrowing field, which a consumer of the version before stays sound ignoring (rules 1 and 6); a major version may change anything. Before 1.0.0 the minor number stands for the major one and the patch number for the minor one: 0.2.0 may change anything 0.1.0 says, and 0.1.1 only what a minor version may.

## Facts about each database

What an implementation needs, and the format does not state on every node.

What a SQLite column that is not STRICT holds, by its declared type's affinity: an `INTEGER` or `NUMERIC` column any of an integer, a float, text and bytes; a `REAL` column a float, text or bytes; a `TEXT` column text or bytes. A column with no declared type is `unknown`. A STRICT column holds its declared type alone.

Which types hold infinities and NaN: Postgres's floats (both), `numeric` (NaN, and with no size the infinities), `date`, `timestamp`, `timestamptz` and, from version 17, `interval`; SQLite's `REAL` holds the infinities and stores a NaN as NULL. MySQL has none, refusing NaN and the infinities even in `FLOAT` and `DOUBLE`.

What a database writes inside its own JSON:
  - Postgres:
      - a `boolean` is `true` or `false`;
      - an integer, a float or a `numeric` is a JSON number, a `numeric`'s of any length and an `int8`'s one that may pass 2^53, and a float's or a `numeric`'s NaN or Infinity a string;
      - a `date`, a `timestamp` and a `timestamptz` are ISO 8601 (`"2026-01-02T03:04:05"`), a `timestamptz` in the session's offset (the offset can carry seconds), a BC year with a suffix (`"0001-01-01 BC"`), and an infinity the string `"infinity"` or `"-infinity"`;
      - an array is a JSON array of its elements, and a composite or any other row an object of its fields (`row(1, 'x')` is `{"f1":1,"f2":"x"}`);
      - an `hstore` is an object of nullable text, and PostGIS's `geometry` GeoJSON;
      - `jsonb` sorts keys and keeps the last duplicate, while `json` keeps the text as written;
      - every other type is a string of its text, structured or not: `bit` and `varbit` (`"101"`), the geometric types (`"(1,2)"`, `"[(0,0),(1,1)]"`), `inet`, `cidr`, `macaddr` and `macaddr8`, ranges and multiranges (`"[1,5)"`), `interval` in the session's IntervalStyle (`"1 mon -1 days"`), `time`, `uuid`, `money`, `oid`, `xml`, and `bytea` in the session's `bytea_output` (hex by default, `"\\x0102"`).
  - MySQL:
      - a `DATETIME` or `TIMESTAMP` is a string with a space and six fractional digits, and a `TIME` its text with six fractional digits (`"12:00:01.500000"`);
      - a `DECIMAL` is a number that keeps its scale, and a `YEAR` a number;
      - a comparison is `true` or `false`;
      - an `ENUM` is its value as text, and a `SET` its elements joined by commas (`"a,b"`);
      - a binary value, a `BIT` among them, is `"base64:type15:…"`, the number its protocol type;
      - a spatial value is GeoJSON;
      - the last duplicate key wins.
  - SQLite: ±Infinity is the number `9e999`, and a blob is never a JSON value.

Bounds no field states:
  - offsets: Postgres's run to ±15:59:59, SQL Server's to ±14:00;
  - Postgres's `jsonb` refuses `\u0000`, as its text holds no NUL;
  - Oracle `VARCHAR2(n CHAR)` is also capped at 4,000 bytes, which its one size, in code points, leaves out.

Each Postgres, MySQL and SQLite type as the engine writes it is on that database's page of the docs (reylo.dev/postgres, /mysql and /sqlite). Other databases' types, as a source would write them:
  - SQL Server: `bit` is a `boolean`, `tinyint` an 8-bit unsigned integer, `float` a double, and `money` a decimal of precision 19 and scale 4 from -922,337,203,685,477.5808 to 922,337,203,685,477.5807; `nvarchar`, `nchar` and `ntext` are ill-formed UTF-16 text whose sizes count code units; `rowversion` is 8 bytes and `uniqueidentifier` a UUID; `datetime2` is a `datetime`, `datetime` one of tick `1/300` and `smalldatetime` one of tick `60`, and `datetimeoffset` a `zoned_datetime` of offsets alone; `hierarchyid` and `sql_variant` are opaque; and `select 1`'s column has an empty name.
  - Oracle: `NUMBER` is a decimal of precision 40 below 10^126 in magnitude, `NUMBER(5,-2)` one of scale -2, rounding to hundreds, and `INTEGER` one of scale at most 0; `VARCHAR2(20 CHAR)`, which stores `''` as null, is text of 1 to 20 code points, and `NVARCHAR2` counts UTF-16 units; `RAW(n)` is bytes; `DATE` is a `datetime`, `TIMESTAMP WITH LOCAL TIME ZONE` an `instant`, and `TIMESTAMP WITH TIME ZONE` a `zoned_datetime`, each value's zone a region or an offset; `INTERVAL YEAR TO MONTH` is a duration of months alone (`P1199M`) and `INTERVAL DAY TO SECOND` one of time alone (`PT2399H59M59.999999S`), a day being 24 hours; a `BFILE` is a struct, `{ directory, file }`; an object type with subtypes is a union of the structs of each; a nested table is a `table`; and `ANYDATA` is opaque.
  - DuckDB: `HUGEINT` is a 128-bit integer and `UHUGEINT` an unsigned one; a `LIST` and an `ARRAY` are arrays whose elements may be NULL; a `STRUCT` is a struct whose fields may each be NULL, and one whose fields have no names a tuple of its values in order, each of which may be NULL too; a `MAP` is a map; and a `UNION` is a tagged union whose every alternative may hold NULL.
  - Elsewhere: `DECFLOAT(34)`, IEEE's decimal128, is a decimal of precision 34 and scale -6111 to 6176 with the infinities and NaN; Vertica's `TINYINT` is 64 bits; ClickHouse's `BFloat16` is a float of widths 8 and 7, and its `String` ill-formed UTF-8 text, as is the text of a Postgres `SQL_ASCII` database and Firebird's `NONE`; Firebird's `WITH TIME ZONE` types are `zoned_datetime`; Cassandra's `timeuuid` is a UUID of version 1; MariaDB's `UUID` is a UUID; and Teradata's `PERIOD` is a range.
