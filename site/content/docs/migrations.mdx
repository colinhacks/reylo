<p className="dk-subheader">Declare your schema in SQL, and let Reylo write each migration</p>

You declare the schema you want in `reylo/schema.sql`. Reylo writes each change to it as a migration, a plain `.sql` file in `reylo/migrations/`, and checks every migration against a throwaway copy of your database before anything runs it.

| | |
| --- | --- |
| Databases | Postgres, MySQL and SQLite |
| Files | `reylo/schema.sql`, `reylo/migrations/` and `reylo/reylo-lock.yaml`, committed |
| Commands | `reylo migrate create`, `apply`, `sync`, `check` and a few more ([Commands](#commands)) |

## Setup

Add a `migrate` section to `.reylo.yaml`. Reylo migrates the database `direct_url` names, unless the section names another:

```yaml title=".reylo.yaml"
direct_url: ${DATABASE_URL}
migrate:
  # the database to migrate (default: direct_url)
  url: ${DATABASE_URL}
```

Then write the schema you want into `reylo/schema.sql`:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null
);
```

To start from a database you already have, run `reylo migrate init`. It writes `schema.sql` and a first migration from the database, and records that migration as applied.

## Write a migration

Change `schema.sql`, then name the change:

```sh
reylo migrate create add_bio
```

Reylo writes the SQL that takes your migrations to `schema.sql`, runs it on a shadow database to check it reaches `schema.sql`, and writes the file, noting at its top anything left for you to finish:

```text
reylo/migrations/20261104140347_add_bio.sql
```

The file is yours: read it, edit it, add the data changes a schema can't say. A table or column that goes while one like it comes is renamed, keeping its rows, and the file says so.

## Apply it in development

To run your new migrations on your development database:

```sh
reylo migrate apply --dev
```

```text
✓ Applied 20261104140347_add_bio.sql · 4 ms
✓ Locked 20261104140347_add_bio.sql in reylo/reylo-lock.yaml
```

Until `apply --dev` runs it, a migration is a draft: edit it freely, since no other database runs it. After a branch switch, `apply --dev` also rewinds what your database ran that the migrations no longer hold, then runs the rest.

### Try a change first

To make what `schema.sql` adds on your development database without writing a migration yet:

```sh
reylo migrate sync
```

```text
✓ Brought this database to schema.sql, unrecorded:

    alter table users add column bio text;

  schema.sql has changes not reflected in any migration file. Write them as a migration:
    reylo migrate create <name>
```

With `--watch`, it syncs again each time you save `schema.sql`. When you then write the migration, `apply --dev` records it without running it again, since your database already has its change.

## Apply it in production

In your deploy, or as your app starts:

```sh
reylo migrate apply
```

It runs only the migrations the lock lists, in its order, and refuses a database whose history disagrees with them, running nothing:

```text
✗ This database has changes no migration made

    create index users_bio on users (bio);

  Keep it: add it to schema.sql, write the migration, then record the history the database has, running nothing:
    reylo migrate create <name>
    reylo migrate sync-history
  On a development database, start over from the migrations (loses its data):
    reylo migrate apply --reset

Nothing was applied.
```

On Postgres and SQLite, each migration runs in one transaction with its history row; on MySQL, where a schema change commits on its own, each migration holds one. With nothing pending, and the database as Reylo's last run left it, `apply` replays nothing; otherwise it checks the database first in shadow databases, on the same server or on the one `migrate.shadow_url` names.

## Data loss

To drop data, you name it. A migration that drops a table or a column, or changes a column's type in a way that loses values, needs it named in `--drop`:

```text
✗ This migration would drop users.email, and its data

  To drop it:
    reylo migrate create drop_email --drop users.email
  If a column was renamed instead:
    reylo migrate create drop_email --rename users.email=<new name>
```

A table or column that goes while one like it comes is renamed instead, keeping its rows, and `create` says so: name it in `--drop` where they are two. Use `--rename` where Reylo can't tell which of two columns became which.

## Branches

The lock lists your migrations in the order they run. When two branches each add one, git conflicts on it, before anything is deployed. Keep main's lines, then run your branch's migrations after them:

```sh
reylo migrate apply --dev
```

It rewinds your branch's migrations, runs main's, runs yours again after them, and adds them back to the lock. For a project that would rather not keep a lock, `reylo migrate unlock` deletes it; migrations then run by name, and one that lands older than one applied runs only where neither changes data and both orders end the same.

## Check in CI

To check the migrations against `schema.sql` and the database, running nothing:

```sh
reylo migrate check
```

```text
✓ The migrations reach reylo/schema.sql, and this database matches its history
✓ Nothing is pending
```

With `--offline`, it checks what needs no database: the lock against the files, and `schema.sql` against the checksum the lock holds from the last time the migrations reached it.

## A change made by hand

To keep a change someone made on a database by hand, add it to `schema.sql`, write the migration, and apply it in development, which locks it:

```sh
reylo migrate create <name>
reylo migrate apply --dev
```

Once that lock is committed, record the change on the database that has it, running nothing. It records the migrations the database's schema already has, once a shadow database shows they make exactly it:

```sh
reylo migrate sync-history
```

## Commands

| Command | What it does |
| --- | --- |
| `reylo migrate create <name>` | Writes the migration that takes the migrations to `schema.sql` |
| `reylo migrate apply` | Checks the database, then applies what the lock lists and it hasn't run |
| `reylo migrate apply --dev` | Takes a development database to its migrations, and locks new ones |
| `reylo migrate sync` | Makes what `schema.sql` adds on a development database, unrecorded |
| `reylo migrate check` | Checks the migrations against `schema.sql` and the database; runs nothing |
| `reylo migrate sync-history` | Records what the database's schema already has; runs nothing |
| `reylo migrate restore <file>` | Writes back the text a database ran for a migration |
| `reylo migrate wipe` | Deletes every row, keeping the schema (development) |
| `reylo migrate apply --reset` | Drops everything and applies every migration again (development) |
| `reylo migrate lock`, `unlock` | Keeps the lock, or stops keeping it |
| `reylo migrate init` | Writes `schema.sql` and a first migration from a database |

The development commands refuse to run where `CI` is set. To run a seed after `apply --reset` and `wipe`, set `migrate.post` ([Configuration](/#configuration)).
