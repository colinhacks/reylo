<p className="dk-subheader">Put your schema in a SQL file, and Reylo writes the migrations</p>

Reylo's migrations are separate from its `.sql` imports: each works without the other, and your own migration tool works just as well.

<Features>
<Feature icon="file" title="One schema file">

Your schema lives in `schema.sql`, and Reylo writes each migration from your changes to it.

</Feature>
<Feature icon="branch" title="Linear history">

A lockfile lists your migrations in order, so two branches that each add one conflict in git, before anything deploys.

</Feature>
<Feature icon="database" title="Postgres, MySQL and SQLite">

One set of commands for all three.

</Feature>
<Feature icon="shield" title="No silent data loss">

A migration drops nothing until you say so with `--drop`, and `--rename` settles what Reylo can't tell apart.

</Feature>
<Feature icon="hash" title="Integrity checks">

Chained hashes in the lock catch a migration edited, deleted or reordered, with no database. A fingerprint on each database catches a change made by hand, and shows it.

</Feature>
<Feature icon="layers" title="Real dry runs">

Reylo replays your migrations on a throwaway database, so `reylo migrate deploy --dry-run` shows what a deploy would do, running nothing on yours.

</Feature>
</Features>

## Basic usage

Install Reylo, and start your migrations from your database:

```terminal
$ npm install reylo
$ npx reylo migrate init
✓ Wrote reylo/schema.sql, reylo/migrations/init.sql and reylo/reylo-lock.yaml
  + init.sql recorded, not run: already in place
✓ The history lists the 1 migration this database's schema has
```

Commit the files it writes, all but the cache:

```terminal
reylo/
├── schema.sql              # the schema you want
├── migrations/             # each change, as plain SQL
│   └── init.sql
├── reylo-lock.yaml         # the order they run in
└── .cache/
    └── .gitignore          # keeps the cache out of git
```

To change your schema, edit `schema.sql`, which holds all of it:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null -- [!code --]
  email text not null, -- [!code ++]
  bio text -- [!code ++]
);
```

Write the migration:

```terminal
$ npx reylo migrate new add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql
```

Read what it wrote. It's plain SQL, the change and nothing else, and yours to edit:

```sql title="20261104140347_add_bio.sql"
alter table users add column bio text;
```

Run it on your development database:

```terminal
$ npx reylo migrate dev
Applying to postgres://localhost:5432/app
  ✓ 20261104140347_add_bio.sql  applied · 4 ms
Wrote reylo/reylo-lock.yaml
```

Commit the migration and the lock. When you deploy, run it on production:

```terminal
$ npx reylo migrate deploy
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
```

## Configuration

Each setting is optional. Here they are with their defaults:

```yaml title=".reylo.yaml"
# The database Reylo migrates
direct_url: ${DATABASE_URL}

# The directory of schema.sql, the migrations, the lock and the cache
dir: reylo

# A server for shadow databases; null uses your database's own
shadow_url: null
```

To migrate another database, pass `--url`.

## Shadow databases

Reylo reads your SQL with a real database.

It makes a throwaway database beside yours, runs your migrations on it, reads the schema they make, and drops it. That's why hand-written SQL counts, and why there's no snapshot file to keep in step. You don't set anything up: on a local database you're a superuser on, you'll never notice them. Writing and repairing migrations need one, and a deploy doesn't:

| Needs a shadow database | Needs none |
| --- | --- |
| `reylo migrate init` | `reylo migrate deploy` |
| `reylo migrate new` | `reylo migrate lint` |
| `reylo migrate dev` | `reylo migrate status` |
| `reylo migrate deploy --dry-run` | `reylo db introspect` |
| `reylo migrate lock` | `reylo db wipe` |
| `reylo migrate history push` | |
| `reylo migrate history pull` | |
| `reylo db push` | |
| `reylo db reset` | |

Each database makes them its own way:

- **Postgres:** on your database's server, with `create database`, so your role needs `CREATEDB`. A local superuser has it, and so do the roles Neon and Supabase give you. Reylo keeps up to 32 as a cache, named `reylo_cache_…`, so a run replays only the migrations that are new.
- **MySQL:** on your database's server, with `create database`, so your user needs the `CREATE` privilege on every database.
- **SQLite:** in memory. There's nothing to grant.

On Supabase, each shadow also gets what Supabase made in your database: its extensions, and its own schemas such as `auth` and `storage`. A migration that references `auth.users`, or adds a policy on `storage.objects`, replays as it runs.

Where your role can't create a database, point `shadow_url` at a server that can, running the same version:

```yaml title=".reylo.yaml"
# A local Postgres 18, for a hosted Postgres 18
shadow_url: postgres://localhost:5433/postgres
```

## The lock

The lock lists your migrations in the order they run.

Each line has a checksum chained to the line before. A migration it doesn't list is a draft, free to edit, which only `reylo migrate dev` runs:

```yaml title="reylo-lock.yaml"
schema: c7bf681b
migrations:
  - 20261104120000_users.sql c86e9de4
  - 20261104140347_add_bio.sql 78ad08c0
```

When two branches each add a migration, git conflicts on the lock, before anything is deployed. Keep main's lines, then run `reylo migrate dev`, which runs your branch's migrations after main's and adds them back.

## Schemaless mode

Delete `schema.sql`, and your migrations are your schema.

Write each migration by hand, or change your development database and let `reylo migrate new` write what it has that your migrations don't make:

```terminal
$ reylo run 'alter table users add column bio text'
✓ alter table users add column bio text

$ reylo migrate new add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql

$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ! 20261104140347_add_bio.sql  recorded, not run: already in place
Wrote reylo/reylo-lock.yaml
```

What changes:

- The checks against `schema.sql` are skipped, and each command that would run one says so.
- Your development database stands in for `schema.sql`, so `reylo migrate new` refuses until it has run every migration. One it hasn't would read as a drop.
- With no `schema.sql` to push, `reylo db push` refuses: try a change on your database directly.

You give up the one file that shows your whole schema, and the check that your migrations make the schema you meant.

## Lock-free mode

Delete `reylo-lock.yaml`, and your migrations run in name order.

Every command says so:

```terminal
$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ✓ 20261105090000_tags.sql  applied · 3 ms
No reylo/reylo-lock.yaml: migrations run in name order, and a database may have run them in another (reylo migrate lock writes one)
```

Two branches that each add a migration then merge with no conflict, and a database may have run a migration that now sorts after the merged one. On a shadow database, `reylo migrate dev` and `reylo migrate deploy` replay such a migration in both orders, and refuse it where the two end differently:

```terminal
$ reylo migrate deploy
✗ 20261105080000_no_nick.sql sorts before 20261105090000_nick.sql, which this database already ran, and the two orders end differently
  + a fresh database: column public.users.nick text
  Give 20261105080000_no_nick.sql a later name, so that every database runs it after 20261105090000_nick.sql

Nothing was applied.
```

You give up:

- **The same data everywhere.** Columns are compared as a set, as everywhere in Reylo, and no check can show that data written in two orders matches.
- **Checks with no database.** With no checksums, `reylo migrate lint` can't see a migration edited or deleted, or hold `schema.sql` against your migrations.

To turn the lock back on, `reylo migrate lock` writes it from a database's history.

## CLI

Every command and flag:

```terminal
Usage: reylo <group> <command> [flags]

Commands:
  migrate init             Start from this database
    --schema <name>        A schema to read (Postgres; public by default)
  migrate new <name>       Write the next migration, from schema.sql or this database
    --drop <names>         Accept what it drops: tables and columns
    --rename <old>=<new>   Say a table or column was renamed
  migrate lint             Check the migrations, the lock and schema.sql, with no database
  migrate status           Show what this database ran, what's pending and what changed
  migrate dev              Take this database to the migrations, and lock them
  migrate deploy           Run what the lock lists, with no shadow database
    --dry-run              Try it on a shadow database, running nothing here
  migrate lock             Write the lock from this database's history
  migrate history push     Record the migrations this database's schema has
  migrate history pull     Write the migrations this database ran into files
  db push                  Take this database to schema.sql, unrecorded
    --watch                Again on each change
  db introspect            Print this database's schema as SQL
    --schema <name>        A schema to read (Postgres; public by default)
  db reset                 Rebuild this database from the migrations
  db wipe                  Delete every row, keeping the schema

Flags:
  --url <url>              The database, in place of direct_url
  --json                   Print the result as one JSON object
  -h, --help               Print this help
```

<Callout title="Development only">

The commands that change a database in ways no deploy wants, `migrate dev`, `db push`, `db reset` and `db wipe`, refuse to run where `CI` is set.

</Callout>

## `reylo migrate`

Writes, checks and runs your migrations.

Your migration files and your database's history table are two copies of one list, and your tables say which is right. The two `history` commands copy the right one over the other.

### `reylo migrate init`

Starts your migrations from a database you already have.

It writes `schema.sql`, a first migration and the lock, and records that migration as run:

```terminal
$ reylo migrate init
✓ Wrote reylo/schema.sql, reylo/migrations/init.sql and reylo/reylo-lock.yaml
  + init.sql recorded, not run: already in place
✓ The history lists the 1 migration this database's schema has
```

### `reylo migrate new`

Writes the next migration, from your change to `schema.sql`.

- It replays your migrations on a shadow database, and writes the change from what they make to `schema.sql`. It never reads your database's schema.
- With no `schema.sql`, it writes what your development database has that your migrations don't make ([Schemaless mode](#schemaless-mode)).
- The file is yours: read it, and add the data changes a schema can't say.
- It names anything in `schema.sql` that Reylo compares by name only, or not at all, such as a text search configuration or a security label. Write a change to those by hand.

Nothing is dropped until you name it. A change that drops a table or column, or changes a type so that values are lost, is refused:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null, -- [!code --]
  email text not null -- [!code ++]
  bio text -- [!code --]
);
```

```terminal
$ reylo migrate new drop_bio
✗ This migration would drop users.bio, and its data

  To drop it:
    reylo migrate new drop_bio --drop users.bio

No migration was written.
```

A column that goes while one just like it comes is a rename, which keeps its rows:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null,
  bio text -- [!code --]
  about text -- [!code ++]
);
```

```terminal
$ reylo migrate new about
! Renames, keeping rows:
    users.bio → about
  If they are two, state it: --drop users.bio
✓ Wrote reylo/migrations/20261104150000_about.sql
```

Where the new one differs too, only you can say what it is. Reylo lists every such pair, and writes nothing until you settle them:

```terminal
$ reylo migrate new tidy
✗ These 2 look like renames, but each changes more than its name

    posts.title → heading  text → character varying(100)
    users.bio   → about    text → character varying(200)

  If they are renames, keeping their rows:
    reylo migrate new tidy \
      --rename posts.title=heading \
      --rename users.bio=about
  If they are new, dropping the old ones and their data:
    reylo migrate new tidy --drop posts.title,users.bio

No migration was written.
```

Where the schema hasn't changed, the migration is empty, for a change of data:

```terminal
$ reylo migrate new backfill
The migrations already make reylo/schema.sql, so the migration is empty, for a change of data
✓ Wrote reylo/migrations/20261104160000_backfill.sql
```

### `reylo migrate lint`

Checks your migrations, the lock and `schema.sql`, with no database.

It reads the files alone: their names, whether each runs atomically, git's conflict markers, the lock's chain, and `schema.sql` against the checksum the lock holds. Run it in a pre-commit hook:

```terminal
$ reylo migrate lint
✓ reylo/reylo-lock.yaml lists every migration, in order, as written
✓ The migrations reach reylo/schema.sql
```

It refuses a `schema.sql` that no migration has been shown to reach yet:

```terminal
$ reylo migrate lint
✗ reylo/schema.sql changed since the migrations were last shown to reach it
  reylo/reylo-lock.yaml holds the checksum of the reylo/schema.sql its migrations make.

  A change to the schema: write its migration, then run it in development:
    reylo migrate new <name>
    reylo migrate dev
  Formatting or comments alone: check it again, which writes no migration:
    reylo migrate dev
```

A lock that holds no checksum of `schema.sql` at all, as one written while your migrations fell short of it, is refused too, until `reylo migrate dev` writes one.

### `reylo migrate status`

Shows what your database ran, what's pending and what changed.

It reads, changes nothing and needs no shadow database. A `!` marks a migration that was cut off, edited since it ran, or deleted:

```terminal
$ reylo migrate status --url $PROD_URL
Migrations on postgres://db.example.com/app
  ✓ init.sql                    applied 2026-11-04 12:00 UTC
  ✓ 20261104140347_add_bio.sql  applied 2026-11-04 15:12 UTC
  · 20261105090000_tags.sql     pending
✗ This database changed since Reylo last ran on it
  + now: column public.users.hotfix bigint
✓ reylo/reylo-lock.yaml lists every migration, in order, as written
✓ The migrations reach reylo/schema.sql
```

### `reylo migrate dev`

Takes your development database to your migrations, and writes the lock.

It runs what is new, and rewinds what no longer agrees, such as a branch's migration after you switch away from it:

```terminal
$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ↺ 20261104120000_tags.sql   rewound: it isn't in the migrations
    Dropped tags, 3 rows
  ✓ 20261104130000_posts.sql  applied · 3 ms
Wrote reylo/reylo-lock.yaml
```

Each time, it takes these steps:

<Steps>
<Step title="Compare" where="your database">

Reads what your database ran, and keeps it as far as it agrees with your migrations, in the lock's order.

</Step>
<Step title="Replay" where="a shadow database">

Runs the migrations it kept on a shadow database, to read the schema they make.

</Step>
<Step title="Rewind" where="your database">

Undoes what your database ran past that point, by the change from what it has to that schema.

</Step>
<Step title="Run" where="your database">

Runs the migrations it hasn't run, as `reylo migrate deploy` will.

</Step>
<Step title="Lock" where="your files">

Writes `reylo-lock.yaml`, listing what ran, in order.

</Step>
</Steps>

It refuses a change on your database that neither `schema.sql` nor a pending migration makes, and shows it as SQL, with three ways out:

```terminal
$ reylo migrate dev
✗ This database has changes nothing in the project makes

    alter table users add column hotfix bigint;

  Keep it: add it to reylo/schema.sql, then write the migration:
    reylo migrate new <name>
  Or undo it:
    reylo run 'alter table users drop column hotfix;'
  Or rebuild this database from the migrations:
    reylo db reset

Nothing was changed.
```

Where nothing changed since its last run, in `schema.sql`, the migrations or your database, it skips the shadow databases and runs what's pending as a deploy does.

### `reylo migrate deploy`

Runs what the lock lists and your database hasn't run, when you deploy.

Each migration runs in one transaction with its history row; on MySQL, where a schema change commits on its own, each holds one change.

```terminal
$ reylo migrate deploy
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
```

It needs no shadow database, so it needs no permission to create one. It refuses to run:

- **On an edited schema file.** A `schema.sql` that isn't the one the lock's checksum is of is refused, as `reylo migrate lint` refuses it.
- **On a database changed by hand.** Each migration it runs stores a fingerprint of the schema, and a database that no longer has it is refused, whatever the change, a hand-added index included.

The refusal shows the change, with the ways to keep it:

```terminal
$ reylo migrate deploy
✗ This database changed since Reylo last ran on it
  + now: column public.users.hotfix bigint

  To keep the change, write it as a migration, then record it here, running nothing:
    reylo migrate new <name>
    reylo migrate history push
  To hold it against the migrations, with shadow databases:
    reylo migrate deploy --dry-run

Nothing was applied.
```

With `--dry-run`, it runs nothing, and replays your migrations on shadow databases instead: against your database, against `schema.sql`, and with what's pending tried on top. Run it in CI, and before you deploy:

```terminal
$ reylo migrate deploy --dry-run
✓ The migrations reach reylo/schema.sql
✓ This database matches its history
✓ 1 pending, and each runs in a shadow database:
    20261104140347_add_bio.sql
```

A migration that fails rolls back, and your database records nothing of it. Fix the file, run `reylo migrate dev`, which locks it again as it now reads, and deploy the fix. A database that already ran the old version refuses the edited one, so where one did, write a new migration instead.

Two things the fingerprint leaves out:

- **Comments.** Your database's `COMMENT ON` comments aren't compared. A migration writes them, but one added in a dashboard stops no deploy.
- **An upgrade.** After a new version of Reylo, or a new major version of your database, the fingerprint it stored can't be compared. A deploy runs, stores a new one and says so, and a dry run checks the database then too.

### `reylo migrate lock`

Writes the lock from your database's history.

It lists the migrations in the order your database ran them, and checks on a shadow database that they reach `schema.sql`. Use it to turn the lock back on ([Lock-free mode](#lock-free-mode)), or to write one that was lost. It refuses where a lock exists, since that one lists what other databases ran too:

```terminal
$ reylo migrate lock
✓ Wrote reylo/reylo-lock.yaml: 2 migrations, in the order this database ran them
✓ The migrations reach reylo/schema.sql
```

### `reylo migrate history push`

Writes your database's history from your migration files, running nothing.

It records the migrations a shadow database shows make the schema your database has; those after them stay pending. It needs your migrations to reach `schema.sql` first:

```terminal
$ reylo migrate history push --url $PROD_URL
  + 20261104160000_users_email.sql recorded, not run: already in place
✓ The history lists the 3 migrations this database's schema has
```

Where your tables hold a change no migration lists, someone made it by hand. Keep it by writing it into `schema.sql` and a migration, then record it on the database that has it:

```terminal
# Print what the database has, and copy the change into reylo/schema.sql
$ reylo db introspect --url $PROD_URL

$ reylo migrate new users_email
$ reylo migrate dev
$ reylo migrate history push --url $PROD_URL
```

### `reylo migrate history pull`

Writes your migration files from your database's history.

A migration someone deleted is written again, one edited since it ran is written over, and a lock that's lost is written back. Files the database hasn't run are left as they are, and listed:

```terminal
$ reylo migrate history pull --url $PROD_URL
Pulling from postgres://db.example.com/app
  ↓ 20261104140347_add_bio.sql  written over: it differed from what ran
Not run on this database, and left as they are: 20261105090000_tags.sql
```

It first replays your database's history in a shadow database. One whose tables differ from what that makes was changed by hand, and is refused: files written from its history wouldn't make it either.

## `reylo db`

Changes your database directly, recording nothing.

### `reylo db push`

Takes your development database to `schema.sql`, with no migration.

It's for trying a change. What the file no longer has is dropped, with its rows:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null,
  bio text -- [!code --]
  bio text, -- [!code ++]
  nick text -- [!code ++]
);
```

```terminal
$ reylo db push
Pushing schema.sql to postgres://localhost:5432/app
  + alter table users add column nick text;

  Not in any migration yet:
    reylo migrate new <name>
```

With `--watch`, it pushes again each time you save. It needs your database at its migrations, so it refuses until `reylo migrate dev` has run. Until you write the migration, `reylo migrate dev` says so, and keeps the lock as it was:

```terminal
$ reylo migrate dev
! The migrations don't make all of reylo/schema.sql yet: reylo migrate new <name> writes the rest
```

Once you write it, `reylo migrate dev` records it without running it again. A `schema.sql` that declares nothing is refused, since it would drop every table, with its rows: to start your database again from the migrations, use `reylo db reset`.

### `reylo db introspect`

Prints your database's schema as SQL, as `reylo migrate init` writes it.

It writes no file. It's the database's own dump, in its own layout:

```terminal
$ reylo db introspect
CREATE TABLE public.users (
    id integer NOT NULL,
    email text NOT NULL
);

ALTER TABLE ONLY public.users
    ADD CONSTRAINT users_pkey PRIMARY KEY (id);
```

To save it over `schema.sql`, write it to another file first. A redirect empties its file before the command runs, so a failed run would leave `schema.sql` empty:

```terminal
$ reylo db introspect > schema.new.sql && mv schema.new.sql reylo/schema.sql
```

### `reylo db reset`

Rebuilds your development database from your migrations.

It drops everything on the database, with its rows, empties the history, and runs every migration as `reylo migrate dev` runs them. A platform's own objects stay, such as Supabase's `auth.users`, and so do the extensions your migrations don't create:

```terminal
$ reylo db reset
Resetting postgres://localhost:5432/app
    Dropped users, 2 rows
Applying to postgres://localhost:5432/app
  ✓ init.sql                    applied · 5 ms
  ✓ 20261104140347_add_bio.sql  applied · 4 ms
```

### `reylo db wipe`

Deletes every row, keeping the schema and the history.

It leaves a platform's own tables alone, such as Supabase's `auth.users`:

```terminal
$ reylo db wipe
✓ Deleted every row of 2 tables; the schema and the history stay
```

## JSON output

With `--json`, a command prints one JSON object, for agents and scripts.

Every command takes it but `reylo db push --watch`:

```terminal
$ reylo migrate status --url $PROD_URL --json
{
  "command": "reylo migrate status",
  "ok": true,
  "exit": 0,
  "result": {
    "migrations": [
      {
        "name": "20261104140347_add_bio.sql",
        "state": "applied",
        "applied_at": "2026-11-04T15:12:00Z"
      },
      {
        "name": "20261105090000_tags.sql",
        "state": "pending"
      }
    ],
    "database": "changed",
    "changes": [
      "+ now: column public.users.hotfix bigint"
    ],
    "lock": "ok",
    "schema_sql": "reached"
  },
  "log": [
    "Migrations on postgres://db.example.com/app",
    …
  ]
}
```

The object holds:

- Whether the command succeeded, in `ok`, and its exit code, in `exit`.
- What it found, in `result`. For a status, that's each migration's state, and the state of the database, the lock and `schema.sql`.
- Each refusal, in `problems`, with a stable `code` such as `database-changed`, and the fixes the terminal shows. Branch on the `code`, which stays the same when the wording changes.
- The schema `reylo db introspect` prints, in `sql`.
- Why a command couldn't start, such as a database it can't reach, in `error`.
- Every line the command would have printed, in `log`.

## Examples

In development:

```terminal
# Write a migration from your change to schema.sql
$ reylo migrate new add_bio

# One that drops a column
$ reylo migrate new drop_bio --drop users.bio

# One that renames a column and changes its type
$ reylo migrate new about --rename users.bio=about

# Run your migrations
$ reylo migrate dev

# Try a change with no migration yet, on every save
$ reylo db push --watch

# Start again from your migrations
$ reylo db reset

# Start again with no rows, and your seed
$ reylo db wipe && reylo run --file seed.sql
```

In CI, and when you deploy:

```terminal
# Check the files, with no database, in a pre-commit hook
$ reylo migrate lint

# See what production ran, and what's pending
$ reylo migrate status --url $PROD_URL

# Try the deploy, running nothing
$ reylo migrate deploy --dry-run

# Deploy
$ reylo migrate deploy --dry-run && reylo migrate deploy

# Take back a migration as production ran it
$ reylo migrate history pull --url $PROD_URL

# Write the lock again from production's history
$ reylo migrate lock --url $PROD_URL

# Run a SQL file on a database, recording nothing
$ reylo run --file backfill.sql --url $PROD_URL
```
