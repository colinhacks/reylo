<p className="dk-subheader">Put your schema in a SQL file, and Reylo Migrate writes the migrations</p>

You keep the schema you want in `schema.sql`. Each command moves a change one step: `reylo migrate new` writes it into a migration, and `reylo migrate dev` runs the migrations on your database:

<MigrationsDiagram />

Reylo Migrate is separate from Reylo's `.sql` imports: each works without the other, and your own migration tool works just as well.

<Features>
<Choice icon="file" title="SQL-first data modeling">
<Way title="via `schema.sql`">

Keep the schema you want in one file, as plain SQL, and Reylo Migrate writes each migration from your changes to it.

</Way>
<Way title="schemaless mode" or>

You or your agents write each migration by hand, and Reylo Migrate checks and runs them all the same. There's no `schema.sql` to keep.

</Way>
</Choice>
<Choice icon="branch" title="Linear or loose history">
<Way title="linear, via `reylo.lock`">

A lockfile keeps one order, so two branches that each add a migration conflict in git, before anything deploys.

</Way>
<Way title="loose, in name order" or>

Delete the lockfile, and Reylo Migrate runs migrations in lexicographic order, while refusing any changes that cause path-dependent drift. Nothing writes the lock again until `reylo migrate lock`.

</Way>
</Choice>
<Feature icon="zap" title="Fast iteration">

Try a change before you write its migration: `reylo db push --watch` takes your development database to `schema.sql` on every save.

</Feature>
<Feature icon="split" title="Explicit drops">

Every destructive change needs `--drop`, in a migration and in a push: a dropped table or column, or a type change that loses values, is refused until `--drop` names it. Where Reylo Migrate can't tell a rename from a drop, `--rename` settles it.

</Feature>
<Feature icon="lock" title="No long locks">

On Postgres, a new constraint or index never blocks writes: it's added without reading the rows, then checked in a migration of its own. A table rewrite waits for `--blocking`, and a statement gives up a busy lock after half a second, then tries again.

</Feature>
<Feature icon="layers" title="Dry runs in shadow databases">

Reylo Migrate replays your migrations on a throwaway database, so `--dry-run` shows what a deploy would do, running nothing on yours.

</Feature>
<Feature icon="hash" title="Integrity checks">

Chained hashes in the lock catch a migration edited, deleted or reordered, before anything runs. A fingerprint on each database catches a change made by hand, and shows it.

</Feature>
<Feature icon="database" title="Dialect-agnostic">

Supports Postgres, MySQL, SQLite (Turso Cloud included) and SQL Server, with one set of commands.

</Feature>
</Features>

## Basic usage

Install Reylo, and start your migrations from your database:

```terminal
$ npm install reylo
$ npx reylo migrate init
✓ Started reylo/ from postgres://localhost:5432/app
  reylo/
  ├── schema.sql          this database's schema
  ├── migrations/
  │   └── init.sql        the same, recorded as run here
  └── reylo.lock          the order the migrations run in
```

Commit what it wrote. Its cache, `reylo/.cache/`, keeps itself out of git.

To change your schema, edit `schema.sql`, which holds all of it:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null -- [!code --]
  email text not null, -- [!code ++]
  bio text -- [!code ++]
);
```

Write the migration:

```terminal
$ npx reylo migrate new add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql
```

Read what it wrote. It's plain SQL, the change and nothing else, and yours to edit:

```sql title="20261104140347_add_bio.sql"
alter table users add column bio text;
```

Run it on your development database:

```terminal
$ npx reylo migrate dev
Applying to postgres://localhost:5432/app
  ✓ 20261104140347_add_bio.sql  applied · 4 ms
✓ Wrote reylo/reylo.lock
```

Commit the migration and the lock. When you deploy, run it on production:

```terminal
$ npx reylo migrate deploy
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
✓ Applied 1 migration
```

## Schema modeling

Your schema lives in `schema.sql`, or in your migrations alone.

### Schema file

By default it's `schema.sql`: the whole schema you want, as plain SQL, from which `reylo migrate new` writes each change as a migration, as in [Basic usage](#basic-usage).

### Schemaless mode

Delete `schema.sql`, and your migrations are your schema.

<MigrationsDiagram without="schema" />

Write each migration by hand, or change your development database and let `reylo migrate new` write what it has that your migrations don't make:

```terminal
$ reylo run 'alter table users add column bio text'
✓ alter table users add column bio text

$ reylo migrate new add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql

$ reylo migrate dev
Applying to postgres://localhost:5432/app
  + 20261104140347_add_bio.sql  recorded: already in place
✓ Wrote reylo/reylo.lock
```

What changes:

- The checks against `schema.sql` are skipped, and each command that would run one says so.
- Your development database stands in for `schema.sql`, so `reylo migrate new` refuses until it has run every migration. One it hasn't would read as a drop.
- With no `schema.sql` to push, `reylo db push` refuses: try a change on your database directly.

You give up the one file that shows your whole schema, and the check that your migrations make the schema you meant.

## Ordering

Your migrations run in one order: the lockfile's, or their names'.

### Lockfile

The lockfile, `reylo.lock`, keeps your migrations in one order.

Each of its lines has a checksum chained to the one before. A migration it doesn't list is a draft, free to edit, which only `reylo migrate dev` runs:

```yaml title="reylo.lock"
schema: c7bf681b
migrations:
  - 20261104120000_users.sql c86e9de4
  - 20261104140347_add_bio.sql 78ad08c0
```

When two branches each add a migration, git conflicts on the lock, before anything is deployed. Keep main's lines, then run `reylo migrate dev`, which runs your branch's migrations after main's and adds them back.

### Lock-free mode

Delete `reylo.lock`, and your migrations run in name order.

<MigrationsDiagram without="lock" />

Status says so:

```terminal
$ reylo migrate status
Migrations on postgres://localhost:5432/app
  ✓ init.sql                 applied 2026-11-04 12:00 UTC
  ✓ 20261105090000_tags.sql  applied 2026-11-05 09:00 UTC
✓ Unchanged since its last migration
· No lock: migrations run in name order (reylo migrate lock writes one)
· With no lock to hold its checksum, reylo/schema.sql is checked against the migrations by reylo migrate deploy --dry-run
```

Two branches that each add a migration then merge with no conflict, and a database may have run a migration that now sorts after the merged one. On a shadow database, `reylo migrate dev` and `reylo migrate deploy` replay such a migration in both orders, and refuse it where the two end differently:

```terminal
$ reylo migrate deploy
✗ 20261105080000_no_nick.sql sorts before 20261105090000_nick.sql, which this database already ran, and the two orders end differently
  + a fresh database: column users.nick text
  Give 20261105080000_no_nick.sql a later name, so that every database runs it after 20261105090000_nick.sql

Nothing was changed.
```

You give up:

- **The same data everywhere.** Columns are compared as a set, as everywhere in Reylo, and no check can show that data written in two orders matches.
- **Checksums.** With none, a migration edited before any database ran it goes unseen, and only a dry run holds `schema.sql` against your migrations.

To turn the lock back on, `reylo migrate lock` writes it from a database's history.

## From code

Run your migrations from your app's code, as on a server's start:

```ts title="server.ts"
import { migrate } from "reylo";

// reylo migrate deploy, in this directory, on direct_url's database
const ran = await migrate();
```

It runs `reylo migrate deploy` as the command line does, and resolves to the names of the migrations it ran. It rejects with the deploy's problems, as on a draft or a database changed by hand. Pass `{ url }` to migrate another database.

<Rust>
In Rust, `reylo::migrate!()` compiles your migrations into the crate and runs them on your sqlx pool ([Rust](/rust#migrations)).
</Rust>

A Cloudflare Durable Object runs its migrations on itself, from its constructor ([Durable Objects](/durable-objects#migrations)).

  migrate deploy           Run what the lock lists, with no shadow database
    --dry-run              Try it on a shadow database, running nothing here

## Configuration

Each setting is optional. Here they are with their defaults:

```yaml title=".reylo.yaml"
# the directory of schema.sql, the migrations, the lock and the cache
dir: reylo

# the database to migrate
direct_url: ${DATABASE_URL}

# a server for shadow databases; null uses your database's own
shadow_url: null
```

To migrate another database, pass `--url`. On Turso Cloud, that's its `libsql://` URL with your auth token ([Turso](/turso#migrations)).

### Shadow databases

Many Reylo Migrate operations rely on a shadow database.

It's a throwaway database beside yours: Reylo Migrate runs your migrations on it, reads the schema they make, and drops it. That's why hand-written SQL counts, and why there's no snapshot file to keep in step. You don't set anything up: on a local database you're a superuser on, you'll never notice them. Writing and repairing migrations need one, and a deploy doesn't:

| Needs a shadow database | Needs none |
| --- | --- |
| `reylo migrate init` | `reylo migrate deploy` |
| `reylo migrate new` | `reylo migrate status` |
| `reylo migrate dev` | `reylo db introspect` |
| `reylo migrate deploy --dry-run` | `reylo db wipe` |
| `reylo migrate lock` | |
| `reylo migrate history push` | |
| `reylo migrate history pull` | |
| `reylo db push` | |
| `reylo db reset` | |

Each database makes them its own way:

- **Postgres:** on your database's server, with `create database`, so your role needs `CREATEDB`. A local superuser has it, and so do the roles Neon and Supabase give you. Reylo Migrate keeps up to 32 as a cache, named `reylo_cache_…`, so a run replays only the migrations that are new.
- **MySQL:** on your database's server, with `create database`, so your user needs the `CREATE` privilege on every database.
- **SQLite:** in memory, Turso Cloud's included. There's nothing to grant.
- **SQL Server:** on your database's server, with `create database`, so your login needs the `CREATE ANY DATABASE` permission, which the `dbcreator` role holds.

On Supabase, each shadow also gets what Supabase made in your database: its extensions, and its own schemas such as `auth` and `storage`. A migration that references `auth.users`, or adds a policy on `storage.objects`, replays as it runs.

Where your role can't create a database, point `shadow_url` at a server that can, running the same version:

```yaml title=".reylo.yaml"
# a local Postgres 18, for a hosted Postgres 18
shadow_url: postgres://localhost:5433/postgres
```
