<p className="dk-subheader">How Reylo types queries on DuckDB</p>

[Reylo](/) is an engine that infers the types of SQL queries from your live database. This page covers how it types and runs queries on DuckDB, in TypeScript: column types, null values, row counts, parameters, files and drivers.

<Callout title="Preview">

DuckDB support is a preview: the types Reylo infers on DuckDB, and the values `.run()` returns for them, may still change in a minor release.

</Callout>

| | |
| --- | --- |
| DuckDB versions | 2.0, through `@duckdb/node-api` |
| Connection | A `duckdb:` URL in `DATABASE_URL` or [`direct_url`](/configuration#direct_url), as `duckdb:./app.duckdb`; a relative path starts at your `package.json`, and `duckdb::memory:` is an empty database, for queries that only read files |
| Drivers | `@duckdb/node-api` ([Drivers](#drivers)) |
| Migrations | [Reylo Migrate](/migrations) runs on the same `@duckdb/node-api`, at 2.0, with its shadow databases in memory |
| Type checking | DuckDB runs inside your app, so the type check prepares each query on your project's own `@duckdb/node-api`, which you install. It opens the database file read-only for each query and closes it right after, and while your app has the file open, it reads a copy of it. On Windows no other process can read a file DuckDB has open for writing, so the type check needs your app stopped |

## Where types come from [#sources]

Reylo types each query from DuckDB's own analysis of it.

DuckDB runs inside your app, so the type check [prepares](https://duckdb.org/docs/stable/sql/query_syntax/prepared_statements) the query on your project's own `@duckdb/node-api` and reads back DuckDB's own type information on its parameters and return type. Reylo reads the catalog for the rest.

## Data types

DuckDB's prepared statement reports the exact type of every parameter and column.

<Rules>

**Integers**

A `BIGINT` or wider integer is a `bigint`, so no value is ever rounded. A parameter of one takes a `number`, a `bigint` or a string of digits.

<InferenceCard>

```sql file="duck_types_integers.sql" dialect="duckdb"
select id, github_id, count(*) over () as n
from users
```

</InferenceCard>

- **Decimals.** A `DECIMAL` is its exact text, as DuckDB stores it with its scale, and a parameter of one takes that text.

- **Dates and times.** A `TIMESTAMP` is its wall-clock text with a `T` between the date and the time, and a `TIMESTAMPTZ` its instant in UTC, as `Temporal.Instant.from` reads it. A year past 9999 is written as ISO 8601 extends it, `+010000-01-01`, and an infinite date or timestamp as `"infinity"` or `"-infinity"`. An `INTERVAL` is an ISO 8601 duration, which its parameter takes back.

**Nested types**

A `STRUCT`, a `LIST`, a `MAP` and a `UNION` hold their values as a row does, a `BIGINT` inside one a `bigint` too. DuckDB lets any field and any element be `NULL`, so each is typed `| null`, except in an `array(select c from (…) c)` of a subquery's or a table's whole rows, whose elements are structs and whose fields are as their columns are. A `STRUCT` whose fields have no names, as `(1, 'a')` and `row(…)` build, is a tuple, an array of its values in order (`[number | null, string | null]`), and a parameter of one takes that array.

<InferenceCard>

```sql file="duck_types_nested.sql" dialect="duckdb"
select tags, meta, meta.host as host
from events
```

</InferenceCard>

- **JSON.** A `JSON` column is the parsed value, typed `Json`, the type Reylo exports for any JSON value. A parameter cast to `json`, or to a JSON Schema with [`::json('…')`](/inference#typed-json), takes any value `JSON.stringify` writes, or the values its schema admits; where the query takes no null for it, `null` is JSON's `null`.

</Rules>

### Files

A query can read Parquet, CSV and JSON files with `read_parquet`, `read_csv` and `read_json`. DuckDB reads a file's columns when it prepares the query, so the files, or a sample with the same columns, must exist wherever the type check runs, at the same paths. A relative path starts at your `package.json` in the type check, and at your app's working directory when it runs.

```sql
select level, count(*) as n
from read_parquet('logs/*.parquet')
group by all
```

Reylo keeps each query's analysis in [`reylo/.cache/`](/faq#faq-reylo-directory) until your database's schema changes, and a file's columns aren't part of the schema: after changing them, delete `reylo/.cache/` so that the next type check reads the files again. Every column of a file may be `NULL`, since nothing declares one `NOT NULL`.

### Type descriptors

How the engine writes each type.

The engine gives every column its type in [Reylo Type Defs](/typedefs), as [`reylo analyze`](/cli#reylo-analyze) prints it. A column of each DuckDB type:

```sql schema
create type mood as enum ('sad', 'ok', 'happy')
```

```sql
select
  null::boolean as "BOOLEAN", null::tinyint as "TINYINT", null::integer as "INTEGER", null::bigint as "BIGINT",
  null::hugeint as "HUGEINT", null::ubigint as "UBIGINT", null::float as "FLOAT", null::double as "DOUBLE",
  null::decimal(10, 2) as "DECIMAL(10, 2)", null::varchar as "VARCHAR", null::blob as "BLOB", null::uuid as "UUID",
  null::mood as "ENUM", null::date as "DATE", null::time as "TIME", null::timetz as "TIMETZ",
  null::timestamp as "TIMESTAMP", null::timestamptz as "TIMESTAMPTZ", null::interval as "INTERVAL",
  null::integer[] as "INTEGER[]", null::integer[3] as "INTEGER[3]", null::struct(a integer, b varchar) as "STRUCT(a INTEGER, b VARCHAR)",
  row(1, 'a') as "STRUCT(INTEGER, VARCHAR)", null::map(varchar, integer) as "MAP(VARCHAR, INTEGER)",
  null::union(num integer, str varchar) as "UNION(num INTEGER, str VARCHAR)", null::bit as "BIT", null::json as "JSON"
```

</Analyzed>

A list that `list(distinct …)` or `array_agg(distinct …)` builds is `distinct`, and so is one from `list_distinct`, whose elements are never null either. A list of text, durations, floats or JSON isn't, since DuckDB may keep apart two of them that are one value or that it finds equal (`'a'` and `'A'` under `NOCASE`, `interval 1 day` and `interval 24 hours`), and neither is a list a `union` makes, which casts both sides to one type.

## Nullability

Each column can be null unless Reylo can tell it never is, from `NOT NULL`, joins, `where` tests and expressions ([Inference](/inference#left-joins)). DuckDB's description of a query doesn't say reliably which columns hold `NULL`, so Reylo reads the schema and the query. On DuckDB:

- **Primary key columns** are non-null, as `NOT NULL` ones are.
- **Division** is nullable, since `SET error_on_division_by_zero = false` makes dividing by zero return `NULL`, and so is a part of a date, such as `year(…)`, which is `NULL` for an infinite date, and a cast of a `JSON` value to anything but text or `JSON`, since JSON's `null` casts to `NULL`.
- **`count_if`** is null over no rows, where `count` never is.
- **`rollup`, `cube` and `grouping sets`** make a key null in the rows that total it, whether it is a column or an expression.
- **A table macro's body** is read as the query it is, so it decides which columns are null and how many rows the macro returns.

## Cardinality

Reylo infers how many rows a query returns from its keys, aggregates, `limit 1` and `returning` ([Inference](/inference#unique-keys)). On DuckDB:

- **One row** comes back from a query with no `from`, and from a `group by all` whose columns read the tables only inside aggregates.
- **A key match** counts only in a query of one table, on its primary key or a `unique` constraint.
- **An insert of one row with `returning`** returns that row, or `null` with `on conflict do nothing`, or `do update` with a `where`.
- **A statement that returns no rows**, such as `create table`, is `void`.
- **A key matches exactly or not at all.** It doesn't count when DuckDB compares a text key with a number, as numbers, so `where code = 1` matches both `'1'` and `'01'`, a number key with a float, as floats, or a text key under a collation such as `collate nocase`.
- **An unnamed expression** among several columns is a type error where DuckDB's name for it isn't an identifier, as with `count_star()`. Name it with `as`.

## Parameters

### Placeholders

Write parameters as `:name`, and pass `.run()` an object with those names, without the colon. You can use DuckDB's `$1`, `?` or `?1` instead, but not beside names; then `.run()` takes an object keyed by number, `{ 1: 42 }`. DuckDB's own named form, `$name`, is an error that says to write `:name`.

### What a parameter takes

A parameter accepts the same values `.run()` returns for its type, so you can pass a row straight into the next query. A `BIGINT` or wider integer also takes a `number` or a string of digits, and a `STRUCT` an object of its fields. A list takes no `null` element, so remove one before passing a list back in, and a `UNION` takes a member's value, not `null`.

A fraction for an integer, such as `1.5` for an `INTEGER`, makes `.run()` throw before the query runs, where DuckDB would round it to 2.

### Parameters without a type

DuckDB types a parameter from where it stands: compared with a column, written to one, or cast. Anywhere else, such as a bare `select :x` or `id + :n`, DuckDB can't type the query at all, and Reylo shows an error at the parameter. Cast it:

<InferenceCard>

```sql file="duck_param_cast.sql" dialect="duckdb"
select :limit::integer + 1 as next
```

</InferenceCard>

### Parameters that may be null

A parameter accepts `null` where the query lets it be `NULL`. Such a parameter is optional in `.run()`, and leaving it out passes `null`.

<Rules>

**Cast to `nullable(…)`**

A cast to `nullable(type)` makes the parameter that type or `null`.

<InferenceCard>

```sql file="duck_param_nullable.sql" dialect="duckdb"
select id, name
from users
where name = coalesce(:name::nullable(varchar), name)
```

</InferenceCard>

**Tested for `NULL`, or written to a nullable column**

A parameter that the query tests for `NULL` or passes to `coalesce`, or writes directly into a column that accepts `NULL`, takes `null`.

<InferenceCard>

```sql file="duck_param_insert.sql" dialect="duckdb"
insert into users (id, name, email)
values (:id, :name, :email)
```

</InferenceCard>

</Rules>

## Drivers

Reylo decodes its query results itself, so settings on your connection don't affect Reylo's queries.

### `@duckdb/node-api`

Pass a connection. A transaction is the connection's own, around the queries you run on it:

```ts
import { DuckDBInstance } from "@duckdb/node-api";
import getUser from "./get_user.sql";

const instance = await DuckDBInstance.create("app.duckdb");
const db = await instance.connect();

const user = await getUser.run(db, { id: 1 });
```

## Migrations

[Reylo Migrate](/migrations) runs on DuckDB with the same commands.

- It runs on your project's own `@duckdb/node-api`, which it needs at 2.0, and refuses an older one.
- DuckDB lets one process at a time open a file to write, so stop your app, its dev server included, before you run a command that writes: each refuses while another process holds the database, and changes nothing. The commands that only read (`status`, `deploy --dry-run` and `db introspect`) open the file read-only, so they run beside other processes that only read it.

DuckDB's `alter table` adds no check or foreign key, changes no column an index covers, and changes little of a table another table's key references. So `reylo migrate new` writes such a change as a rebuild: the table's rows go to a temporary table, the table is made again, and the rows come back, with those of every table whose keys reference it. A check added to `authors`:

```sql title="20261114120000_check_author_names.sql"
create temporary table reylo_copy_authors as select * from authors;
create temporary table reylo_copy_books as select * from books;
drop table books;
drop table authors;
create table authors (id bigint, name varchar, primary key (id), check (("name" != '')));
create table books (id bigint, author_id bigint, pages integer, primary key (id), foreign key (author_id) references authors (id));
insert into authors (id, name) select id, name from temp.main.reylo_copy_authors;
insert into books (id, author_id, pages) select id, author_id, pages from temp.main.reylo_copy_books;
drop table temp.main.reylo_copy_authors;
drop table temp.main.reylo_copy_books;
```

A table whose check or generated column calls a macro, or casts to an enum, is rebuilt the same way when that macro or enum changes.

DuckDB refuses a few things a migration may need, on your rows rather than in the check:

- A table whose key references the table itself can't take its rows back in a rebuild where a row references another, so that migration fails and changes nothing. The migration says so above the rebuild.
- DuckDB has no `alter sequence`, so a changed sequence is made again, and in a migration it starts again where `schema.sql` starts it. Start it past the values your rows hold.
- An `update` of a table, then `set not null` or a new index on it, is refused in one migration. Put the backfill in a migration of its own.

Also on DuckDB:

- DuckDB's catalog holds no macro parameter's default (the `5` of `b := 5`), so Reylo Migrate takes those from `schema.sql`, the migrations and DuckDB's export of the database, and never compares them: write a change to a default alone by hand, as `create or replace macro`. DuckDB can't export a database where a column's default calls a macro of a schema other than `main`. There, `reylo migrate init` and `reylo db introspect` start their SQL with a comment for each macro that has parameters, saying to add its defaults by hand.
- DuckDB 2.0 writes a comment on a column so that the file no longer opens, where the column's table calls a macro (in a check, a default or a generated column) and another table's key references it. Reylo Migrate follows such a comment with an `alter table` that changes nothing, which writes the table again whole. Do the same in a migration you write by hand.
- An extension is loaded once, in `schema.sql` or the migration that first needs it, as `create extension` is on Postgres: write `install spatial;` and `load spatial;` there. Every database Reylo Migrate opens for the project loads it before anything else, its shadows included, so a migration that uses the extension's types, functions or indexes (spatial's `st_` functions, an R-tree index) needs no `load` of its own.

## Limits

What Reylo can't type on DuckDB, and what to do instead:

| Limit | Instead |
| --- | --- |
| A `PIVOT` without its values, whose columns are the values it reads | Name the values: `pivot logs on level in ('info', 'warn') using count(*)` |
| A table function with side effects: `.readOnly` looks only for a `with` query that writes, sequences and `query()` | Don't retry a query that calls one |
| A query in syntax Reylo's parser doesn't read, such as `PIVOT` or `SUMMARIZE`: its columns are typed, but each may be `NULL` and the query returns `Row[]` | None needed: the types hold, if loosely |
| An app that opens the database file for writing at the moment the type check reads it, which DuckDB refuses | Start the app again |
| A session that sets `default_collation`, which the type check doesn't see: `where code = 'a'` can match more than the one row it's typed as | Declare the collation on the column |
| `.runSync()`, since `@duckdb/node-api` answers through a promise | Use `.run()` |
| DuckDB in the browser, through `@duckdb/duckdb-wasm`, which `.run()` doesn't take yet | Run queries through `@duckdb/node-api` |
| `rows(…)` and `row(…)` parameters | Pass each value as a parameter of its own |
| A file of several statements, such as a migration | Put each statement in a file of its own |
| What your app's connection sets for itself, which the type check's connection doesn't share: a temporary table that shadows a table of the same name, and `default_collation`, under which `'a'` can equal `'A'` | Name a temporary table apart from your tables, and write `collate` on the comparisons it should change |
