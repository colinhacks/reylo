<p className="dk-subheader">How Reylo types queries on Postgres</p>

[Reylo](/) lets you import `.sql` files into TypeScript, with every query typed from your live database. This page covers how it types and runs queries on Postgres: column types, null values, row counts, parameters and drivers.

| | |
| --- | --- |
| Postgres versions | 14 to 18 |
| Connection | A `postgres://` URL in `DATABASE_URL` or [`direct_url`](/#direct_url). Connect directly, not through a pooler such as PgBouncer. |
| Drivers | postgres.js, `pg`, `pg-promise`, `Bun.sql`, PGlite, Neon and `@vercel/postgres`, and Drizzle over `pg`, postgres.js, Neon, PGlite or `Bun.sql` ([Drivers](#drivers)) |
| Type checking | Reads the schema through the postgres.js inside `@reylosql/postgres`, so your project needs no driver for it |

<Details summary="View the schema behind the examples" id="schema">

```sql file="schema.sql"
create extension if not exists pg_jsonschema;

create type user_role as enum ('admin', 'member');
create domain amount as numeric(12, 2) check (value >= 0);

create table users (
  id serial primary key,
  name text not null,
  email text unique,
  role user_role not null default 'member',
  tags text[] not null default '{}',
  created_at timestamptz not null default now()
);
create unique index users_email_lower on users (lower(email));
```

```sql file="schema.sql"
create table orders (
  id bigserial primary key,
  user_id integer not null references users (id),
  total amount not null,
  paid boolean not null default false,
  placed_at timestamptz not null default now(),
  ships_on date,
  receipt bytea
);
```

```sql file="schema.sql"
create table events (
  id bigserial primary key,
  kind text not null check (kind in ('click', 'key')),
  payload jsonb not null check (jsonb_matches_schema('{
    "type": "object",
    "properties": {
      "x": { "type": "integer" },
      "y": { "type": "integer" },
      "code": { "type": "string" }
    }
  }', payload)),
  at timestamp not null default localtimestamp
);
```

</Details>

## Data types

Each Postgres type maps to one TypeScript type, and `.run()` returns the same value for it on every driver:

| SQL type | TypeScript | The value `.run()` returns |
| --- | --- | --- |
| `smallint`, `integer`, `oid` | `number` | `42` |
| `bigint`, `bigserial`, `count(*)` | `bigint` | `9007199254740993n` |
| `real`, `double precision` | `number` | `1.1` |
| `numeric`, `money` | `string` | `"12.50"`, `"$1.50"` |
| `text`, `varchar`, `char`, `uuid` | `string` | `"Ada"` |
| `boolean` | `boolean` | `true` |
| `date` | `string` | `"2026-10-20"` |
| `timestamp` | `string` | `"2026-10-20T10:00:00.123456"` |
| `timestamptz` | `string` | `"2026-10-20T08:00:00.123456Z"` |
| `time`, `timetz` | `string` | `"10:00:00"` |
| `interval` | `string` | `"P1DT2H3M4S"` |
| `json`, `jsonb` | `unknown` | `{ a: 1 }` |
| `json`, `jsonb` a JSON Schema `CHECK` holds | what the schema admits | `{ x: 10, y: 20 }` |
| JSON the statement builds (`jsonb_build_object`, `jsonb_agg`) | the object or array it builds | `{ total: 12.5 }` |
| `bytea` | `Uint8Array` | `Uint8Array.of(1, 2, 255)` |
| An array | an array of its element type | `["math", "poetry"]` |
| An enum | the union of its labels | `"admin"` |
| A domain | its base type | its base type's |
| A row value | `string` | `"(1,Ada)"` |
| pgvector's `vector`, `halfvec` | `number[]` | `[1, 2.5, -3]` |
| Every other type (`inet`, ranges, `point`, `tsvector`, `xml`, …) | `string` | `"[1,5)"` |

Each example below pairs a SQL value with the value `.run()` returns for it: `select <SQL> as v` returns the row `{ v: <JavaScript> }`.

### Integers

A `bigint` comes back as a JavaScript `bigint`. So does `count(*)`, since Postgres types it `bigint`. To get a `number`, cast to `int` in the query:

```ts twoslash tab="main.ts"
import countOrders from "./pg_count_orders.sql";

const counts = await countOrders.run(db);
//    ^?
```

```sql tab="pg_count_orders.sql"
select count(*) as total, count(*)::int as total_number
from orders
```

Postgres types a `sum()` by what it adds up: an `integer` column sums to a `bigint`, and a `bigint` or `numeric` column to a `numeric`, which comes back as a `string`:

<Pairs>

- `sum(2::integer)` → `2n`
- `sum(2::bigint)` → `"2"`
- `sum(2.5::numeric)` → `"2.5"`

</Pairs>

### Decimals

A `numeric` comes back as its exact text, keeping the column's scale, and so does an `avg()`. A `money` comes back as text in the server's currency format:

<Pairs>

- `12.50::numeric` → `"12.50"`
- `avg(2::integer)` → `"2.0000000000000000"`
- `1.50::money` → `"$1.50"`

</Pairs>

### Dates and times

No value comes back as a `Date`. A `timestamptz` is the instant in UTC, in ISO 8601 with a `Z`, and an `interval` is an ISO 8601 duration. The other types are the text Postgres writes, with a `T` between the date and the time of a `timestamp`:

```ts twoslash tab="main.ts"
import orderDates from "./pg_order_dates.sql";

const order = await orderDates.run(db, { id: 1 });
//    ^?
```

```sql tab="pg_order_dates.sql"
select placed_at, ships_on from orders where id = :id
```

If your runtime has `Temporal`, read the instant with `Temporal.Instant.from()`, the date with `Temporal.PlainDate.from()` and an interval with `Temporal.Duration.from()`. You can pass each value back in as a parameter unchanged ([What a parameter takes](#what-a-parameter-takes)).

<Rules>

**Fractions of a second**

Fractions keep the server's precision, up to microseconds, without trailing zeros.

<Pairs>

- `'2026-10-20 10:00:00.123456+00'::timestamptz` → `"2026-10-20T10:00:00.123456Z"`
- `'2026-10-20 10:00:00.5+00'::timestamptz` → `"2026-10-20T10:00:00.5Z"`
- `'2026-10-20 10:00:00+00'::timestamptz` → `"2026-10-20T10:00:00Z"`

</Pairs>

**Infinity**

Postgres's `infinity` and `-infinity` come back as those words, in every date and time type, so `Temporal` can't parse them.

<Pairs>

- `'infinity'::timestamptz` → `"infinity"`
- `'-infinity'::date` → `"-infinity"`

</Pairs>

**Years past 9999 or before 1 AD**

A `timestamptz` uses ISO 8601's extended year, as `Temporal.Instant` does. A `date` or `timestamp` keeps Postgres's own text.

<Pairs>

- `'12344-12-31 18:30:00+00'::timestamptz` → `"+012344-12-31T18:30:00Z"`
- `'0002-06-01 12:00:00+00 BC'::timestamptz` → `"-000001-06-01T12:00:00Z"`
- `'0002-06-01 BC'::date` → `"0002-06-01 BC"`

</Pairs>

**Times**

A `time` or `timetz` is the text Postgres writes in its default `DateStyle`. If your session changes it, the text changes too.

<Pairs>

- `'10:00:00+02'::timetz` → `"10:00:00+02"`

</Pairs>

**Intervals**

An interval is an ISO 8601 duration with its sign in front, which `Temporal.Duration.from()` reads. Postgres signs an interval's months, days and time separately, so when those differ in sign, each part keeps its own sign: Postgres reads that form back, and `Temporal` doesn't. This holds in Postgres's default `IntervalStyle`; if your session changes it, the text is Postgres's own.

<Pairs>

- `'1 day 02:03:04'::interval` → `"P1DT2H3M4S"`
- `'1 year 2 mons'::interval` → `"P1Y2M"`
- `'-1 day'::interval` → `"-P1D"`
- `'1 mon -1 day'::interval` → `"P1M-1D"`

</Pairs>

</Rules>

### JSON

A `json` or `jsonb` column is typed `unknown`, unless a JSON Schema `CHECK` constrains it or your query builds the JSON. Here `payload` is typed by its schema, and `kind` by its `CHECK`:

```ts twoslash tab="main.ts"
import events from "./pg_events.sql";

const rows = await events.run(db);
//    ^?
```

```sql tab="pg_events.sql"
select kind, payload from events
```

JSON your query builds with `jsonb_build_object`, `json_build_object`, `jsonb_agg`, `json_agg`, or `to_jsonb` of a whole row, is typed from what you put in it:

```ts twoslash tab="main.ts"
import orderSummaries from "./pg_order_summaries.sql";

const rows = await orderSummaries.run(db);
//    ^?
```

```sql tab="pg_order_summaries.sql"
select u.name,
  jsonb_build_object(
    'total', o.total,
    'placed_at', o.placed_at,
    'paid', o.paid
  ) as summary
from orders o
join users u on u.id = o.user_id
```

A schema's type carries through an aggregate, and `to_jsonb` of a row is typed column by column, enums included:

```ts twoslash tab="main.ts"
import eventsByKind from "./pg_events_by_kind.sql";

const groups = await eventsByKind.run(db);
//    ^?
```

```sql tab="pg_events_by_kind.sql"
select kind, jsonb_agg(payload order by id) as payloads
from events
group by kind
```

```ts twoslash tab="main.ts"
import userRow from "./pg_user_row.sql";

const row = await userRow.run(db, { id: 1 });
//    ^?
```

```sql tab="pg_user_row.sql"
select to_jsonb(u) as "user" from users u where u.id = :id::int
```

<Rules>

**Values inside a document**

Inside JSON, a value can differ from the same value in a column. Numbers past 2^53 lose precision in `JSON.parse`, a float or `numeric` that is not finite is text (JSON has no number for it), a `timestamptz` is written in the session's time zone (here `America/Los_Angeles`), a `bytea` is hex text, an `oid` is text, an `interval` is Postgres's own text rather than an ISO 8601 duration, an `hstore` is an object of its keys, each value text or null, and a PostGIS `geometry` is GeoJSON. An extension's type with no cast to JSON, such as pgvector's `vector`, is its text.

<Pairs>

- `jsonb_build_object('n', 9007199254740993::bigint)` → `{ n: 9007199254740992 }`
- `jsonb_build_object('n', 12.50::numeric)` → `{ n: 12.5 }`
- `jsonb_build_object('n', 'NaN'::numeric)` → `{ n: "NaN" }`
- `jsonb_build_object('at', '2026-10-20 08:00:00+00'::timestamptz)` → `{ at: "2026-10-20T01:00:00-07:00" }`
- `jsonb_build_object('b', '\x0102ff'::bytea)` → `{ b: "\\x0102ff" }`
- `jsonb_build_object('d', '1 day 02:03:04'::interval)` → `{ d: "1 day 02:03:04" }`
- `json_build_object('u', row(1, 'Ada'))` → `{ u: { f1: 1, f2: "Ada" } }`
- `json_build_object('o', 7::oid)` → `{ o: "7" }`
- `json_build_object('h', 'a=>1, b=>NULL'::hstore)` → `{ h: { a: "1", b: null } }`
- `json_build_object('g', 'POINT(1 2)'::geometry)` → `{ g: { type: "Point", coordinates: [1, 2] } }`
- `json_build_object('v', '[1,2.5]'::vector)` → `{ v: "[1,2.5]" }`

</Pairs>

**Aggregates beside columns**

Inside JSON a statement builds, an aggregate can sit beside the statement's columns wherever its `GROUP BY` allows. With `group by 1`, or a `GROUP BY` by a name from the select list, an object that mixes the two has `unknown` values.

<Inferred>

```sql file="pg_json_grouped.sql"
select jsonb_build_object('name', u.name, 'orders', count(o.id)) as summary
from users u
left join orders o on o.user_id = u.id
group by u.id
```

</Inferred>

**Aggregates over no rows**

Over no rows, `jsonb_agg` returns `null`, and its type includes `null`. Write `coalesce(jsonb_agg(…), '[]')` to always get an array. With any other default, the column is `unknown`.

<Pairs>

- `jsonb_agg(1) filter (where false)` → `null`
- `coalesce(jsonb_agg(1) filter (where false), '[]')` → `[]`

</Pairs>

**Where a schema's type applies**

A JSON Schema `CHECK`'s type reaches the column wherever you use it as it is: selected directly or through a view or subquery, inside JSON you build, in a whole row, and as a parameter written to the column.

<Inferred>

```sql file="pg_json_schema_param.sql"
insert into events (kind, payload)
values (:kind, :payload)
returning id
```

</Inferred>

**Keys read from the column**

A key read with `->`, `->>`, `#>` or `#>>` and a literal key is typed by the schema, and is non-null where the schema requires the key:

<Inferred>

```sql schema
create extension if not exists pg_jsonschema;

create table events (
  id bigserial primary key,
  payload jsonb not null check (jsonb_matches_schema('{
    "type": "object",
    "properties": {
      "kind": { "enum": ["click", "key"] },
      "x": { "type": "integer" }
    },
    "required": ["kind"]
  }', payload))
);
```

```sql file="pg_json_keys.sql"
select payload ->> 'kind' as kind, payload -> 'x' as x
from events
```

</Inferred>

**Where it doesn't**

Any other expression on the column, a key read from a JSON parameter, a column under a `union`, a `CHECK` added `NOT VALID`, and `to_jsonb` of a single value are typed `unknown`.

<Inferred>

```sql file="pg_json_unknown.sql"
select payload || '{"seen": true}' as merged, to_jsonb(kind) as k
from events
```

</Inferred>

**Through a `with` query or a subquery**

JSON built in a `with` query or a subquery in `from`, a `lateral` one included, keeps its type when you select its column as it is, put it inside JSON you build, or default it with `coalesce(…, '[]')`. Through a `union` or a `*`, it's `unknown`.

<Inferred>

```sql file="pg_json_with.sql"
with totals as (
  select user_id, jsonb_agg(total) as totals
  from orders
  group by user_id
)
select u.name, t.totals
from users u
join totals t on t.user_id = u.id
```

</Inferred>

**Through a `case`**

A `case` whose one branch builds JSON and whose other branches are `null` keeps that branch's type, and is nullable.

<Inferred>

```sql file="pg_json_case.sql"
select case when total > 100
  then jsonb_build_object('id', id)
end as big_order
from orders
```

</Inferred>

</Rules>

The JSON Schema validators Reylo reads are pg_jsonschema's `jsonb_matches_schema` and `json_matches_schema`, and those of `jsonschema`, `postgres-json-schema`, `is_jsonb_valid` and `json_schema_validate`, each by the keywords and draft it enforces.

### Arrays

An array comes back as a JavaScript array of its element type, including arrays of enums and domains:

```ts twoslash tab="main.ts"
import orderIds from "./pg_order_ids.sql";

const rows = await orderIds.run(db);
//    ^?
```

```sql tab="pg_order_ids.sql"
select u.name, u.tags, array_agg(o.id) as order_ids
from users u
left join orders o on o.user_id = u.id
group by u.id
```

<Rules>

**`NULL` elements**

Postgres lets any array contain `NULL`, even in a `NOT NULL` column, so a `text[]` column is typed `(string | null)[]`. An array your query builds from non-null values, like `array[id]`, is typed `number[]`.

<Pairs>

- `'{a,NULL}'::text[]` → `[ "a", null ]`

</Pairs>

**Several dimensions**

Postgres doesn't track an array's dimensions, so a two-dimensional `int[]` is still typed `(number | null)[]`, though it comes back as nested arrays.

<Pairs>

- `'{{1,2},{3,4}}'::int[]` → `[ [ 1, 2 ], [ 3, 4 ] ]`

</Pairs>

**pgvector's vectors**

A `vector` or `halfvec` comes back as a `number[]`, and a parameter of either takes one; `NaN`, infinities and an empty array are rejected before the query runs. A `halfvec` keeps half-precision floats, so a value comes back as the float it stored, and a `sparsevec` comes back as its text.

<Pairs>

- `'[1,2.5,-3]'::vector` → `[ 1, 2.5, -3 ]`
- `'[0.1,2]'::halfvec` → `[ 0.099975586, 2 ]`
- `'{1:1.5,3:2}/4'::sparsevec` → `"{1:1.5,3:2}/4"`

</Pairs>

</Rules>

### Enums and domains

An enum is typed as the union of its labels. So is a `text` column whose `CHECK` limits it to a list (`kind in ('click', 'key')`). A domain is typed as its base type: `orders.total` is an `amount`, a `numeric`, so a `string`.

<Pairs>

- `'{admin,member}'::user_role[]` → `[ "admin", "member" ]`

</Pairs>

A domain over `jsonb` with a JSON Schema `CHECK` is typed by its schema. A `CHECK` added `NOT VALID` is ignored, since older rows may break it.

## Nullability

Every column is typed `| null` unless Reylo can tell it never is null. On Postgres, it reads your schema and the query:

<Rules>

**`NOT NULL` columns**

A table's column is non-null if it has a valid `NOT NULL` constraint, including in every table that inherits from it.

<Inferred>

```sql file="pg_null_columns.sql"
select name, email
from users
```

</Inferred>

**Outer joins**

An outer join makes the joined table's columns nullable: the right side of a `left join`, the left side of a `right join`, and both sides of a `full join`. A table joined to itself is told apart by its alias.

<Inferred>

```sql file="pg_null_left_join.sql"
select u.name, o.total
from users u
left join orders o on o.user_id = u.id
```

</Inferred>

**Tests that rule out `NULL`**

A test that fails on `NULL`, in the `where` or a later inner join's `on`, makes its column non-null. On a joined table, it also shows the row exists, so the table's `NOT NULL` columns are non-null again.

<Inferred>

```sql file="pg_null_where.sql"
select u.name, o.total, o.ships_on
from users u
left join orders o on o.user_id = u.id
where o.paid
```

</Inferred>

**Expressions**

Literals, `count`, `exists` and `is null` are never null. Operators, casts, built-in functions and `case` are non-null when their inputs are, and `coalesce`, `greatest` and `least` are non-null when one of their arguments is.

<Inferred>

```sql file="pg_null_expressions.sql"
select name || '!' as shout,
  upper(email) as upper_email,
  coalesce(email, '') as email_or_empty,
  email is null as no_email
from users
```

</Inferred>

**Aggregates**

Without a `group by`, an aggregate other than `count` returns `NULL` over no rows. With one, every group has rows: `array_agg` and `jsonb_agg` are non-null, `max` and `sum` are non-null when their argument is, and a `filter` keeps an aggregate nullable.

<Inferred>

```sql file="pg_null_aggregates.sql"
select user_id,
  array_agg(id) as order_ids,
  max(ships_on) as last_ships_on,
  sum(total) filter (where paid) as paid_total
from orders
group by user_id
```

</Inferred>

**Scalar subqueries**

A scalar subquery is non-null only when it always returns one non-null value: an aggregate without a `group by`, or a `select` without a `from`.

<Inferred>

```sql file="pg_null_subqueries.sql"
select (select count(*) from orders) as orders,
  (select name from users order by id limit 1) as first_name
```

</Inferred>

**Window functions**

A window function is typed like any other function: `lag` is nullable, since the first row has no previous row.

<Inferred>

```sql file="pg_null_window.sql"
select id,
  lag(placed_at) over (order by placed_at) as previous,
  row_number() over (order by placed_at) as n
from orders
```

</Inferred>

**`union`**

A `union` column is non-null when it's non-null in every branch. A column of a `with` query or a subquery in `from` is as nullable as it is in that query.

<Inferred>

```sql file="pg_null_union.sql"
select name as label, email as contact from users
union all
select 'guest', null
```

</Inferred>

**Whole rows**

A whole row is non-null unless an outer join can null it, and keeps each column's type. Turned into JSON, an outer-joined row's fields keep their own nullability.

<Inferred>

```sql file="pg_null_rows.sql"
select to_jsonb(o) as "order"
from orders o
```

</Inferred>

</Rules>

Your own operators, functions and casts, or an extension's, tell Reylo nothing: it assumes nothing wherever Postgres could pick one of them over a built-in. To tell Reylo a value is never null, say so in the query: `coalesce(x, …)` gives a default, and `where x is not null` filters out the nulls.

## Cardinality

Reylo infers how many rows a query returns, and types `.run()`'s result to match:

| `.run()` returns | `cardinality` | When the query |
| --- | --- | --- |
| `Row` | `one` | is an aggregate without a `group by`, or inserts one row with `values (…)` and has `returning`, an `on conflict do update` included |
| `Row \| null` | `maybeOne` | matches every column of a primary key or unique index with `=`, through joins on the joined table's key; has `limit 1` or `fetch first 1 row only`; is a `distinct` or `group by` over values the `where` pins; is an `update` or `delete` by key with `returning`; or inserts one row with `on conflict do nothing` and `returning` |
| `void` | `none` | is an `insert`, `update`, `delete` or `merge` without `returning` |
| `Row[]` | `many` | is anything else |

<Rules>

**Unique keys**

A query that compares every column of a primary key or unique index with `=` returns one row or `null`. A unique index on an expression counts when the query compares the same expression, written as Postgres stores it in the index, cast included.

<Inferred>

```sql file="pg_card_unique.sql"
select id, name
from users
where lower(email) = lower(:email)
```

</Inferred>

**Partial unique indexes**

A partial unique index counts only when the `where` includes its condition.

<Inferred>

```sql schema
create table slugs (
  id serial primary key,
  slug text not null,
  deleted boolean not null default false
);
create unique index on slugs (slug) where not deleted;
```

```sql file="pg_card_partial.sql"
select id
from slugs
where slug = :slug and not deleted
```

</Inferred>

**What doesn't count**

Part of a composite key doesn't count, and neither does a `having` or an `insert … select … returning`.

<Inferred>

```sql file="pg_card_insert_select.sql"
insert into orders (user_id, total)
select id, 0 from users
returning id
```

</Inferred>

</Rules>

## Parameters

### Placeholders

Write parameters as `:name`, and pass `.run()` an object with those names. You can use Postgres's `$1` instead, but not both in one query; then `.run()` takes an object keyed by number, `{ 1: 42 }`.

### What a parameter takes

A parameter accepts the same values `.run()` returns for its type, so you can pass a row straight into the next query:

| SQL type | A parameter takes |
| --- | --- |
| `smallint`, `integer` | `number` |
| `bigint`, `limit`, `offset` | `number`, `bigint` or a string of digits |
| `numeric` | `string` |
| `boolean` | `boolean` |
| `date`, `timestamp`, `time` | `string` |
| `timestamptz` | a `string` that names its zone |
| `interval` | a `string`: an ISO 8601 duration (`-P1D` too) or Postgres's own text |
| `json`, `jsonb` | any JSON value, or what the column's JSON Schema admits |
| `bytea` | `Uint8Array` |
| An array | an array of its element's parameter type, without `null` |
| An enum | the union of its labels |
| pgvector's `vector`, `halfvec` | `number[]` |

<Rules>

**Dates and times**

A date or time parameter takes text, never a `Date`, since drivers convert a `Date` in different time zones. A `timestamptz` needs a zone in its text, as `.run()` returns it, so pass a `Date` as `date.toISOString()`:

```ts twoslash tab="main.ts"
import ordersSince from "./pg_orders_since.sql";

await ordersSince.run(db, { since: "2026-10-12T19:06:48Z" });
await ordersSince.run(db, { since: new Date().toISOString() });
// rejected before the query runs: the text names no zone
await ordersSince.run(db, { since: "2026-10-12 19:06:48" });
```

```sql tab="pg_orders_since.sql"
select id from orders where placed_at > :since
```

**JSON text**

A JSON parameter is sent as JSON, so a string is stored as a JSON string. To pass JSON text you already have, cast it from text:

```ts twoslash tab="main.ts"
import addEvent from "./pg_add_event_text.sql";

// stored as the object {"x": 1}
await addEvent.run(db, { payload: '{"x": 1}' });
```

```sql tab="pg_add_event_text.sql"
insert into events (kind, payload)
values ('click', :payload::text::jsonb)
```

</Rules>

A `bytea` parameter takes only a `Uint8Array`, and rejects base64 or hex text before the query runs, since each driver would store a string differently. Decode the text into a `Uint8Array` first.

### Parameters that may be null

A parameter accepts `null` in two places. Such a parameter is optional in `.run()`, and leaving it out passes `null`.

<Rules>

**Cast to `nullable(…)`**

A cast to `nullable(type)` makes the parameter that type or `null`.

<Inferred>

```sql file="pg_param_nullable.sql"
select id, name
from users
where role = coalesce(:role::nullable(user_role), role)
```

</Inferred>

**Written to a nullable column**

Written directly into a column that accepts `NULL`, with no cast. A column accepts it unless it's `NOT NULL`, its domain is `not null`, or a `check (… is not null)` covers it.

<Inferred>

```sql file="pg_param_insert.sql"
insert into orders (user_id, total, ships_on)
values (:user_id, :total, :ships_on)
```

</Inferred>

</Rules>

Any other cast sets the parameter's whole type, so `:email::text` never accepts `null`. Neither `coalesce` nor a test for null (`:role is null`) makes a parameter nullable, and one cast to `nullable(…)` but written to a column that refuses `null` is an error.

## Database errors

With [`.try()`](/#try), an error Postgres raised comes back as `{ error }`, with the fields the server sent under the same names on every driver:

| Field | What it holds |
| --- | --- |
| `code` | The SQLSTATE, as `"23505"`: one of the 251 that Postgres defines, or one a function raises itself (`raise ... using errcode = 'U0001'`) |
| `condition` | The code's name, as `"unique_violation"`, or `undefined` for a code Postgres doesn't define |
| `severity` | `ERROR`, or `FATAL` when the session ended |
| `message`, `detail`, `hint` | The server's texts |
| `position` | Where in the statement the error is, as a character's place from 1 |
| `where` | The functions the error was raised in |
| `schema`, `table`, `column`, `dataType`, `constraint` | What the error is about: a unique violation's constraint and table, a not-null violation's column, a domain's type |

Since a function may raise any code, TypeScript takes any string for `code`. Compare `condition` to have it catch a misspelled name.

An error inside a transaction aborts it, even when `.try()` returns the error: every later statement fails with `in_failed_sql_transaction`, and a commit rolls back without an error. With postgres.js, `sql.begin()` and `tx.savepoint()` reject with any error a statement in them raised, including one `.try()` returned. To carry on after an error, run the statement in a savepoint and roll back to it: with pg, `savepoint s` before it and `rollback to savepoint s` when it fails; with postgres.js, `.run()` inside `tx.savepoint()`, catching the error it rejects with.

## Drivers

Reylo decodes its query results itself, so type parsers and options you set on your client don't affect Reylo's queries, and Reylo's don't affect yours. Type checking reads your schema through the postgres.js that `@reylosql/postgres` carries, whatever driver your app uses.

Each example below runs this query:

```sql file="pg_get_user.sql"
select id, name, email from users where id = :id
```

### `pg`

Pass a `Pool`, a connected `Client`, or a client taken from the pool, which can run a transaction:

```ts twoslash tab="main.ts"
import pg from "pg";
import getUser from "./pg_get_user.sql";

const db = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const user = await getUser.run(db, { id: 1 });

const client = await db.connect();
await client.query("begin");
await getUser.run(client, { id: 1 });
await client.query("commit");
client.release();
```

A client created with `binary: true` isn't supported.

### postgres.js

Pass the `sql` function, or a transaction, savepoint or reserved connection taken from it:

```ts twoslash tab="main.ts"
import postgres from "postgres";
import getUser from "./pg_get_user.sql";

const db = postgres(process.env.DATABASE_URL);
const user = await getUser.run(db, { id: 1 });

await db.begin(async (tx) => {
  await getUser.run(tx, { id: 1 });
  await tx.savepoint((sp) => getUser.run(sp, { id: 1 }));
});

const reserved = await db.reserve();
await getUser.run(reserved, { id: 1 });
reserved.release();
```

A client created with `transform.row` isn't supported.

### `pg-promise`

Pass the database object, or the context a task or transaction hands its callback:

```ts twoslash tab="main.ts"
import pgPromise from "pg-promise";
import getUser from "./pg_get_user.sql";

const pgp = pgPromise();
const db = pgp(process.env.DATABASE_URL);
const user = await getUser.run(db, { id: 1 });

await db.task((t) => getUser.run(t, { id: 1 }));
await db.tx(async (t) => {
  await getUser.run(t, { id: 1 });
  await t.tx((sp) => getUser.run(sp, { id: 1 }));
});
```

A `receive` event that rewrites results isn't supported.

### `Bun.sql`

Pass the client, or a transaction, savepoint or reserved connection taken from it:

```ts twoslash tab="main.ts"
import { SQL } from "bun";
import getUser from "./pg_get_user.sql";

const db = new SQL(process.env.DATABASE_URL);
const user = await getUser.run(db, { id: 1 });

await db.begin(async (tx) => {
  await getUser.run(tx, { id: 1 });
  await tx.savepoint((sp) => getUser.run(sp, { id: 1 }));
});

const reserved = await db.reserve();
await getUser.run(reserved, { id: 1 });
reserved.release();
```

Bun loses the microseconds of a `timestamp` or `timestamptz` before Reylo sees them, and a date before 1 AD, which Reylo rejects. Queries with parameters are read in binary and others as text, so a `real` comes back exact (`1.100000023841858`) only with a parameter. Bun itself fails with "Failed to read data" on a `NULL` in an `int4[]` or `float4[]`, a two-dimensional `int[]` in a query with a parameter, and an array with explicit bounds in one without.

### PGlite

Pass the database, or the transaction it hands its callback:

```ts twoslash tab="main.ts"
import { PGlite } from "@electric-sql/pglite";
import getUser from "./pg_get_user.sql";

const db = new PGlite("./pgdata");
const user = await getUser.run(db, { id: 1 });

await db.transaction((tx) => getUser.run(tx, { id: 1 }));
```

### Neon

Pass the `neon()` function, which sends each query over HTTP, or a `Pool` or `Client`, which hold a WebSocket and run transactions:

```ts twoslash tab="main.ts"
import { neon, Pool } from "@neondatabase/serverless";
import getUser from "./pg_get_user.sql";

const sql = neon(process.env.DATABASE_URL);
const user = await getUser.run(sql, { id: 1 });

const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const client = await pool.connect();
await client.query("begin");
await getUser.run(client, { id: 1 });
await client.query("commit");
client.release();
```

### `@vercel/postgres`

Pass its `sql` client:

```ts twoslash tab="main.ts"
import { sql } from "@vercel/postgres";
import getUser from "./pg_get_user.sql";

const user = await getUser.run(sql, { id: 1 });
```

The package is deprecated on npm: Reylo's types accept its client, but Reylo's tests don't run it.

### Drizzle

Pass a Drizzle database over `pg`, postgres.js, Neon, PGlite or `Bun.sql`, or a transaction or savepoint taken from it. Over Neon's HTTP driver, Drizzle has no transactions:

```ts twoslash tab="main.ts"
import { drizzle } from "drizzle-orm/node-postgres";
import getUser from "./pg_get_user.sql";

const db = drizzle(process.env.DATABASE_URL);
const user = await getUser.run(db, { id: 1 });

await db.transaction(async (tx) => {
  await getUser.run(tx, { id: 1 });
  await tx.transaction((sp) => getUser.run(sp, { id: 1 }));
});
```

## Limits

What Reylo can't type on Postgres, and what to do instead:

| Limit | Instead |
| --- | --- |
| A function's body: a SQL function is typed from its declared `returns`, and a PL/pgSQL body isn't read | Declare the type you return |
| An array's dimensions, and whether its elements are `null` | Keep arrays one-dimensional, and remove `null` elements before passing an array back in |
| A row value outside JSON, which comes back as text | Select its fields as columns, or build an object with `to_jsonb` |
| A query nested past 1,000 levels, about 164 subqueries deep | None: Reylo falls back to Postgres's own types, any number of rows and every column nullable |
| A statement other than a query, such as `create index` or `explain` | None: it returns nothing, or rows whose columns are all nullable, as Postgres reports |
| `copy … from stdin` and `copy … to stdout`, whose rows go through the connection | Run them through your driver |
| A file of several statements, such as a migration | Put each statement in a file of its own |
| A float or `cube` on Supabase, whose Postgres prints floats rounded (`extra_float_digits = 0`), so `0.1::float8 + 0.2` comes back `0.3` | Run `alter role postgres set extra_float_digits = 1` once; the role's later connections read exact values |
