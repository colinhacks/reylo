<p className="dk-subheader">How Reylo types queries on Postgres</p>

[Reylo](/) lets you import `.sql` files into TypeScript, with every query typed from your live database. This page covers how it types and runs queries on Postgres: column types, null values, row counts, parameters and drivers.

| | |
| --- | --- |
| Postgres versions | 14, 17 and 18 |
| Connection | A `postgres://` URL in `DATABASE_URL` or [`direct_url`](/#direct_url). Connect directly, not through a pooler such as PgBouncer. |
| Drivers | postgres.js, `pg`, `pg-promise`, `Bun.sql`, PGlite, Neon and `@vercel/postgres`, and Drizzle over `pg` or postgres.js ([Drivers](#drivers)) |
| Type checking | Needs postgres.js or `pg` in your project, to read the schema |

```sql file="schema.sql"
create extension if not exists pg_jsonschema;

```

```sql file="schema.sql"
create table orders (

  total amount not null,
```

```sql file="schema.sql"
      "x": { "type": "integer" },

      "code": { "type": "string" }
    }
  }', payload)),
  at timestamp not null default localtimestamp
);
```

</Details>

## Data types

Each Postgres type maps to one TypeScript type, and `.run()` returns the same value for it on every driver:

| SQL type | TypeScript | The value `.run()` returns |
| --- | --- | --- |
| `smallint`, `integer`, `oid` | `number` | `42` |
| `bigint`, `bigserial`, `count(*)` | `bigint` | `9007199254740993n` |
| `real`, `double precision` | `number` | `1.1` |
| `numeric`, `money` | `string` | `"12.50"`, `"$1.50"` |
| `text`, `varchar`, `char`, `uuid` | `string` | `"Ada"` |
| `boolean` | `boolean` | `true` |
| `date` | `string` | `"2026-10-20"` |
| `timestamp` | `string` | `"2026-10-20T10:00:00.123456"` |
| `timestamptz` | `string` | `"2026-10-20T08:00:00.123456Z"` |
| `time`, `timetz`, `interval` | `string` | `"10:00:00"`, `"1 day 02:03:04"` |
| `json`, `jsonb` | `unknown` | `{ a: 1 }` |
| `json`, `jsonb` a JSON Schema `CHECK` holds | what the schema admits | `{ x: 10, y: 20 }` |
| JSON the statement builds (`jsonb_build_object`, `jsonb_agg`) | the object or array it builds | `{ total: 12.5 }` |
| `bytea` | `Uint8Array` | `Uint8Array.of(1, 2, 255)` |
| An array | an array of its element type | `["math", "poetry"]` |
| An enum | the union of its labels | `"admin"` |
| A domain | its base type | its base type's |
| A row value | `string` | `"(1,Ada)"` |
| Every other type (`inet`, ranges, `point`, `tsvector`, `xml`, …) | `string` | `"[1,5)"` |

Each example below pairs a SQL value with the value `.run()` returns for it: `select <SQL> as v` returns the row `{ v: <JavaScript> }`.

### Integers

A `bigint` comes back as a JavaScript `bigint`. So does `count(*)`, since Postgres types it `bigint`. To get a `number`, cast to `int` in the query:

```ts twoslash tab="main.ts"
import countOrders from "./pg_count_orders.sql";

const counts = await countOrders.run(db);
//    ^?
```

```sql tab="pg_count_orders.sql"
select count(*) as total, count(*)::int as total_number
from orders
```

Postgres types a `sum()` by what it adds up: an `integer` column sums to a `bigint`, and a `bigint` or `numeric` column to a `numeric`, which comes back as a `string`:

<Pairs>

- `sum(2::integer)` → `2n`
- `sum(2::bigint)` → `"2"`
- `sum(2.5::numeric)` → `"2.5"`

</Pairs>

### Decimals

A `numeric` comes back as its exact text, keeping the column's scale, and so does an `avg()`. A `money` comes back as text in the server's currency format:

<Pairs>

- `12.50::numeric` → `"12.50"`
- `avg(2::integer)` → `"2.0000000000000000"`
- `1.50::money` → `"$1.50"`

</Pairs>

### Dates and times

No value comes back as a `Date`. A `timestamptz` is the instant in UTC, in ISO 8601 with a `Z`. The other types are the text Postgres writes, with a `T` between the date and the time of a `timestamp`:

```ts twoslash tab="main.ts"
import orderDates from "./pg_order_dates.sql";

const order = await orderDates.run(db, { id: 1 });
//    ^?
```

```sql tab="pg_order_dates.sql"
select placed_at, ships_on from orders where id = :id
```

If your runtime has `Temporal`, read the instant with `Temporal.Instant.from()` and the date with `Temporal.PlainDate.from()`. You can pass each value back in as a parameter unchanged ([What a parameter takes](#what-a-parameter-takes)).

<Rules>

**Fractions of a second**

Fractions keep the server's precision, up to microseconds, without trailing zeros.

<Pairs>

- `'2026-10-20 10:00:00.123456+00'::timestamptz` → `"2026-10-20T10:00:00.123456Z"`
- `'2026-10-20 10:00:00.5+00'::timestamptz` → `"2026-10-20T10:00:00.5Z"`
- `'2026-10-20 10:00:00+00'::timestamptz` → `"2026-10-20T10:00:00Z"`

</Pairs>

**Infinity**

Postgres's `infinity` and `-infinity` come back as those words, in every date and time type, so `Temporal` can't parse them.

<Pairs>

- `'infinity'::timestamptz` → `"infinity"`
- `'-infinity'::date` → `"-infinity"`

</Pairs>

**Years past 9999 or before 1 AD**

A `timestamptz` uses ISO 8601's extended year, as `Temporal.Instant` does. A `date` or `timestamp` keeps Postgres's own text.

<Pairs>

- `'12344-12-31 18:30:00+00'::timestamptz` → `"+012344-12-31T18:30:00Z"`
- `'0002-06-01 12:00:00+00 BC'::timestamptz` → `"-000001-06-01T12:00:00Z"`
- `'0002-06-01 BC'::date` → `"0002-06-01 BC"`

</Pairs>

**Times and intervals**

A `time`, `timetz` or `interval` is the text Postgres writes in its default `DateStyle` and `IntervalStyle`. If your session changes those, the text changes too.

<Pairs>

- `'10:00:00+02'::timetz` → `"10:00:00+02"`
- `'1 day 02:03:04'::interval` → `"1 day 02:03:04"`

</Pairs>

</Rules>

### JSON

A `json` or `jsonb` column is typed `unknown`, unless a JSON Schema `CHECK` constrains it or your query builds the JSON. Here `payload` is typed by its schema, and `kind` by its `CHECK`:

```ts twoslash tab="main.ts"
import events from "./pg_events.sql";

const rows = await events.run(db);
//    ^?
```

```sql tab="pg_events.sql"
select kind, payload from events
```

JSON your query builds with `jsonb_build_object`, `json_build_object`, `jsonb_agg`, `json_agg`, or `to_jsonb` of a whole row, is typed from what you put in it:

```ts twoslash tab="main.ts"
import orderSummaries from "./pg_order_summaries.sql";

const rows = await orderSummaries.run(db);
//    ^?
```

```sql tab="pg_order_summaries.sql"
select u.name,
  jsonb_build_object(
    'total', o.total,
    'placed_at', o.placed_at,
    'paid', o.paid
  ) as summary
from orders o
join users u on u.id = o.user_id
```

A schema's type carries through an aggregate, and `to_jsonb` of a row is typed column by column, enums included:

```ts twoslash tab="main.ts"
import eventsByKind from "./pg_events_by_kind.sql";

const groups = await eventsByKind.run(db);
//    ^?
```

```sql tab="pg_events_by_kind.sql"
select kind, jsonb_agg(payload order by id) as payloads
from events
group by kind
```

```ts twoslash tab="main.ts"
import userRow from "./pg_user_row.sql";

const row = await userRow.run(db, { id: 1 });
//    ^?
```

```sql tab="pg_user_row.sql"
select to_jsonb(u) as "user" from users u where u.id = :id::int
```

<Rules>

**Values inside a document**

Inside JSON, a value can differ from the same value in a column. Numbers past 2^53 lose precision in `JSON.parse`, a `timestamptz` is written in the session's time zone (here `America/Los_Angeles`), and a `bytea` is hex text.

<Pairs>

- `jsonb_build_object('n', 9007199254740993::bigint)` → `{ n: 9007199254740992 }`
- `jsonb_build_object('n', 12.50::numeric)` → `{ n: 12.5 }`
- `jsonb_build_object('at', '2026-10-20 08:00:00+00'::timestamptz)` → `{ at: "2026-10-20T01:00:00-07:00" }`
- `jsonb_build_object('b', '\x0102ff'::bytea)` → `{ b: "\\x0102ff" }`
- `json_build_object('u', row(1, 'Ada'))` → `{ u: { f1: 1, f2: "Ada" } }`

</Pairs>

**Aggregates over no rows**

Over no rows, `jsonb_agg` returns `null`, and its type includes `null`. Write `coalesce(jsonb_agg(…), '[]')` to always get an array. With any other default, the column is `unknown`.

<Pairs>

- `jsonb_agg(1) filter (where false)` → `null`
- `coalesce(jsonb_agg(1) filter (where false), '[]')` → `[]`

</Pairs>

</Rules>

- **Where a schema's type applies:** selecting the column, directly or through a view or subquery; the column inside JSON your query builds; a whole row (`jsonb_agg(e)`); and a parameter written to the column.
- **Where it doesn't:** an expression on the column (`payload -> 'x'`), a column under a `union`, a `CHECK` added `NOT VALID`, and a single value passed to `to_jsonb` are all `unknown`.
- **Through a `with` query or a subquery in `from`,** built JSON keeps its type when you select its column as it is, alone or inside JSON you build, including under `coalesce(…, '[]')`. Through a `union`, a `lateral` subquery or a `*`, it's `unknown`.
- **Supported validators:** pg_jsonschema's `jsonb_matches_schema` and `json_matches_schema`, and those of `jsonschema`, `postgres-json-schema`, `is_jsonb_valid` and `json_schema_validate`. Reylo reads only the keywords and draft each one enforces.

### Arrays

An array comes back as a JavaScript array of its element type, including arrays of enums and domains:

```ts twoslash tab="main.ts"
import orderIds from "./pg_order_ids.sql";

const rows = await orderIds.run(db);
//    ^?
```

```sql tab="pg_order_ids.sql"
select u.name, u.tags, array_agg(o.id) as order_ids
from users u
left join orders o on o.user_id = u.id
group by u.id
```

<Rules>

**`NULL` elements**

Postgres lets any array contain `NULL`, even in a `NOT NULL` column, so a `text[]` column is typed `(string | null)[]`. An array your query builds from non-null values, like `array[id]`, is typed `number[]`.

<Pairs>

- `'{a,NULL}'::text[]` → `[ "a", null ]`

</Pairs>

**Several dimensions**

Postgres doesn't track an array's dimensions, so a two-dimensional `int[]` is still typed `(number | null)[]`, though it comes back as nested arrays.

<Pairs>

- `'{{1,2},{3,4}}'::int[]` → `[ [ 1, 2 ], [ 3, 4 ] ]`

</Pairs>

</Rules>

### Enums and domains

An enum is typed as the union of its labels. So is a `text` column whose `CHECK` limits it to a list (`kind in ('click', 'key')`). A domain is typed as its base type: `orders.total` is an `amount`, a `numeric`, so a `string`.

<Pairs>

- `'{admin,member}'::user_role[]` → `[ "admin", "member" ]`

</Pairs>

A domain over `jsonb` with a JSON Schema `CHECK` is typed by its schema. A `CHECK` added `NOT VALID` is ignored, since older rows may break it.

## Nullability

Every column is typed `| null` unless Reylo can tell it never is null. On Postgres, it reads your schema and the query:

- **A table's column** is non-null if it has a valid `NOT NULL` constraint, in every table that inherits from it too.
- **An outer join** makes the joined table's columns nullable: the right side of a `left join`, the left side of a `right join`, and both sides of a `full join`. Aliases tell apart a table joined to itself, so in `employees e left join employees m …`, `e.name` stays non-null.
- **A test that fails on `NULL`**, in the `where` or in a later inner join's `on`, makes that column non-null: `where o.total > 0`, `where email is not null`, `where lower(email) = :email`.
- **An expression** is non-null when Reylo's rules show it:
  - a literal, a cast, `count`, `exists` and `is null` are always non-null;
  - concatenation (`||`), comparisons, arithmetic, `like` and the other pattern matches, and the bit, containment and JSON key operators (`&`, `@>`, `&&`, `?`) are non-null over non-null operands;
  - so are built-in functions that return `NULL` only for a `NULL` argument (`length`, `lower`, `round`, …);
  - so are the values of `generate_series`, and of `unnest(array[…])` over non-null elements;
  - a `coalesce` is non-null if one of its arguments is, and a `case` if every branch is.
- **An aggregate** other than `count` returns `NULL` over no rows, so it's nullable without a `group by`. With a `group by`, every group has rows:
  - the aggregates `array_agg`, `json_agg`, `jsonb_agg` and `jsonb_object_agg` are non-null;
  - the others, such as `sum`, `max` and `string_agg`, are non-null when their argument is;
  - an aggregate with a `filter` stays nullable, since the filter can leave a group empty.
- **A whole row** (`select e`, `jsonb_agg(e)`) is non-null unless an outer join can null it, and its columns keep their types.
- **A scalar subquery** is non-null only when it always returns one non-null value: an aggregate without `group by`, like `(select count(*) …)`, or a `select` without `from`, like `(select 1)`.
- **A `union` column** is non-null when it's non-null in every branch.
- **A column of a `with` query or a subquery in `from`** is as nullable as it is in that query.
- **Your own operators, functions and casts**, or an extension's, tell Reylo nothing: it assumes nothing wherever Postgres could pick one of them over a built-in.

```ts twoslash tab="main.ts"
import userTotals from "./pg_user_totals.sql";

const rows = await userTotals.run(db);
//    ^?
```

```sql tab="pg_user_totals.sql"
select u.name, o.total, coalesce(o.paid, false) as paid
from users u
left join orders o on o.user_id = u.id
```

A `where` test on the joined table means its row exists, so its columns are non-null. Window functions are typed like anything else: `lag` is nullable, since the first row has no previous row:

```ts twoslash tab="main.ts"
import paidOrders from "./pg_paid_orders.sql";

const rows = await paidOrders.run(db);
//    ^?
```

```sql tab="pg_paid_orders.sql"
select u.name, o.total, o.placed_at
from users u
left join orders o on o.user_id = u.id
where o.paid
```

```ts twoslash tab="main.ts"
import orderGaps from "./pg_order_gaps.sql";

const rows = await orderGaps.run(db);
//    ^?
```

```sql tab="pg_order_gaps.sql"
select id, placed_at,
  placed_at - lag(placed_at) over (order by placed_at) as since_previous,
  row_number() over (order by placed_at) as n
from orders
```

To tell Reylo a value is never null, say so in the query: `coalesce(x, …)` gives a default, and `where x is not null` filters out the nulls.

## Cardinality

Reylo infers how many rows a query returns, and types `.run()`'s result to match:

| `.run()` returns | `cardinality` | When the query |
| --- | --- | --- |
| `Row` | `one` | is an aggregate without a `group by`, or inserts one row with `values (…)` and has `returning`, an `on conflict do update` included |
| `Row \| null` | `maybeOne` | matches every column of a primary key or unique index with `=`, through joins on the joined table's key; has `limit 1` or `fetch first 1 row only`; is a `distinct` or `group by` over values the `where` pins; is an `update` or `delete` by key with `returning`; or inserts one row with `on conflict do nothing` and `returning` |
| `void` | `none` | is an `insert`, `update`, `delete` or `merge` without `returning` |
| `Row[]` | `many` | is anything else |

A unique index on an expression counts when the query compares the same expression, and a partial unique index counts when the `where` includes its condition:

```ts twoslash tab="main.ts"
import userByEmail from "./pg_user_by_email.sql";

const user = await userByEmail.run(db, { email: "Ada@example.com" });
//    ^?
```

```sql tab="pg_user_by_email.sql"
select id, name from users where lower(email) = lower(:email)
```

- The expression must match the one Postgres stores in the index. An index on a domain column stores a cast, `lower((email)::text)`, so the query must write the cast too.
- Without its condition in the `where`, a partial unique index doesn't count: if the index is `on (slug) where not deleted`, then `where slug = :slug` returns `Row[]`.
- Part of a composite key doesn't count, and neither does a `having` or an `insert … select … returning`.

## Parameters

### Placeholders

Write parameters as `:name`, and pass `.run()` an object with those names. You can use Postgres's `$1` instead, but not both in one query; then `.run()` takes an object keyed by number, `{ 1: 42 }`.

### What a parameter takes

A parameter accepts the same values `.run()` returns for its type, so you can pass a row straight into the next query:

| SQL type | A parameter takes |
| --- | --- |
| `smallint`, `integer` | `number` |
| `bigint` | `number`, `bigint` or a string of digits |
| `numeric` | `string` |
| `boolean` | `boolean` |
| `date`, `timestamp`, `time` | `string` |
| `timestamptz` | a `string` that names its zone |
| `json`, `jsonb` | any JSON value, or what the column's JSON Schema admits |
| `bytea` | `Uint8Array` |
| An array | an array of its element's parameter type, without `null` |
| An enum | the union of its labels |

- A `timestamptz` parameter needs a time zone in its text, as `.run()` returns it: `"2026-10-12T19:06:48Z"`, `"2026-10-12 19:06:48+09"`, `"2026-10-12 19:06:48 Asia/Tokyo"`, or `infinity`. Pass a `Date` as `date.toISOString()`. Text without a zone is rejected before the query runs, since Postgres would read it in the session's time zone.
- A `timestamp` or `date` parameter rejects a `Date`, since drivers convert a `Date` using different time zones.
- A `bytea` parameter takes only a `Uint8Array`, and rejects base64 or hex text before the query runs, since each driver would store a string differently. Decode the text into a `Uint8Array` first.
- A JSON parameter is sent as JSON, so a string is stored as a JSON string: `'{"a":1}'` becomes `"{\"a\":1}"`. To pass JSON text you already have, cast it from text: `:data::text::jsonb`.
- The parameters of `limit` and `offset` are `bigint`s, which accept a `number` too.

### Parameters that may be null

A parameter accepts `null` in two places:

- as the first argument of `coalesce`;
- written directly into a nullable column, with no cast. A column is nullable unless it's `NOT NULL`, its domain is `not null`, or a `check (… is not null)` covers it.

```ts twoslash tab="main.ts"
import addOrder, { type Params } from "./pg_add_order.sql";
//                      ^?
```

```sql tab="pg_add_order.sql"
insert into orders (user_id, total, ships_on)
values (:user_id, :total, :ships_on)
```

A cast sets the parameter's whole type, so `:email::text` never accepts `null`. Testing a parameter for null (`:role is null`) doesn't make it nullable.

## Drivers

Reylo decodes its query results itself, so type parsers and options you set on your client don't affect Reylo's queries, and Reylo's don't affect yours. Drivers differ only in what they reject or lose:

| Driver | Not supported | Lost before Reylo sees it |
| --- | --- | --- |
| `pg` | `binary: true` | |
| `pg-promise` | A `receive` event that rewrites results | |
| postgres.js | A `transform.row` | |
| `Bun.sql` | | Microseconds of a `timestamp` or `timestamptz`, and dates before 1 AD, which Reylo rejects |
| PGlite, Neon, `@vercel/postgres` | | |

- On `Bun.sql`, queries with parameters are read in binary and others as text, so a `real` comes back exact (`1.100000023841858`) only with a parameter. Bun itself fails with "Failed to read data" on a `NULL` in an `int4[]` or `float4[]`, a two-dimensional `int[]` in a query with a parameter, and an array with explicit bounds in one without.
- The `@vercel/postgres` package is deprecated on npm: Reylo's types accept its client, but Reylo's tests don't run it.
- Transactions and connections from each driver work too: `pg`'s Pool, Client and PoolClient; postgres.js's and `Bun.sql`'s `.begin()`, `.savepoint()` and `.reserve()`; PGlite's `.transaction()`; Neon's Pool and Client; `pg-promise`'s `.task()` and `.tx()`; and a Drizzle database's `.transaction()` and savepoints, over `pg` or postgres.js.

Type checking reads your schema through postgres.js or `pg`, so if your app uses another driver, add one of these as a dev dependency.

## Limits

What Reylo can't type on Postgres, and what to write instead:

- **Function bodies.** A SQL function is typed from its declared `returns`, never its body, and a PL/pgSQL body isn't read at all. Declare the type you return.
- **Array dimensions and elements.** An `int[]` is `(number | null)[]` whatever its dimensions, and its elements may be `null` unless your query builds it from non-null values. Keep arrays one-dimensional, and remove `null` elements before passing an array back as a parameter.
- **Row values outside JSON.** A row value comes back as text. Select its fields as columns, or build an object with `to_jsonb` or `jsonb_build_object`.
- **Very deep queries.** Past 1,000 levels of nesting (about 496 terms of `a + b + …`, or 164 nested subqueries), Reylo uses only what Postgres reports: any number of rows, every column nullable.
