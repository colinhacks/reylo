<p className="dk-subheader">Reylo on Neon's serverless Postgres</p>

Reylo works with Neon.

Neon is Postgres, so everything on the [Postgres](/postgres) page holds for it. This page covers what's specific to Neon: its two connection strings, its serverless driver and its branches.

| | |
| --- | --- |
| Dialect | Postgres |
| The type check reads | The direct connection string, through [`direct_url`](/configuration#direct_url) |
| Queries run on | `@neondatabase/serverless`, `pg` or postgres.js, through the pooled connection string |
| Transactions | On a `Pool`'s client over a WebSocket, not on `neon()` over HTTP |
| Branches | Each has connection strings of its own, to type against its schema |
| Edge runtimes | Neon's driver, on the [Next.js edge runtime](/nextjs#the-edge-runtime) and in [Cloudflare Workers](/d1#setup) |

## Connection strings

Neon gives each branch two connection strings. The pooled one's host ends in `-pooler`:

```sh title=".env"
# pooled, for your app
DATABASE_URL=postgresql://…@ep-name-pooler.us-east-2.aws.neon.tech/neondb
# direct, for the type check
DATABASE_URL_UNPOOLED=postgresql://…@ep-name.us-east-2.aws.neon.tech/neondb
```

Point [`direct_url`](/configuration#direct_url) at the direct one:

```yaml title=".reylo.yaml"
direct_url: ${DATABASE_URL_UNPOOLED}
```

- Neon's pooler is PgBouncer in transaction mode. Your app's queries can go through it, but the type check can fail there.
- Without this line, Reylo reads `DATABASE_URL` and nothing else. `DATABASE_URL_UNPOOLED` is the name Neon's Vercel integration gives the direct string.
- The type check takes the string as Neon writes it, `sslmode=require` and `channel_binding=require` included ([TLS](/configuration#tls)).

## Serverless driver

Pass `neon()` from `@neondatabase/serverless`, which sends each query over HTTP:

```ts twoslash tab="main.ts"
import { neon } from "@neondatabase/serverless";
import getUser from "./get_user.sql";

const sql = neon(process.env.DATABASE_URL);
const user = await getUser.run(sql, { id: 1 });
//    ^?
```

```sql tab="get_user.sql" dialect="postgres"
select id, name, email
from users
where id = :id
```

A `Pool` or `Client` from the same package works too, over a WebSocket. Passed a `Pool`, each query runs on a client the pool checks out for it.

## Transactions

Run a transaction on a client checked out of a `Pool`:

```ts twoslash tab="main.ts"
import { Pool } from "@neondatabase/serverless";
import createUser from "./create_user.sql";

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// both inserts land, or neither
const client = await pool.connect();
try {
  await client.query("begin");
  await createUser.run(client, { name: "Ada" });
  await createUser.run(client, { name: "Grace" });
  await client.query("commit");
} catch (error) {
  await client.query("rollback");
  throw error;
} finally {
  client.release();
}
```

```sql tab="create_user.sql" dialect="postgres"
insert into users (name)
values (:name)
returning id
```

- The `transaction()` of `neon()` takes queries built with Neon's own `sql` tag, so a Reylo query can't join one.
- Drizzle over Neon's driver has transactions over a `Pool`, and none over HTTP ([Drizzle](/postgres#drizzle)).

## TCP drivers

Over TCP, pass a `pg` pool or a postgres.js client, or in Rust an sqlx pool, made with the pooled connection string:

```ts twoslash tab="pg"
import pg from "pg";
import getUser from "./get_user.sql";

const db = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const user = await getUser.run(db, { id: 1 });
```

```ts twoslash tab="postgres.js"
import postgres from "postgres";
import getUser from "./get_user.sql";

const db = postgres(process.env.DATABASE_URL);
const user = await getUser.run(db, { id: 1 });
```

```rust tab="sqlx"
#[reylo::query("select id, name, email from users where id = :id")]
pub mod get_user {}

// sqlx with its "tls-rustls" feature: Neon requires TLS
let db = sqlx::PgPool::connect(&std::env::var("DATABASE_URL")?).await?;
let user = get_user::Query { id: 1 }.run(&db).await?;
```

Each runs a transaction its own way: on a client checked out of the pool with `pg`, in `db.begin()` with postgres.js ([Drivers](/postgres#drivers)), and in `db.begin()` with sqlx ([Rust](/rust#run)).

## Branches

Each branch has connection strings of its own. Neon's CLI prints a branch's direct one:

```sh title="Terminal"
# add --pooled for the pooled one
neon connection-string my-branch
```

To type against your own branch, set it in `.env.local`, which Reylo reads before `.env`:

```sh title=".env.local"
DATABASE_URL_UNPOOLED=postgresql://…@ep-mine.us-east-2.aws.neon.tech/neondb
```

A branch starts with its parent's schema, so run your migrations on it before the type check reads it.

## Pull requests

In CI, create a branch for each pull request with Neon's GitHub Action, migrate it, and type-check against it:

```yaml title=".github/workflows/ci.yml"
on: pull_request
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      # ...
      - id: branch
        uses: neondatabase/create-branch-action@v6
        with:
          project_id: ${{ vars.NEON_PROJECT_ID }}
          api_key: ${{ secrets.NEON_API_KEY }}
          branch_name: pr-${{ github.event.number }}
      - env:
          DATABASE_URL_UNPOOLED: ${{ steps.branch.outputs.db_url }}
        # your migrations, then the type check and the build
        run: |
          npm run migrate
          npm run typecheck
          npm run build
```

Delete the branch when the pull request closes:

```yaml title=".github/workflows/cleanup.yml"
on:
  pull_request:
    types: [closed]
jobs:
  delete:
    runs-on: ubuntu-latest
    steps:
      - uses: neondatabase/delete-branch-action@v3
        with:
          project_id: ${{ vars.NEON_PROJECT_ID }}
          api_key: ${{ secrets.NEON_API_KEY }}
          branch: pr-${{ github.event.number }}
```

- The action's `db_url` is the branch's direct connection string, and `db_url_pooled` its pooled one.
- Neon's Vercel integration can also create a branch for each preview deployment, with its own `DATABASE_URL_UNPOOLED`. It starts with its parent's schema, so run your migrations on it before the build ([A host that builds before it migrates](/deployment#build-before-migrate)).

## Edge runtimes

Neon's driver connects over HTTP and WebSockets, so it runs where TCP doesn't, such as a Cloudflare Worker:

```ts twoslash tab="worker.ts"
import { neon } from "@neondatabase/serverless";
import getUser from "./get_user.sql";

export default {
  async fetch(request: Request, env: { DATABASE_URL: string }) {
    const sql = neon(env.DATABASE_URL);
    return Response.json(await getUser.run(sql, { id: 1 }));
  },
};
```

- In a Worker, it needs no `nodejs_compat` flag. [Cloudflare D1](/d1#setup) covers the Vite plugin that loads `.sql` files there.
- On the Next.js edge runtime, use it the same way ([The edge runtime](/nextjs#the-edge-runtime)).
- In an edge runtime, connect, use and close a `Pool` or `Client` within one request.
