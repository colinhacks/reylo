<p className="dk-subheader">Put your schema in a SQL file, and Reylo writes the migrations</p>

<Features>
<Feature icon="file" title="One schema file">

Your schema lives in `schema.sql`, and Reylo writes each migration from your changes to it.

</Feature>
<Feature icon="branch" title="Linear history">

A lockfile lists your migrations in order, so two branches that each add one conflict in git, before anything deploys.

</Feature>
<Feature icon="database" title="Postgres, MySQL and SQLite">

One set of commands for all three.

</Feature>
<Feature icon="shield" title="No silent data loss">

Nothing is dropped until you say so with `--drop`, and `--rename` settles what Reylo can't tell apart.

</Feature>
<Feature icon="hash" title="Integrity checks">

Chained hashes in the lock catch a migration edited, deleted or reordered, with no database. A fingerprint on each database catches changes made by hand.

</Feature>
<Feature icon="layers" title="Real dry runs">

Reylo replays your migrations on a throwaway database, so `reylo migrate prod --dry-run` shows what a deploy would do, running nothing on yours.

</Feature>
</Features>

## Basic usage

Install Reylo, and start your migrations from your database:

```terminal
$ npm install reylo
$ npx reylo migration init
✓ Wrote reylo/schema.sql, reylo/migrations/init.sql and reylo/reylo-lock.yaml
  + init.sql recorded, not run: already in place
✓ The history lists the 1 migration this database's schema has
```

Commit the files it writes, all but the cache:

```terminal
reylo/
├── schema.sql              # the schema you want
├── migrations/             # each change, as plain SQL
│   └── init.sql
├── reylo-lock.yaml         # the order they run in
└── .cache/
    └── .gitignore          # keeps the cache out of git
```

To change your schema, edit `schema.sql`, which holds all of it:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null -- [!code --]
  email text not null, -- [!code ++]
  bio text -- [!code ++]
);
```

Generate the migration:

```terminal
$ npx reylo migration create add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql
```

Read what it wrote. It's plain SQL, the change and nothing else, and yours to edit:

```sql title="20261104140347_add_bio.sql"
alter table users add column bio text;
```

Run it on your development database:

```terminal
$ npx reylo migrate dev
Applying to postgres://localhost:5432/app
  ✓ 20261104140347_add_bio.sql  applied · 4 ms
Wrote reylo/reylo-lock.yaml
```

Commit the migration and the lock. When you deploy, run it on production:

```terminal
$ npx reylo migrate prod
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
```

## Configuration

Each setting is optional. Here they are with their defaults:

```yaml title=".reylo.yaml"
# The database Reylo migrates
direct_url: ${DATABASE_URL}

# The directory of schema.sql, the migrations, the lock and the cache
dir: reylo

# A server for shadow databases; null uses your database's own
shadow_url: null
```

To migrate another database, pass `--url`.

## Shadow databases

Reylo reads your SQL with a real database.

It makes a throwaway database beside yours, runs your migrations on it and reads the schema they make. That's why hand-written SQL counts, and why there's no snapshot file to keep in step. Writing and repairing migrations need one, and a deploy doesn't:

```text
Needs one      migration init (on a database with a schema)
               migration create
               migration history push
               migrate dev
               migrate prod --dry-run
               schema push

Needs none     migrate prod
               migration lint
               migration history pull
               schema pull
               db wipe
```

Reylo makes its shadow databases on your database's own server, and drops them when it's done. Where that server refuses `create database`, as a hosted database often does, point `shadow_url` at another server running the same version:

```yaml title=".reylo.yaml"
# A local Postgres 18, for a hosted Postgres 18
shadow_url: postgres://localhost:5433/postgres
```

## The lock

The lock lists your migrations in the order they run.

Each line has a checksum chained to the line before. A migration it doesn't list is a draft, free to edit, which only `reylo migrate dev` runs:

```yaml title="reylo-lock.yaml"
schema: c7bf681b
migrations:
  - 20261104120000_users.sql c86e9de4
  - 20261104140347_add_bio.sql 78ad08c0
```

When two branches each add a migration, git conflicts on the lock, before anything is deployed. Keep main's lines, then run `reylo migrate dev`, which runs your branch's migrations after main's and adds them back.

## CLI

Every command and flag:

```terminal
Usage: reylo <group> <command> [flags]

Commands:
  migration init           Start from this database
    --schema <name>        A schema to read (Postgres; public by default)
  migration create <name>  Write a migration from your change to schema.sql
    --drop <names>         Accept what it drops: tables and columns
    --rename <old>=<new>   Say a table or column was renamed
  migration lint           Check the migrations and schema.sql, with no database
  migration history push   Record the migrations this database's schema has
  migration history pull   Write the migrations this database ran into files
  migrate dev              Take this database to the migrations, and lock them
  migrate prod             Run what the lock lists, with no shadow database
    --dry-run              Try it on a shadow database, running nothing here
  schema push              Take this database to schema.sql, unrecorded
    --watch                Again on each change
  schema pull              Write schema.sql from this database
    --schema <name>        A schema to read (Postgres; public by default)
  db wipe                  Delete every row, keeping the schema

Flags:
  --url <url>              The database, in place of direct_url
  -h, --help               Print this help
```

<Callout title="Development only">

The commands that change a database in ways no deploy wants, `migrate dev`, `schema push` and `db wipe`, refuse to run where `CI` is set.

</Callout>

### `migration init`

Starts your migrations from a database you already have.

It writes `schema.sql` and a first migration, and records that migration as run:

```terminal
$ reylo migration init
✓ Wrote reylo/schema.sql, reylo/migrations/init.sql and reylo/reylo-lock.yaml
  + init.sql recorded, not run: already in place
✓ The history lists the 1 migration this database's schema has
```

### `migration create`

Writes a migration from your change to `schema.sql`.

It tries the migration on a shadow database first. The file is yours: read it, and add the data changes a schema can't say.

Nothing is dropped until you name it. A change that drops a table or column, or changes a type so that values are lost, is refused:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null, -- [!code --]
  email text not null -- [!code ++]
  bio text -- [!code --]
);
```

```terminal
$ reylo migration create drop_bio
✗ This migration would drop users.bio, and its data

  To drop it:
    reylo migration create drop_bio --drop users.bio

No migration was written.
```

A column that goes while one just like it comes is a rename, which keeps its rows:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null,
  bio text -- [!code --]
  about text -- [!code ++]
);
```

```terminal
$ reylo migration create about
! Renames, keeping rows:
    users.bio → about
  If they are two, state it: --drop users.bio
✓ Wrote reylo/migrations/20261104150000_about.sql
```

Where the new one differs too, only you can say what it is. Reylo lists every such pair, and writes nothing until you settle them:

```terminal
$ reylo migration create tidy
✗ These 2 look like renames, but each changes more than its name

    posts.title → heading  text → character varying(100)
    users.bio   → about    text → character varying(200)

  If they are renames, keeping their rows:
    reylo migration create tidy \
      --rename posts.title=heading \
      --rename users.bio=about
  If they are new, dropping the old ones and their data:
    reylo migration create tidy --drop posts.title,users.bio

No migration was written.
```

### `migration lint`

Checks your migrations and `schema.sql`, with no database.

It reads the files alone: their names, whether each runs atomically, the lock's chain, and `schema.sql` against the checksum the lock holds. Run it in a pre-commit hook:

```terminal
$ reylo migration lint
✓ reylo/reylo-lock.yaml lists every migration, in order, as written
✓ The migrations reach reylo/schema.sql
```

### `migrate`

Runs your migrations, in development and in production.

On your development database, `reylo migrate dev` runs what is new, rewinds what no longer agrees, such as a branch's migration after you switch away from it, and writes the lock:

```terminal
$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ↺ 20261104120000_tags.sql   rewound: it isn't in the migrations
    Dropped tags, 3 rows
  ✓ 20261104130000_posts.sql  applied · 3 ms
Wrote reylo/reylo-lock.yaml
```

When you deploy, `reylo migrate prod` runs what the lock lists and the database hasn't run. Each migration runs in one transaction with its history row; on MySQL, where a schema change commits on its own, each holds one change.

```terminal
$ reylo migrate prod
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
```

It needs no shadow database, so it needs no permission to create one. Each migration it runs stores a fingerprint of the schema, and it refuses a database that no longer has it:

```terminal
$ reylo migrate prod
✗ This database changed since Reylo last ran on it

  See how:
    reylo migrate prod --dry-run

Nothing was applied.
```

With `--dry-run`, it runs nothing, and replays your migrations on shadow databases instead: against your database, against `schema.sql`, and with what's pending tried on top. Run it in CI, and before you deploy:

```terminal
$ reylo migrate prod --dry-run
✓ The migrations reach reylo/schema.sql
✓ This database matches its history
✓ 1 pending, and each runs in a shadow database:
    20261104140347_add_bio.sql
```

Your database's `COMMENT ON` comments aren't compared. A migration writes them, but one added in a dashboard is no drift, and stops no deploy.

After a new version of Reylo, or a new major version of your database, the fingerprint it stored can't be compared: `reylo migrate prod` runs, stores a new one, and says so. A dry run checks the database then too.

### `schema`

Copies your schema between `schema.sql` and your database, with no migration.

To try a change, `reylo schema push` takes your development database to `schema.sql`. What the file no longer has is dropped, with its rows:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null,
  bio text -- [!code --]
  bio text, -- [!code ++]
  nick text -- [!code ++]
);
```

```terminal
$ reylo schema push
Pushing schema.sql to postgres://localhost:5432/app
  + alter table users add column nick text;

  Not in any migration yet:
    reylo migration create <name>
```

With `--watch`, it pushes again each time you save. It needs your database at its migrations, so it refuses until `reylo migrate dev` has run. When you then write the migration, `reylo migrate dev` records it without running it again.

To go the other way, `reylo schema pull` writes `schema.sql` from your database. It's for a change made on the database itself, which `reylo migration create` then writes as a migration. It writes the database's own dump, so your comments and layout go, and git keeps them:

```terminal
$ reylo schema pull
✓ Wrote reylo/schema.sql from postgres://localhost:5432/app
```

### `migration history`

Repairs the record of what ran.

Your migration files and your database's history table are two copies of one list, and your tables say which is right. Copy the right one over the other.

Where the files are right, `reylo migration history push` writes the history table from them, running nothing. It records the migrations a shadow database shows make the schema your database has; those after them stay pending:

```terminal
$ reylo migration history push --url $PROD_URL
  + 20261104160000_users_email.sql recorded, not run: already in place
✓ The history lists the 3 migrations this database's schema has
```

Where the database is right, `reylo migration history pull` writes the files from it. A migration someone deleted is written again, one edited since it ran is written over, and a lock that's lost is written back. Files the database hasn't run are left as they are, and listed:

```terminal
$ reylo migration history pull --url $PROD_URL
Pulling from postgres://db.example.com/app
  ↓ 20261104140347_add_bio.sql  written over: it differed from what ran
Not run on this database, and left as they are: 20261105090000_tags.sql
```

Where your tables hold a change neither lists, someone made it by hand. Keep it by writing it as a migration, then record it on the database that has it:

```terminal
$ reylo schema pull --url $PROD_URL
$ reylo migration create users_email
$ reylo migrate dev
$ reylo migration history push --url $PROD_URL
```

### `db wipe`

Deletes every row, keeping the schema and the history.

It leaves a platform's own tables alone, such as Supabase's `auth.users`:

```terminal
$ reylo db wipe
✓ Deleted every row of 2 tables; the schema and the history stay
```

## Examples

In development:

```terminal
# Write a migration from your change to schema.sql
$ reylo migration create add_bio

# One that drops a column
$ reylo migration create drop_bio --drop users.bio

# One that renames a column and changes its type
$ reylo migration create about --rename users.bio=about

# Run your migrations
$ reylo migrate dev

# Try a change with no migration yet, on every save
$ reylo schema push --watch

# Start again with no rows, and your seed
$ reylo db wipe && reylo run --file seed.sql
```

In CI, and when you deploy:

```terminal
# Check the files, with no database, in a pre-commit hook
$ reylo migration lint

# Try the deploy, running nothing
$ reylo migrate prod --dry-run

# Deploy
$ reylo migrate prod --dry-run && reylo migrate prod

# Take back a migration as production ran it
$ reylo migration history pull --url $PROD_URL

# Run a SQL file on a database, recording nothing
$ reylo run --file backfill.sql --url $PROD_URL
```
