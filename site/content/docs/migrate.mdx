<p className="dk-subheader">Put your schema in a SQL file, and Reylo writes the migrations</p>

<Features>
<Feature icon="file" title="One schema file">

Your schema lives in `schema.sql`, and Reylo writes each migration from your changes to it.

</Feature>
<Feature icon="branch" title="Linear history">

A lockfile lists your migrations in order, so two branches that each add one conflict in git, before anything deploys. Opt out with `lock: false`.

</Feature>
<Feature icon="database" title="Postgres, MySQL and SQLite">

One set of commands for all three.

</Feature>
<Feature icon="shield" title="No silent data loss">

Nothing is dropped until you say so with `--drop`, and `--rename` settles what Reylo can't tell apart.

</Feature>
<Feature icon="hash" title="Integrity checks">

Chained hashes in the lock catch a migration edited, deleted or reordered, with no database. A fingerprint on each database catches changes made by hand.

</Feature>
<Feature icon="layers" title="Real dry runs">

Shadow databases replay every migration with `reylo migrate check`, running nothing on yours.

</Feature>
</Features>

## Basic usage

Install Reylo, and start from your database:

```terminal
$ npm install reylo
$ npx reylo migrate init
✓ Wrote reylo/schema.sql, reylo/migrations/init.sql and reylo/reylo-lock.yaml
  + init.sql recorded, not run: already in place
✓ The history lists the 1 migration this database's schema has
✓ Added migrate to .reylo.yaml
```

It adds a section to your project file:

```yaml title=".reylo.yaml"
direct_url: ${DATABASE_URL}
migrate: # [!code ++]
  lock: true # [!code ++]
```

And it writes these files, which you commit, all but the cache:

```terminal
reylo/
├── schema.sql              # the schema you want
├── migrations/             # each change, as plain SQL
│   └── init.sql
├── reylo-lock.yaml         # the order they run in
└── .cache/
    └── .gitignore          # keeps the cache out of git
```

Your schema now lives in one file:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null
);
```

To change your schema, change that file:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null -- [!code --]
  email text not null, -- [!code ++]
  bio text -- [!code ++]
);
```

Reylo writes the migration:

```terminal
$ reylo migrate create add_bio
✓ Wrote reylo/migrations/20261104140347_add_bio.sql
```

It's plain SQL, the change and nothing else:

```sql title="20261104140347_add_bio.sql"
alter table users add column bio text;
```

Run it on your development database:

```terminal
$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ✓ 20261104140347_add_bio.sql  applied · 4 ms
Wrote reylo/reylo-lock.yaml
```

Commit it, and run it on production when you deploy:

```terminal
$ reylo migrate prod
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
```

## Configuration

Every setting is optional.

```yaml title=".reylo.yaml"
# A server to build shadow databases on, where the database's own
# refuses create database. Default: the database's own server.
shadow_url: ${SHADOW_URL}

migrate:
  # Whether the lock sets the order your migrations run in. Without it,
  # their names do. Default: true.
  lock: true
```

Reylo migrates the database your type check reads: [`direct_url`](/#direct_url), else `DATABASE_URL`. It keeps its files in `reylo/`, or the directory [`dir`](/#dir) names.

## CLI

Every command and flag:

```terminal
Usage: reylo migrate <command> [flags]

Commands:
  init                    Start from this database
    --schema <name>       A schema to read (Postgres; public by default)
  create <name>           Write a migration from your change to schema.sql
    --drop <names>        Accept what it drops: tables and columns
    --rename <old>=<new>  Say a table or column was renamed
  dev                     Take this database to the migrations, and lock them
  prod                    Run what the lock lists, with no shadow database
  sync                    Take this database to schema.sql, unrecorded
    --watch               Again on each change
  check                   Check the migrations, schema.sql and this database
    --offline             Check only what needs no database
  reset                   Drop everything in this database
  wipe                    Delete every row, keeping the schema
  pull                    Write the migrations this database ran into files
  sync-history            Record what this database's schema already has
  lock                    Write the lock from what this database ran
  unlock                  Delete the lock: migrations run by name

Flags:
  --url <url>             The database, in place of direct_url
  --dir <path>            Reylo's directory, in place of dir
  -h, --help              Print this help
```

<Callout title="Development only">

The commands that change a database in ways no deploy wants, `dev`, `sync`, `reset` and `wipe`, refuse to run where `CI` is set.

</Callout>

### `init`

Starts your migrations from a database you already have.

It writes `schema.sql` and a first migration, and records that migration as run:

```terminal
$ reylo migrate init
Wrote reylo/schema.sql, reylo/migrations/init.sql and reylo/reylo-lock.yaml
  + init.sql recorded, not run: already in place
✓ The history lists the 1 migration this database's schema has
```

### `create`

Writes a migration from your change to `schema.sql`.

It tries the migration on a shadow database first, a throwaway one Reylo builds beside yours. The file is yours: read it, and add the data changes a schema can't say.

Nothing is dropped until you name it. A change that drops a table or column, or changes a type so that values are lost, is refused:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null, -- [!code --]
  email text not null -- [!code ++]
  bio text -- [!code --]
);
```

```terminal
$ reylo migrate create drop_bio
✗ This migration would drop users.bio, and its data

  To drop it:
    reylo migrate create drop_bio --drop users.bio

No migration was written.
```

A column that goes while one just like it comes is a rename, which keeps its rows:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null,
  bio text -- [!code --]
  about text -- [!code ++]
);
```

```terminal
$ reylo migrate create about
! Renames, keeping rows:
    users.bio → about
  If they are two, state it: --drop users.bio
✓ Wrote reylo/migrations/20261104150000_about.sql
```

Where the new one differs too, only you can say what it is. Reylo lists every such pair, and writes nothing until you settle them:

```terminal
$ reylo migrate create tidy
✗ These 2 look like renames, but each changes more than its name

    posts.title → heading  text → character varying(100)
    users.bio   → about    text → character varying(200)

  If they are renames, keeping their rows:
    reylo migrate create tidy \
      --rename posts.title=heading \
      --rename users.bio=about
  If they are new, dropping the old ones and their data:
    reylo migrate create tidy --drop posts.title,users.bio

No migration was written.
```

### `migrate`

Runs your migrations, in development and in production.

On your development database, `reylo migrate dev` runs what is new, rewinds what no longer agrees, such as a branch's migration after you switch away from it, and writes the lock:

```terminal
$ reylo migrate dev
Applying to postgres://localhost:5432/app
  ↺ 20261104120000_tags.sql   rewound: it isn't in the migrations
    Dropped tags, 3 rows
  ✓ 20261104130000_posts.sql  applied · 3 ms
Wrote reylo/reylo-lock.yaml
```

When you deploy, `reylo migrate prod` runs what the lock lists and the database hasn't run. Each migration runs in one transaction with its history row; on MySQL, where a schema change commits on its own, each holds one change.

```terminal
$ reylo migrate prod
Applying to postgres://db.example.com/app
  ✓ 20261104140347_add_bio.sql  applied · 12 ms
```

It builds no shadow database, so it needs no permission to create one. Each migration it runs stores a fingerprint of the schema, and it refuses a database that no longer has it:

```terminal
$ reylo migrate prod
✗ This database changed since Reylo last ran on it

  See how:
    reylo migrate check

Nothing was applied.
```

After a new version of Reylo, or a new major version of your database, the fingerprint it stored can't be compared: it runs, stores a new one, and says so. Run `reylo migrate check` first, as in every deploy, and it checks the database then too.

### `sync`

Takes your development database to `schema.sql` without writing a migration.

It's for trying a change. What the file no longer has is dropped, with its rows:

```sql title="schema.sql"
create table users (
  id integer primary key,
  email text not null,
  bio text -- [!code --]
  bio text, -- [!code ++]
  nick text -- [!code ++]
);
```

```terminal
$ reylo migrate sync
Syncing postgres://localhost:5432/app with schema.sql
  + alter table users add column nick text;

  Not in any migration yet:
    reylo migrate create <name>
```

With `--watch`, it syncs again each time you save. It needs your database at its migrations, so it refuses until `reylo migrate dev` has run. When you then write the migration, `reylo migrate dev` records it without running it again.

### `check`

Checks your migrations, `schema.sql` and your database, running nothing.

It replays them on shadow databases. Run it in CI, and before you deploy:

```terminal
$ reylo migrate check
✓ The migrations reach reylo/schema.sql
✓ This database matches its history
✓ Nothing is pending
```

Your database's `COMMENT ON` comments aren't compared. A migration writes them, but one added in a dashboard is no drift, and stops no deploy.

With `--offline`, it checks what needs no database: the lock against the files, and `schema.sql` against the checksum the lock holds.

```terminal
$ reylo migrate check --offline
✓ reylo/reylo-lock.yaml lists every migration, in order, as written
✓ The migrations reach reylo/schema.sql
```

### `reset`

Drops everything in your development database.

The migrations' history goes with it. Run your migrations again, and your seed, after it:

```terminal
$ reylo migrate reset
✓ Dropped everything in postgres://localhost:5432/app
$ reylo migrate dev
$ reylo run --file seed.sql
```

### `wipe`

Deletes every row, keeping the schema and the history.

```terminal
$ reylo migrate wipe
✓ Deleted every row of 2 tables; the schema and the history stay
```

### `pull`

Writes each migration your database ran into its file, as it ran it.

The text comes from the history Reylo keeps in the database: a migration someone deleted is written again, and one edited since it ran is written over. Files the database hasn't run are left as they are.

```terminal
$ reylo migrate pull --url $PROD_URL
Pulling from postgres://db.example.com/app
  ↓ 20261104140347_add_bio.sql  written over: it differed from what ran
```

### `sync-history`

Records what your database's schema already has, running nothing.

It rewrites the history once a shadow database shows the migrations make exactly that schema. To keep a change someone made by hand, add it to `schema.sql`, write its migration, and lock it:

```terminal
$ reylo migrate create users_email
$ reylo migrate dev
```

Then, with the lock committed, record it on the database that has it:

```terminal
$ reylo migrate sync-history --url $PROD_URL
  + 20261104160000_users_email.sql recorded, not run: already in place
✓ The history lists the 3 migrations this database's schema has
```

### `lock` and `unlock`

The lock lists your migrations in the order they run.

Each line has a checksum chained to the line before. A migration it doesn't list is a draft, free to edit:

```yaml title="reylo-lock.yaml"
schema: c7bf681b
migrations:
  - 20261104120000_users.sql c86e9de4
  - 20261104140347_add_bio.sql 78ad08c0
```

When two branches each add a migration, git conflicts on the lock, before anything is deployed. Keep main's lines, then run `reylo migrate dev`, which runs your branch's migrations after main's and adds them back.

To stop keeping a lock, unlock the project. Migrations then run by name, and two branches no longer conflict. One that lands older than one already run runs only if neither changes data; `reylo migrate check` says whether both orders end the same.

```terminal
$ reylo migrate unlock
✓ Unlocked: deleted reylo-lock.yaml; .reylo.yaml says lock: false
  reylo migrate lock locks it again, in the order a database applied the migrations
```

To start keeping one again, lock it, from what your database ran:

```terminal
$ reylo migrate lock
✓ Wrote reylo/reylo-lock.yaml: the 5 migrations this database applied, in its order
```

## Examples

In development:

```terminal
# Write a migration from your change to schema.sql
$ reylo migrate create add_bio

# One that drops a column
$ reylo migrate create drop_bio --drop users.bio

# One that renames a column and changes its type
$ reylo migrate create about --rename users.bio=about

# Run your migrations
$ reylo migrate dev

# Try a change with no migration yet, on every save
$ reylo migrate sync --watch

# Start over, with your seed
$ reylo migrate reset && reylo migrate dev && reylo run --file seed.sql
```

In CI, and when you deploy:

```terminal
# Check everything
$ reylo migrate check

# Check with no database, in a pre-commit hook
$ reylo migrate check --offline

# Deploy
$ reylo migrate check && reylo migrate prod

# Take back a migration as production ran it
$ reylo migrate pull --url $PROD_URL

# Run a SQL file on a database, recording nothing
$ reylo run --file backfill.sql --url $PROD_URL
```
