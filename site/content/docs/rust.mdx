<p className="dk-subheader">Typed SQL in Rust, checked against your database when your crate compiles</p>

Reylo types each statement from your database at compile time.

```rust
#[reylo::query("select id, name, email from users where id = :id::int")]
pub mod get_user {}

// user: Option<get_user::Row>
let user = get_user::Query { id: 1 }.run(&pool).await?;
```

The attribute fills the module with the statement's types: `Query`, its parameters, and `Row`, one row of its result. The query runs on sqlx, on your own pool, connection or transaction.

<Callout title="Not on crates.io yet">

The `reylo` and `reylo-build` crates aren't on crates.io yet.

</Callout>

## Setup

To use Reylo in Rust, you'll need:

- **sqlx 0.9 or 0.8**, with its Tokio runtime and your database's driver. SQLite needs sqlx 0.9.
- **A running dev database.** Reylo reads your current schema from it each time the crate compiles:
  - **Postgres** 14 to 19
  - **MySQL** 8.0.38 or later
  - **SQLite**

<div className="dk-steps">

### Install

Add Reylo and sqlx to `Cargo.toml`:

```toml title="Cargo.toml"
[dependencies]
reylo = { version = "0.8", features = ["chrono", "uuid"] }
sqlx = { version = "0.9", features = ["runtime-tokio", "postgres"] }
```

Reylo's features choose the database and the Rust types the attribute writes:

```toml title="Cargo.toml"
reylo = { version = "0.8", features = [
  "sqlx_0_9",      # the default; or "sqlx_0_8"
  "postgres",      # the default; or "mysql" or "sqlite"
  "chrono",        # dates and times as chrono's types; or "time"
  "uuid",          # uuid as uuid::Uuid
  "rust_decimal",  # numeric as rust_decimal::Decimal; or "bigdecimal"
  "migrate",       # the default; reylo::migrate!(), which runs your migrations
] }
```

A statement that reads a type whose feature is off fails to compile, and says which feature to turn on. Reylo's crates need Rust 1.94 or later, the oldest sqlx 0.9 builds on.

On sqlx 0.8, turn off Reylo's default features and turn on `sqlx_0_8`:

```toml title="Cargo.toml"
[dependencies]
reylo = { version = "0.8", default-features = false, features = ["sqlx_0_8", "postgres", "migrate", "chrono"] }
sqlx = { version = "0.8", features = ["runtime-tokio", "postgres", "chrono"] }
```

On 0.8, sqlx's own `json`, `chrono`, `time` and `uuid` features are yours to turn on, as your types need them; `json` is one of sqlx's defaults.

### Database

Reylo finds your dev database through the `DATABASE_URL` environment variable, or a `.env` file beside the crate's `Cargo.toml`. In a workspace, that's the member's own, not the workspace root's:

```sh title=".env"
# or mysql://… or sqlite:./path/to/your.db, etc
DATABASE_URL=postgres://postgres@localhost:5432/app
```

The URL's scheme names the database: `postgres://`, `mysql://`, or `sqlite:` with a path relative to the crate.

A change to `reylo/schema.sql` or the migrations' lock compiles the crate again. After a change made another way, such as SQL run by hand, compile it again yourself:

```sh
touch src/main.rs && cargo build
```

### Command line

The `reylo` command runs your migrations and writes modules to files. Install it once:

```sh
cargo binstall reylo-cli
```

[Install](/cli#install) has the other ways: Homebrew, Scoop, mise and a script. In a Rust project, it runs the version your `Cargo.lock` holds for the `reylo` crate, the same as the attribute's: a version it doesn't have yet, it fetches once, checked against the release's checksums.

<Details summary="Run it through cargo, with nothing installed">

Add a package to your workspace that runs it:

```toml title="tools/Cargo.toml"
[package]
name = "tools"
version = "0.0.0"
edition = "2021"
publish = false

[dependencies]
reylo-cli = "0.8"
```

```rust title="tools/src/main.rs"
fn main() {
    reylo_cli::main()
}
```

```toml title=".cargo/config.toml"
[alias]
reylo = "run -q -p tools --"
```

Then `cargo reylo db push` runs it. It compiles the CLI in your project the first time, beside the attribute's own copy of the engine.

</Details>

## Macro

Each statement gets a module of its types.

```rust
#[reylo::query("select id, name, email from users where id = :id::int")]
pub mod get_user {
    // written by the attribute:

    // the parameters
    pub struct Query { pub id: i32 }
    // one row of the result
    pub struct Row { pub id: i32, pub name: String, pub email: Option<String> }
    // the statement as sqlx sends it, with the database's own placeholders
    pub const SQL: &str = "…";

    // and an enum for each database enum it reads or binds,
    // and a struct for each JSON object it builds
}
```

### Parameters

Each `:name` in the statement is a field of `Query`.

Its type comes from its cast, or from where the statement uses it, and a text parameter is a `&str`. To accept null, cast it to `nullable(…)`, which makes its field an `Option`:

```rust
#[reylo::query("
    select id, title from posts
    where user_id = coalesce(:user_id::nullable(int), user_id)
    order by id
")]
pub mod posts_of {}

let everyone = posts_of::Query { user_id: None }.run(&pool).await?;
let ada_s = posts_of::Query { user_id: Some(1) }.run(&pool).await?;
```

### Results

What `.run()` returns follows the statement's cardinality:

| Rows | `.run()` returns |
| --- | --- |
| Exactly one, as `select count(*) from users` | `Row` |
| At most one, as a lookup by a unique key | `Option<Row>` |
| Any number | `Vec<Row>` |
| None: a write with no `returning` | `u64`, the number of rows it changed |

Each column of `Row` is its [Rust type](/inference#primitives), in an `Option` where it may be null. The struct derives `Debug`, `Clone` and `PartialEq`, and serde's `Serialize` where every field's type has it. A second row where the cardinality allows one is an error, `reylo::UnexpectedRow`.

To read rows into a struct of your own, name it `Row` in the module. Each field takes its column through `Into`, and an enum field through `.cast()`, so its enum needs `#[reylo::reflect]` ([Enums](#enums)):

```rust
#[reylo::reflect("public.user_role")]
pub enum UserRole {} // filled in: Admin, Member

pub struct Member { pub id: i32, pub name: String, pub role: UserRole }

#[reylo::query("select id, name, role from users where id = :id::int")]
pub mod find_member {
    pub use crate::Member as Row;
}
```

To add a method to the row, implement it inside the module, which sees the items of the one around it:

```rust
#[reylo::query("select id, name, email from users where id = :id::int")]
pub mod get_contact {
    impl Row {
        pub fn label(&self) -> &str {
            self.email.as_deref().unwrap_or(&self.name)
        }
    }
}
```

### Transactions

To run a query in a transaction, pass `.run()` the connection it holds:

```rust
let mut tx = pool.begin().await?;
let user = get_user::Query { id: 1 }.run(&mut *tx).await?;
tx.commit().await?;
```

### Streams

To read the rows one at a time as they arrive, call `.stream()` on a query that returns any number of them:

```rust
use futures_util::TryStreamExt;

#[reylo::query("select id, title from posts where user_id = :user_id::int order by id")]
pub mod posts_by_user {}

let mut posts = posts_by_user::Query { user_id: 1 }.stream(&pool);
while let Some(post) = posts.try_next().await? {
    println!("{}", post.title);
}
```

### Enums

Each database enum a statement reads or binds is an enum in its module.

Its variants are its values in PascalCase, and `.label()` gives a value as the database stores it:

```rust
#[reylo::query("select id, name from users where role = :role order by id")]
pub mod users_by_role {}

let admins = users_by_role::Query { role: users_by_role::UserRole::Admin }.run(&pool).await?;
let label = users_by_role::UserRole::Admin.label(); // "admin"
```

A `text` column whose `CHECK` lists its values, and a MySQL `ENUM`, is an enum the same way:

```rust
// posts.status text not null check (status in ('draft', 'published'))
#[reylo::query("select id, status from posts order by id")]
pub mod post_statuses {}

let rows = post_statuses::Query.run(&pool).await?;
let status: post_statuses::Status = rows[0].status;
```

Each module holds its own enum. To pass one query's value to another, `.cast()` it, which compiles only between enums of the same database enum:

```rust
use reylo::Enum;

#[reylo::query("select id, role from users where id = :id::int")]
pub mod get_role {}

let ada = get_role::Query { id: 1 }.run(&pool).await?.expect("ada");
let admins = users_by_role::Query { role: ada.role.cast() }.run(&pool).await?;
```

To read a column into an enum of your own, write `Row` in the module with that field alone. The module writes the other fields, and matches your enum's variants by name:

```rust
#[derive(Debug, Clone, Copy, PartialEq)]
pub enum Role { Admin, Member }

#[reylo::query("select id, name, role from users where id = :id::int")]
pub mod get_member {
    pub struct Row {
        pub role: crate::Role,
    }
}
```

A variant your enum lacks, or one it has beyond the database's values, fails to compile. A `Params` with some of the fields types parameters the same way.

The `#[reylo::reflect]` attribute checks an enum's variants against the database's values, or fills in an empty one. It takes a Postgres enum type, or a column whose `CHECK` or MySQL `ENUM` lists its values, as `#[reylo::reflect("posts.status")]`.

### JSON

A JSON object the statement builds is a struct of its fields, in sqlx's `Json`:

```rust
#[reylo::query("
    select json_build_object('id', u.id, 'name', u.name) as author
    from users u where u.id = :id::int
")]
pub mod author_json {}

let row = author_json::Query { id: 1 }.run(&pool).await?.expect("ada");
// author: author_json::Author { id: i32, name: String }
let author = row.author.0;
```

A JSON column a JSON Schema `CHECK` holds is typed by what the schema admits, in sqlx's `Json` too:

- An object is a struct of its properties, with an `Option` for each one the schema doesn't require, and any keys the schema doesn't name in `additional_properties`.
- An integer is an `i64`. A value it can't hold, such as one written as `1.0` or one beyond its range, fails `.run()`.
- A `number` is an `f64`, so `9007199254740993` reads as the nearest `f64`, and `1e400` fails.

Any other JSON is a `serde_json::Value`, and so is JSON no one Rust type holds, such as a union of a string and a number. A decimal inside JSON the statement builds fails to compile, since no Rust number reads it exactly: cast it to text inside the JSON.

### Errors

A mistake in a statement or its parameters fails to compile, where it is.

A statement the database refuses fails at its string, with the database's own error and the line and column it points at:

```text
error: column "nme" does not exist (42703)
       at src/main.rs:2:16
 --> src/main.rs:1:16
  |
1 |   #[reylo::query("
  |  ________________^
2 | |     select id, nme
3 | |     from users where id = :id::int
4 | | ")]
  | |_^
```

A misspelt, missing or mistyped parameter is Rust's own error on the struct, which compiler errors call by its other name, `Params`:

```text
error[E0560]: struct `Params` has no field named `user_id`
 --> src/main.rs:4:34
  |
4 |     let user = get_user::Query { user_id: 1 }.run(&pool).await?;
  |                                  ^^^^^^^ `Params` does not have this field
  |
  = note: available fields are: `id`
```

## Codegen

Reylo can write each query's module to a file instead.

```sh
reylo generate rust-sqlx
```

It writes a `.rs` file beside each `.sql` file of the crate, holding what `#[reylo::query]` would: `Query`, `Row` and `.run()`, with the [command line](#command-line) installed.

```text
src/
  queries.rs          pub mod get_user;
  queries/
    get_user.sql
    get_user.rs       written by reylo generate
```

```rust
let user = queries::get_user::Query { id: 1 }.run(&pool).await?;
```

The crate compiles them as any other Rust: no proc macro, and no database when it builds.

### Inputs

Name the files or folders to read, or a glob in quotes:

```sh
reylo generate rust-sqlx src/queries src/reports
reylo generate rust-sqlx 'src/**/*.sql'
```

With none, it reads every `.sql` file under the crate's `src/`, found from the nearest `Cargo.toml`, and at a workspace's root, every member's.

### One file

To write every module to one file, name it with `--out`:

```sh
reylo generate rust-sqlx src/queries --out src/queries.rs
```

Each folder under an input becomes a module, so `users/get.sql` and `posts/get.sql` are `queries::users::get` and `queries::posts::get`.

In one file, each Postgres enum type is declared once, in a module named after its schema, so every query's value of it is the same type:

```rust
let role: queries::public::UserRole = ada.role;
let same: queries::UserRole = role; // the public schema's, also at the top
```

### CI

Generate again in CI, against its database, and fail when a file changed:

```sh
reylo generate rust-sqlx && git diff --exit-code
```

A `.sql` file edited after its module was written fails to compile, with no database, until the module is written again.

### Build scripts

To commit nothing generated, write the modules in `build.rs` instead:

```rust title="build.rs"
fn main() {
    reylo_build::rust_sqlx()
        .input("src/queries")
        .out("queries.rs")
        .run();
}
```

```rust title="src/main.rs"
mod queries {
    include!(concat!(env!("OUT_DIR"), "/queries.rs"));
}
```

A build script writes only into Cargo's `OUT_DIR`, so this writes one file, and every build that changes a `.sql` file needs the database.

A statement the database refuses fails the build with Cargo's own error, at its file, line and column:

```text
error: app@0.1.0: src/queries/get_user.sql:1:12: column "nme" does not exist (42703)
error: build script logged errors
```
