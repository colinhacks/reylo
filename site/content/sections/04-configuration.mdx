## Configuration

Configure Reylo in a `.reylo.yaml` (or `.reylo.yml`) file beside `package.json`. Every key is optional:

```yaml title=".reylo.yaml"
# the dev database Reylo reads your schema from (the default)
direct_url: ${DATABASE_URL}
# the .env files Reylo reads (the default)
env: [.env.local, .env]
# an error for a parameter whose type cannot be inferred (the default)
strict_params: true
# a comment naming each query's file, for your database's monitoring (the default)
sqlcommenter: true
# the directory of Reylo's files: schema.sql, the migrations and its cache (the default)
dir: reylo
```

### `direct_url`

The dev database Reylo reads your schema from. It defaults to `DATABASE_URL`, and its scheme names the dialect:

```sh title=".env" tab="Postgres" tab-group="dialect"
# or postgresql://
DATABASE_URL=postgres://localhost:5432/app
```

```sh title=".env" tab="MySQL" tab-group="dialect"
# or mariadb://
DATABASE_URL=mysql://root@localhost:3306/app
```

```sh title=".env" tab="SQLite" tab-group="dialect"
# or sqlite:; the path starts at package.json
DATABASE_URL=file:./app.db
```

Point it at a direct connection, not a pooler: describing a query through a pooler in transaction mode, such as PgBouncer's, can fail. You can interpolate other variables from your environment to construct a connection string.

```yaml title=".reylo.yaml"
# the default is ${DATABASE_URL}
direct_url: postgres://${DB_USER}:${DB_PASSWORD}@${DB_HOST}:5432/app
```

To keep a password out of every file, `$(…)` runs a command, such as a password manager's or a cloud's token command, and puts what it prints in its place. Reylo runs it once per editor session or build, and again when the database refuses the login, as when a token expires.

```yaml title=".reylo.yaml"
# or $(aws rds generate-db-auth-token …) for a short-lived token
direct_url: postgres://app:$(op read op://dev/db/password)@db:5432/app
```

### `env`

The `.env` files Reylo reads, relative to `.reylo.yaml`. The first file that sets a variable wins, and the environment wins over every file.

```yaml title=".reylo.yaml"
# the default is [.env.local, .env]
env: [.env.development, .env]
```

### `strict_params`

A [parameter whose type cannot be inferred](#a-parameter-nothing-types) is an error that says to [cast it](#casts). Set `strict_params: false` to type it `unknown` instead.

```yaml title=".reylo.yaml"
# the default is true
strict_params: false
```

### `sqlcommenter`

Each query Reylo sends ends with a comment that names its file, in [sqlcommenter](https://google.github.io/sqlcommenter/)'s format, so database monitoring that reads it, such as Datadog's and PlanetScale's, groups your queries by file. The query's [`.sql`](#sql) leaves it out. Set `sqlcommenter: false` to leave it off what Reylo sends too.

```yaml title=".reylo.yaml"
# the default is true
sqlcommenter: false
```

```sql title="What Postgres receives for queries/get_user.sql, by default"
select id, name, email from users where id = $1::int /*file='queries%2Fget_user.sql'*/
```

### `dir`

The directory beside `.reylo.yaml` that holds Reylo's files: the `schema.sql`, `migrations/` and `reylo-lock.yaml` of [migrations](/migrations), which you commit, and its cache in `.cache/`, which keeps itself out of git.

```yaml title=".reylo.yaml"
# the default is reylo
dir: db
```

### `migrate`

Turns on [migrations](/migrations), and holds their settings:

```yaml title=".reylo.yaml"
migrate:
  # the database to migrate (the default is direct_url)
  url: ${DATABASE_URL}
  # a server for shadow databases, where the database's own refuses create database
  shadow_url: ${SHADOW_URL}
  # no lock, and migrations run by name (the default is linear: locked)
  history: loose
  # compare comments on tables and columns too (the default is true)
  strict_comments: true
  # a command run after reylo migrate apply --reset and wipe, such as a seed
  post: reylo run --file reylo/seed.sql
```
