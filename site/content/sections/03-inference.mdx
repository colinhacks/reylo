Reylo lets you use the full power of SQL, on Postgres, MySQL and SQLite.

## How it works [#how-it-works]

Your database does the typing.

Reylo has it prepare each statement without running it, and reads its catalog. Run `reylo analyze` on a file to see what it learns:

<Analyzed file="queries/is_verified.sql">

```sql schema
create table users (
  id int8 primary key,
  verified boolean not null
);
```

```sql
-- Whether a user has verified their email.
select verified from users where id = :id
```

</Analyzed>

| Field | What it holds |
| --- | --- |
| `file` | The file the statement was read from |
| `$schema` | The format's version, as the URL of its JSON Schema |
| `dialect` | The database, and its server's version |
| `sql` | The statement as the database runs it, with the database's own placeholders |
| `kind` | What the statement does: `select`, `insert`, `update`, `delete`, `merge` or `other` |
| `comment` | The comment before the statement |
| `params` | Each parameter's name and [type](/typedefs) |
| `result` | Each column's name and type, and the cardinality: how many rows the statement returns |
| `capabilities` | The tables the statement reads or writes |
| `diagnostics` | What the database reports where it refuses the statement |

Reylo caches each answer in [`reylo/.cache/`](/faq#faq-reylo-directory), keyed by a fingerprint of the schema, so the next check after a migration sees the new schema.

## Primitives [#primitives]

Each SQL type has one TypeScript type, the same on every driver<Rust>, and one Rust type</Rust>.

In TypeScript, a 64-bit integer is a `bigint`, a decimal its exact text, and an instant its ISO 8601 text in UTC: no value is a `Date`. On Postgres, an instant always has six fraction digits, so two of them sort as strings. Pass back the text `.run()` returned, since a `Date` drops microseconds ([Dates and times](/postgres#dates-and-times)).

## Named parameters [#naming]

For convenience, there is some Reylo-specific syntax that can be used inside your `.sql` files. This syntax is transpiled into the idiomatic form for your database's dialect.

Name a parameter with a colon, and Reylo infers its type from where it's used:

<InferenceCard>

```sql file="inferred_rename_user.sql" dialect="all"
update users
set name = :name
where id = :id
```

</InferenceCard>

## Casts [#casts]

Where the query doesn't pin down a parameter's type, cast it. Reylo compiles the cast to each database's own:

<InferenceCard>

```sql file="inferred_search_users.sql" dialect="all"
select id, name
from users
where name like concat('%', :q::text, '%')
```

</InferenceCard>

<Details summary="When a parameter's type cannot be inferred" id="a-parameter-nothing-types">

It's an error that says to [cast it](#casts), unless [`allow_untyped_params: true`](/configuration#allow_untyped_params) types it `unknown`.

<DialectTabs>
<Dialect value="Postgres">

Postgres types a parameter from its context: a bare `select :x` is a `string`, and `select :x is null` is an error until a cast types it.

</Dialect>
<Dialect value="MySQL">

MySQL types every parameter: one that nothing else types, such as a bare `select :x`, is a `string`.

</Dialect>
<Dialect value="SQLite">

A bare `select :x`, or an argument of a table-valued function other than `json_each` and `json_tree`, has no type until a cast gives it one:

```sql
select length(:text::text) as n
```

A call to a function your application registers fails the type check, cast or not: Reylo prepares the statement in its own SQLite, which lacks it ("no such function"). Apply that function in TypeScript instead.

</Dialect>
</DialectTabs>

</Details>

## Left joins

A left join makes the joined table's columns nullable:

<InferenceCard>

```sql file="inferred_user_titles.sql" dialect="all"
select u.name, p.title
from users u
left join posts p on p.user_id = u.id
where u.id = :user_id::int
```

</InferenceCard>

A test in the `where` that fails on null, like a comparison, makes the whole joined row non-null:

<InferenceCard>

```sql file="inferred_published_titles.sql" dialect="all"
select u.name, p.title
from users u
left join posts p on p.user_id = u.id
where p.published_at > :since
```

</InferenceCard>

## Computed columns

Reylo infers which computed columns can never be null:

<InferenceCard>

```sql file="inferred_user_flags.sql" dialect="all"
select u.name,
  coalesce(u.email, '') as email,
  exists (select 1 from posts p where p.user_id = u.id) as has_posts
from users u
where u.role = :role
```

</InferenceCard>

## Nullable parameters

To accept null, cast a parameter to `nullable(…)`. Leaving it out passes `null`:

<InferenceCard>

```sql file="inferred_posts_by_user.sql" dialect="all"
select id, title
from posts
where user_id = coalesce(:user_id::nullable(int), user_id)
```

</InferenceCard>

A parameter written as it is to a column that may hold null, as `:published_at` is to `posts.published_at`, takes null too, and may be left out as well. Any other parameter takes no null: if one gets `null`, or is left out, `.run()` throws before the query runs, since the result's types rely on its value. A JSON parameter there takes `null` as JSON's `null`, which a `not null` JSON column holds; cast it to `nullable(…)` to pass SQL's `NULL` instead.

## Dynamic sorting

To pick the sort order at run time, order by a `case` on a parameter:

<InferenceCard>

```sql file="sort_users.sql" dialect="all"
-- a parameter appears once, so one read twice comes from a with
with input as (select :sort::text as sort)
select u.id, u.name
from users u, input
order by
  case when input.sort = 'name' then u.name end,
  case when input.sort = 'newest' then u.created_at end desc,
  u.id
```

</InferenceCard>

## Dynamic filtering

To filter a list by a form's values, pass them as one [JSON parameter](#typed-json). Its schema says what each filter takes and what it defaults to, and Reylo checks it before the query runs:

<InferenceCard>

```sql file="search_posts.sql" dialect="postgres"
with input as (
  select f ->> 'q' as q, (f ->> 'author_id')::int as author_id, f ->> 'status' as status, f ->> 'sort' as sort
  from (select :filters::jsonb('{
    "type": "object",
    "properties": {
      "q": { "type": "string", "maxLength": 100, "default": "" },
      "author_id": { "type": "integer" },
      "status": { "enum": ["published", "draft", "all"], "default": "all" },
      "sort": { "enum": ["newest", "oldest", "title"], "default": "newest" }
    },
    "additionalProperties": false
  }') as f)
)
select p.id, p.title, u.name as author
from posts p
join users u on u.id = p.user_id
cross join input
where p.title like concat('%', input.q, '%')
  and (input.author_id is null or p.user_id = input.author_id)
  and case input.status
    when 'published' then p.published_at is not null
    when 'draft' then p.published_at is null
    else true
  end
order by
  case when input.sort = 'title' then p.title end,
  case when input.sort = 'oldest' then p.id end,
  p.id desc
```

```sql file="search_posts.sql" dialect="mysql"
with input as (
  select f ->> '$.q' as q, f ->> '$.author_id' as author_id, f ->> '$.status' as status, f ->> '$.sort' as sort
  from (select :filters::json('{
    "type": "object",
    "properties": {
      "q": { "type": "string", "maxLength": 100, "default": "" },
      "author_id": { "type": "integer" },
      "status": { "enum": ["published", "draft", "all"], "default": "all" },
      "sort": { "enum": ["newest", "oldest", "title"], "default": "newest" }
    },
    "additionalProperties": false
  }') as f) as f
)
select p.id, p.title, u.name as author
from posts p
join users u on u.id = p.user_id
cross join input
where p.title like concat('%', input.q, '%')
  and (input.author_id is null or p.user_id = input.author_id)
  and case input.status
    when 'published' then p.published_at is not null
    when 'draft' then p.published_at is null
    else true
  end
order by
  case when input.sort = 'title' then p.title end,
  case when input.sort = 'oldest' then p.id end,
  p.id desc
```

```sql file="search_posts.sql" dialect="sqlite"
with input as (
  select f ->> '$.q' as q, f ->> '$.author_id' as author_id, f ->> '$.status' as status, f ->> '$.sort' as sort

    "type": "object",
    "properties": {
      "q": { "type": "string", "maxLength": 100, "default": "" },
      "author_id": { "type": "integer" },
      "status": { "enum": ["published", "draft", "all"], "default": "all" },

  case when input.sort = 'title' then p.title end,

```

</InferenceCard>

A filter left out takes its default, and one with none, like the author, is null, which turns it off:

```ts twoslash
declare const request: Request;
// ---cut---
import searchPosts from "./search_posts.sql";

// POST /posts/search with { "q": "sql", "status": "draft" }
const posts = await searchPosts.run(db, { filters: await request.json() });
```

Read with `->>`, each filter is a value the database can plan with, so on Postgres and MySQL a filter left out drops out of the plan and one given, like the author, can use an index.

<Details summary="Which filters use an index, in each dialect" id="filter-indexes">

- **Postgres** plans each run with its values on pg and PGlite. On postgres.js and Bun.sql, which prepare each statement once per connection, it can switch to one plan for every value after five runs, which reads the whole table; create the client with `connection: { plan_cache_mode: "force_custom_plan" }` to keep planning each run with its values. The same filter read from `jsonb_to_record` reads the whole table under every plan.
- **MySQL** plans each run with its values. The same filter read from `json_table` reads the whole table.
- **SQLite** plans a statement before its values are bound, so a filter that may be left out reads every row.

</Details>

## Unique keys

Reylo infers each query's cardinality, how many rows it returns. A query that matches a unique key returns one row or null:

<InferenceCard>

```sql schema dialect="postgres"
create table users (
  id serial primary key,
  name text not null,
  email text unique
);
```

```sql schema dialect="mysql"
create table users (
  id int auto_increment primary key,
  name text not null,
  email varchar(255) unique
);
```

```sql schema dialect="sqlite"
create table users (
  id integer primary key,
  name text not null,
  email text unique
) strict;
```

```sql file="inferred_user_by_email.sql" dialect="all"
select id, name
from users
where email = :email::text
```

</InferenceCard>

<Details summary="Which matches count as a key, in each dialect" id="key-matches">

<DialectTabs>
<Dialect value="Postgres">

Also a key match:

- a join on the joined table's key
- a unique index on an expression or with a `where`
- a `distinct` or `group by` over values the `where` pins
- a subquery, a `with` query or a view that keeps a key

</Dialect>
<Dialect value="MySQL">

Also a key match:

- a join on the joined table's numeric key
- a `distinct` or `group by` over values the `where` pins
- a derived table, a `with` query or a view that keeps a key

A unique index on an expression gives `many`.

</Dialect>
<Dialect value="SQLite">

Also a key match:

- a join on the joined table's key
- a `distinct` or `group by` over values the `where` pins
- a subquery, a `with` query or a view that keeps a key

A unique index on an expression or with a `where` gives `many`.

</Dialect>
</DialectTabs>

</Details>

At run time, `.run()` throws rather than return a row count its type rules out.

## Aggregates

An aggregate without a group by returns exactly one row:

<InferenceCard>

```sql file="inferred_post_count.sql" dialect="postgres"
select count(*)::int as posts
from posts
where user_id = :user_id::int
```

```sql file="inferred_post_count.sql" dialect="mysql"
select count(*) as posts
from posts
where user_id = :user_id::int
```

```sql file="inferred_post_count.sql" dialect="sqlite"
select count(*) as posts
from posts
where user_id = :user_id::int
```

</InferenceCard>

A rollup adds a row for the total, whose grouped column is null:

<InferenceCard>

```sql file="rollups.sql" dialect="postgres" play="Rollups"
select user_id, count(*)::int as posts
from posts
group by rollup (user_id)
order by user_id
```

```sql file="rollups.sql" dialect="mysql"
select user_id, count(*) as posts
from posts
group by user_id with rollup
order by user_id
```

</InferenceCard>

## Single values [#values]

A column with no name returns its values instead of rows:

<InferenceCard>

```sql file="post_total.sql" dialect="postgres"
select count(*)::int
from posts
where user_id = :user_id::int
```

```sql file="post_total.sql" dialect="mysql"
select count(*)
from posts
where user_id = :user_id::int
```

```sql file="post_total.sql" dialect="sqlite"
select count(*)
from posts
where user_id = :user_id::int
```

</InferenceCard>

An expression with no `as` has no name of its own, only what your database makes up for it, which can differ by driver. Add an `as` to get rows back, as in the [query above](#aggregates). A column read as it is, like `select id`, already has a name and keeps its rows.

- Where such a value may be null and the query may also match no row, `null` stands for both. Name the column to tell them apart.
- Among several columns, a made-up name that isn't an identifier, like `count(*)` or `?column?`, is a type error. Name the column with `as`.

## Window functions

Reylo types each window function: a row number is never null, while `lag()` is null on the first row:

<InferenceCard>

```sql file="window_functions.sql" dialect="all"
select id, title,
  row_number() over (
    partition by user_id
    order by published_at
  ) as n,
  lag(title) over (order by id) as prev
from posts
```

</InferenceCard>

## Subqueries

Run unrelated subqueries side by side, in one query and one round trip. With no `from`, the query returns exactly one row, and `.run()` resolves to it:

<InferenceCard>

```sql file="dashboard.sql" dialect="postgres"
-- the latest posts
with recent as (select id, title from posts order by id desc limit :limit::int)
select
  (select count(*)::int from users) as user_count,
  (select count(*)::int from posts) as post_count,
  (
    select coalesce(jsonb_agg(jsonb_build_object(
      'id', r.id,
      'title', r.title
    )), '[]')
    from recent r
  ) as recent_posts
```

```sql file="dashboard.sql" dialect="mysql"
-- the latest posts
with recent as (select id, title from posts order by id desc limit :limit::int)
select
  (select count(*) from users) as user_count,
  (select count(*) from posts) as post_count,
  (
    select coalesce(json_arrayagg(json_object(
      'id', r.id,
      'title', r.title
    )), json_array())
    from recent r
  ) as recent_posts
```

```sql file="dashboard.sql" dialect="sqlite"
-- the latest posts
with recent as (select id, title from posts order by id desc limit :limit::int)
select
  (select count(*) from users) as user_count,
  (select count(*) from posts) as post_count,
  (
    select json_group_array(json_object(
      'id', r.id,
      'title', r.title
    ))
    from recent r
  ) as recent_posts
```

</InferenceCard>

A lateral join runs its subquery once per row, here each user's latest post, or null for a user with none:

<InferenceCard>

```sql file="lateral_joins.sql" dialect="postgres" play="Lateral joins"
select u.name, p.title, p.published_at
from users u
left join lateral (
  select title, published_at
  from posts
  where user_id = u.id
  order by published_at desc nulls last
  limit 1
) p on true
```

```sql file="lateral_joins.sql" dialect="mysql"
select u.name, p.title, p.published_at
from users u
left join lateral (
  select title, published_at
  from posts
  where user_id = u.id
  order by published_at desc
  limit 1
) p on true
```

</InferenceCard>

## Returning rows [#returning-inserts]

## Nested fetching

Fetch each row's related rows with a subquery. Postgres collects them into an array of rows, MySQL and SQLite into JSON, and Reylo types every field:

<InferenceCard>

```sql file="users_with_posts.sql" dialect="postgres"
select u.id, u.name,
  -- every post, as an array
  array(
    select p from (
      select id, title from posts where user_id = u.id order by id
    ) p
  ) as posts,
  -- the latest post, or null
  (
    select p from (
      select id, title from posts
      where user_id = u.id
      order by published_at desc nulls last
      limit 1
    ) p
  ) as latest_post
from users u
where u.id = :id::int
```

```sql file="users_with_posts.sql" dialect="mysql"
select u.id, u.name,
  -- every post, as an array
  (
    select coalesce(json_arrayagg(json_object(
      'id', p.id,
      'title', p.title
    )), json_array())
    from posts p
    where p.user_id = u.id
  ) as posts,
  -- the latest post, or null
  (
    select json_object('id', p.id, 'title', p.title)
    from posts p
    where p.user_id = u.id
    order by p.published_at desc
    limit 1
  ) as latest_post
from users u
where u.id = :id::int
```

```sql file="users_with_posts.sql" dialect="sqlite"
select u.id, u.name,
  -- every post, as an array
  (
    select json_group_array(json_object(
      'id', p.id,
      'title', p.title
    ))
    from posts p
    where p.user_id = u.id
  ) as posts,
  -- the latest post, or null
  (
    select json_object('id', p.id, 'title', p.title)
    from posts p
    where p.user_id = u.id
    order by p.published_at desc nulls last
    limit 1
  ) as latest_post
from users u
where u.id = :id::int
```

</InferenceCard>

On Postgres, each field of an array of rows is read as a column is, so a `bigint` stays exact. [Inside JSON, values can differ](/postgres#json). JSON is still the smaller result when rows nest three levels deep and hold JSON documents, since a row's text escapes the quotes of what it holds at each level:

<InferenceCard>

```sql file="users_with_posts_json.sql" dialect="postgres"
select u.id,
  (
    select coalesce(jsonb_agg(p), '[]')
    from (select id, title from posts where user_id = u.id order by id) p
  ) as posts
from users u
```

</InferenceCard>

## Nested inserts

Users with their posts, in one parameter. The posts find their user by `email`, a unique key.

<DialectTabs>
<Dialect value="Postgres">

Postgres writes both tables in one statement: a `with` inserts the users, and the statement inserts the posts:

<InferenceCard>

```sql file="create_users_with_posts.sql" dialect="postgres"
with input as (
  select :users::jsonb('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "email": { "type": "string", "format": "email" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "string" } },
            "required": ["title"]
          }
        }
      },
      "required": ["name", "email", "posts"]
    }
  }') as users
),
new_users as (
  insert into users (name, email)
  select u.name, u.email
  from input, jsonb_to_recordset(input.users) as u(name text, email text)
  returning id, email
)
insert into posts (user_id, title)
select n.id, p.title
from input
cross join jsonb_to_recordset(input.users) as u(email text, posts jsonb)
join new_users n on n.email = u.email
cross join jsonb_to_recordset(u.posts) as p(title text)
```

</InferenceCard>

</Dialect>
