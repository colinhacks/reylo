## Inference

Reylo lets you use the full power of SQL provided by your database. Postgres, SQLite, and MySQL are all supported.

Reylo is a [content mapper](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/#content-mappers), the kind of plugin [TypeScript 7.1](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/) introduced for files that aren't TypeScript. Whenever the type checker meets a `.sql` import, in `tsc` or in your editor, it hands Reylo the file and takes back the module's types.

<HowItWorksDiagram />

To type a query, Reylo has your live database prepare it, without running it, and reads the catalog. From the answer, it learns:

- the parameter types
- the column types
- nullability, from `NOT NULL` and outer joins
- the cardinality, from keys, aggregates, `limit 1` and `returning`
- each column's comment (`comment on column` on Postgres, `comment '…'` on MySQL), which your editor shows on hover over a field that reads the column

<Details summary="The TypeScript type of each SQL type, in each dialect" id="data-types">

Reylo decodes its own queries' values itself, so every driver gives the same types. A 64-bit integer is a `bigint`, a decimal its exact text, and an instant its ISO 8601 text in UTC: no value is a `Date`.

At run time, the [preload](#setup-node) or a bundler [plugin](#plugins) turns the same file into a module that runs the query through your driver.

Reylo caches each answer in [`.reylo/`](#faq-reylo-directory), keyed by a fingerprint of the schema, so after a migration the next type check sees the new schema: a dropped column fails in the `.sql` file that names it, and in the code that reads it.

<Details summary="Where each type comes from, in each dialect" id="sources">

<DialectTabs>
<Dialect value="Postgres">

Reylo sends the query to the live database [prepared](https://www.postgresql.org/docs/current/sql-prepare.html) and reads back the database's own type information on its parameters and return type. This information is cross-referenced against the schema catalog, enabling high-fidelity type inference for any query.

| What | Where it comes from |
| --- | --- |
| Parameter types | the server's description of the prepared statement |
| Column types | the server's description; an enum as its labels, a domain as its base type, a JSON column as what its JSON Schema `CHECK` admits |
| Nullability | the catalog's `NOT NULL`, outer joins, the expressions |
| Cardinality | primary and unique keys, aggregates, `limit 1`, `returning` |
| Nested JSON | built with `jsonb_build_object`, `jsonb_agg` or `to_jsonb` of a row, typed from their arguments |

</Dialect>
<Dialect value="MySQL">

Reylo sends the query to the live database [prepared](https://dev.mysql.com/doc/refman/8.4/en/sql-prepared-statements.html) and reads back the database's own type information on its parameters and return type.

Reylo adds which parameters may be null, the row count, and the shape of JSON the query builds.

| What | Where it comes from |
| --- | --- |
| Parameter types | the prepared statement's metadata; whether one may be null, from the statement, as on Postgres |
| Column types | the prepared statement's metadata; a JSON column read from its table as what its JSON Schema `CHECK` admits |
| Nullability | the server's `NOT NULL` flag |
| Cardinality | primary and unique keys, aggregates; a write is `void` |
| Nested JSON | built with `json_object` and `json_arrayagg`, typed from their arguments |

</Dialect>
<Dialect value="SQLite">

Reylo reads the schema from the database file and [prepares](https://sqlite.org/c3ref/prepare.html) the query in its own copy of SQLite, which reports where each column and parameter comes from.

| What | Where it comes from |
| --- | --- |
| Parameter types | where SQLite places the parameter: a comparison with a column, an element of a row value, an `insert` or `update` column, a `cast`, `limit` and `offset` |
| Column types | the declared type's affinity |
| Nullability | the table's `NOT NULL`, outer joins, Reylo's table of SQLite's built-in functions |
| Cardinality | unique indexes and `integer primary key` |
| Nested JSON | built with `json_object` and `json_group_array`, typed from their arguments |

</Dialect>
</DialectTabs>

</Details>


### Named parameters [#naming]

For convenience, there is some Reylo-specific syntax that can be used inside your `.sql` files. This syntax is transpiled into the idiomatic form for your database's dialect.

Name a parameter with a colon, and Reylo infers its type from where it's used:

<Inferred>

```sql file="inferred_rename_user.sql" dialect="all"
update users
set name = :name
where id = :id
```

</Inferred>

### Casts [#casts]

Where the query doesn't pin down a parameter's type, cast it. Reylo compiles the cast to each database's own:

<Inferred>

```sql file="inferred_search_users.sql" dialect="all"
select id, name
from users
where name like concat('%', :q::text, '%')
```

</Inferred>

<Details summary="When a parameter's type cannot be inferred" id="a-parameter-nothing-types">

It's an error that says to [cast it](#casts), unless [`strict_params: false`](#strict_params) types it `unknown`.

<DialectTabs>
<Dialect value="Postgres">

Postgres types a parameter from its context: a bare `select :x` is a `string`, and `select :x is null` is an error until a cast types it.

</Dialect>
<Dialect value="MySQL">

MySQL types every parameter: one that nothing else types, such as a bare `select :x`, is a `string`.

</Dialect>
<Dialect value="SQLite">

A bare `select :x`, or an argument of a table-valued function other than `json_each` and `json_tree`, has no type until a cast gives it one:

```sql
select length(:text::text) as n
```

A call to a function your application registers fails the type check, cast or not: Reylo prepares the statement in its own SQLite, which lacks it ("no such function"). Apply that function in TypeScript instead.

</Dialect>
</DialectTabs>

</Details>

### Left joins

A left join makes the joined table's columns nullable:

<Inferred>

```sql file="inferred_user_titles.sql" dialect="all"
select u.name, p.title
from users u
left join posts p on p.user_id = u.id
```

</Inferred>

A null check on one joined column makes the whole joined row non-null:

<Inferred>

```sql file="inferred_published_titles.sql" dialect="all"
select u.name, p.title
from users u
left join posts p on p.user_id = u.id
where p.published_at is not null
```

</Inferred>

### Computed columns

Reylo infers which computed columns can never be null:

<Inferred>

```sql file="inferred_user_flags.sql" dialect="all"
select u.name,
  coalesce(u.email, '') as email,
  exists (select 1 from posts p where p.user_id = u.id) as has_posts
from users u
```

</Inferred>

### Nullable parameters

To accept null, wrap a parameter in coalesce:

<Inferred>

```sql file="inferred_posts_by_user.sql" dialect="all"
select id, title
from posts
where user_id = coalesce(:user_id::int, user_id)
```

</Inferred>

A parameter written as it is to a column that may hold null, as in `insert into posts (published_at) values (:published_at)`, takes null too. Any other parameter takes no null: if one gets `null`, or is left out, `.run()` throws before the query runs, since the result's types rely on its value.

### Dynamic sorting

To pick the sort order at run time, order by a `case` on a parameter:

<Inferred>

```sql file="sort_users.sql" dialect="all"
-- a parameter appears once, so one read twice comes from a with
with input as (select :sort::text as sort)
select u.id, u.name
from users u, input
order by
  case when input.sort = 'name' then u.name end,
  case when input.sort = 'newest' then u.created_at end desc,
  u.id
```

</Inferred>

### Dynamic filtering

To filter a list by whatever the page's URL holds, declare every parameter up front in a `with`, each coalesced to the value that matches every row. A filter with no such value, like the author, coalesces to null:

<Inferred>

```sql file="search_posts.sql" dialect="all"
with input as (
  select
    coalesce(:q::text, '') as q,
    coalesce(:author_id::int, null) as author_id,
    coalesce(:status::text, 'all') as status,
    coalesce(:sort::text, 'newest') as sort
)
select p.id, p.title, u.name as author
from posts p
join users u on u.id = p.user_id
cross join input
where p.title like concat('%', input.q, '%')
  and (input.author_id is null or p.user_id = input.author_id)
  and case input.status
    when 'published' then p.published_at is not null
    when 'draft' then p.published_at is null
    else true
  end
order by
  case when input.sort = 'title' then p.title end,
  case when input.sort = 'oldest' then p.id end,
  p.id desc
```

</Inferred>

A search param missing from the URL is null, which turns its filter off:

```ts twoslash
declare const request: Request;
// ---cut---
import searchPosts from "./search_posts.sql";

// /posts?q=sql&status=draft
const url = new URL(request.url);
const author = url.searchParams.get("author");

const posts = await searchPosts.run(db, {
  q: url.searchParams.get("q"),
  author_id: author === null ? null : Number(author),
  status: url.searchParams.get("status"),
  sort: url.searchParams.get("sort"),
});
```

### Unique keys

Reylo infers each query's cardinality, how many rows it returns. A query that matches a unique key returns one row or null:

<Inferred>

```sql schema dialect="postgres"
create table users (
  id serial primary key,
  name text not null,
  email text unique
);
```

```sql schema dialect="mysql"
create table users (
  id int auto_increment primary key,
  name text not null,
  email varchar(255) unique
);
```

```sql schema dialect="sqlite"
create table users (
  id integer primary key,
  name text not null,
  email text unique
) strict;
```

```sql file="inferred_user_by_email.sql" dialect="all"
select id, name
from users
where email = :email::text
```

</Inferred>

<Details summary="Which matches count as a key, in each dialect" id="key-matches">

<DialectTabs>
<Dialect value="Postgres">

Also a key match:

- a join on the joined table's key
- a unique index on an expression or with a `where`
- a `distinct` or `group by` over values the `where` pins

</Dialect>
<Dialect value="MySQL">

Only a match on one table's own primary or unique key counts, with or without a `distinct` or `group by`. These give `many`:

- a joined table's key
- a unique index on an expression
- a `distinct` or `group by` over pinned values that are not a key

</Dialect>
<Dialect value="SQLite">

Also a key match:

- a join on the joined table's key
- a `distinct` or `group by` over values the `where` pins

A unique index on an expression or with a `where` gives `many`.

</Dialect>
</DialectTabs>

</Details>

At run time, `.run()` throws rather than return a row count its type rules out.

### Subqueries

Run unrelated subqueries side by side, in one query and one round trip. With no `from`, the query returns exactly one row, and `.run()` resolves to it:

<Inferred>

```sql file="dashboard.sql" dialect="postgres"
-- the five latest posts
with recent as (select id, title from posts order by id desc limit 5)
select
  (select count(*)::int from users) as user_count,
  (select count(*)::int from posts) as post_count,
  (
    select coalesce(jsonb_agg(jsonb_build_object(
      'id', r.id,
      'title', r.title
    )), '[]')
    from recent r
  ) as recent_posts
```

```sql file="dashboard.sql" dialect="mysql"
-- the five latest posts
with recent as (select id, title from posts order by id desc limit 5)
select
  (select count(*) from users) as user_count,
  (select count(*) from posts) as post_count,
  (
    select coalesce(json_arrayagg(json_object(
      'id', r.id,
      'title', r.title
    )), json_array())
    from recent r
  ) as recent_posts
```

```sql file="dashboard.sql" dialect="sqlite"
-- the five latest posts
with recent as (select id, title from posts order by id desc limit 5)
select
  (select count(*) from users) as user_count,
  (select count(*) from posts) as post_count,
  (
    select json_group_array(json_object(
      'id', r.id,
      'title', r.title
    ))
    from recent r
  ) as recent_posts
```

</Inferred>

### Nested fetching

Fetch each row's related rows with an aggregated subquery: it collects them into JSON, and Reylo types every field inside it:

<Inferred>

```sql file="users_with_posts.sql" dialect="postgres"
select u.id, u.name,
  -- every post, as an array
  (
    select coalesce(jsonb_agg(jsonb_build_object(
      'id', p.id,
      'title', p.title
    ) order by p.id), '[]')
    from posts p
    where p.user_id = u.id
  ) as posts,
  -- the latest post, or null
  (
    select jsonb_build_object('id', p.id, 'title', p.title)
    from posts p
    where p.user_id = u.id
    order by p.published_at desc nulls last
    limit 1
  ) as latest_post
from users u
```

```sql file="users_with_posts.sql" dialect="mysql"
select u.id, u.name,
  -- every post, as an array
  (
    select coalesce(json_arrayagg(json_object(
      'id', p.id,
      'title', p.title
    )), json_array())
    from posts p
    where p.user_id = u.id
  ) as posts,
  -- the latest post, or null
  (
    select json_object('id', p.id, 'title', p.title)
    from posts p
    where p.user_id = u.id
    order by p.published_at desc
    limit 1
  ) as latest_post
from users u
```

```sql file="users_with_posts.sql" dialect="sqlite"
select u.id, u.name,
  -- every post, as an array
  (
    select json_group_array(json_object(
      'id', p.id,
      'title', p.title
    ))
    from posts p
    where p.user_id = u.id
  ) as posts,
  -- the latest post, or null

    select json_object('id', p.id, 'title', p.title)
    from posts p
    where p.user_id = u.id

from users u
```

</Inferred>

### JSON Schema [#json-schema]

Declare a JSON Schema, and Reylo types the JSON it describes. A JSON column declares one in a check constraint:

<Inferred>

```sql schema dialect="postgres"
create extension if not exists pg_jsonschema;

create table events (
  id serial primary key,
  payload jsonb not null check (jsonb_matches_schema('{
    "type": "object",
    "properties": {
      "x": { "type": "integer" },
      "y": { "type": "integer" }
    },
    "required": ["x", "y"],
    "additionalProperties": false
  }', payload))
);
```

```sql schema dialect="mysql"
create table events (
  id int auto_increment primary key,
  payload json not null check (json_schema_valid('{
    "type": "object",
    "properties": {
      "x": { "type": "integer" },
      "y": { "type": "integer" }
    },
    "required": ["x", "y"],
    "additionalProperties": false
  }', payload))
);
```

```sql file="inferred_event_payloads.sql" dialect="postgres"
select id, payload
from events
```

```sql file="inferred_event_payloads.sql" dialect="mysql"
select id, payload
from events
```

</Inferred>

### JSON parameters [#typed-json]

A JSON parameter declares its schema in its cast to `json` or `jsonb`, and Reylo infers the parameter's type from it:

<Inferred>

```sql file="record_click.sql" dialect="all"
insert into events (kind, payload)
values ('click', :payload::json('{
  "type": "object",
  "properties": {
    "x": { "type": "integer" },
    "y": { "type": "integer" },
    "button": { "type": "string", "enum": ["left", "right"] }
  },
  "required": ["x", "y"]
}'))
```

</Inferred>

Reylo also checks the value against the schema when you call `.run()`:

```ts twoslash
import recordClick from "./record_click.sql";

// type-checks, but .run() rejects it: x must be an integer
await recordClick.run(db, { payload: { x: 1.5, y: 20 } });
```

A schema can nest objects and arrays, and check every value in them:

<Inferred>

```sql file="record_order.sql" dialect="all"
insert into events (kind, payload)
values ('order', :order::json('{
  "type": "object",
  "properties": {
    "customer": { "type": "string", "format": "email" },
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "properties": {
          "sku": { "type": "string", "pattern": "^[A-Z]{3}-[0-9]{4}$" },
          "qty": { "type": "integer", "minimum": 1 }
        },
        "required": ["sku", "qty"]
      }
    },
    "shipping": { "enum": ["standard", "express"] }
  },
  "required": ["customer", "items"]
}'))
```

</Inferred>

A JSON parameter written to a schema-checked column takes that schema as its type, with no cast:

<Inferred>

```sql schema dialect="postgres"
create extension if not exists pg_jsonschema;

create table events (
  id serial primary key,
  payload jsonb not null check (jsonb_matches_schema('{
    "type": "object",
    "properties": {
      "x": { "type": "integer" },
      "y": { "type": "integer" }
    },
    "required": ["x", "y"],
    "additionalProperties": false
  }', payload))
);
```

```sql file="inferred_record_event.sql" dialect="postgres"
insert into events (payload)
values (:payload)
```

</Inferred>

### Filtering by a list

Pass the list as one parameter:

<Inferred>

```sql file="users_by_ids.sql" dialect="postgres"
select id, name from users where id = any(:ids::int[])
```

```sql file="users_by_ids.sql" dialect="mysql"
-- MySQL has no array type, so the list is a JSON parameter
with input as (
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
)
select id, name from users
where id in (
  select j.id from input, json_table(input.ids, '$[*]' columns (
    id int path '$'
  )) as j
)
```

```sql file="users_by_ids.sql" dialect="sqlite"
-- SQLite has no array type, so the list is a JSON parameter
with input as (
  select :ids::json('{
    "type": "array",
    "items": { "type": "integer" }
  }') as ids
)
select id, name from users
where id in (select j.value from input, json_each(input.ids) as j)
```

</Inferred>

### Bulk inserts

Pass the rows as one [JSON parameter](#typed-json): the schema in its cast types them, and Reylo checks every row before the statement runs:

<Inferred>

```sql file="create_users.sql" dialect="postgres"
with input as (
  select :users::jsonb('{
    "type": "array",
    "maxItems": 1000,
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "email": { "type": ["string", "null"], "format": "email" }
      },
      "required": ["name"]
    }
  }') as users
)
insert into users (name, email)
select u.name, u.email
from input, jsonb_to_recordset(input.users) as u(name text, email text)
returning id
```


### Nested inserts

Users with their posts, in one parameter. The posts find their user by `email`, a unique key.

<DialectTabs>
<Dialect value="Postgres">

Postgres writes both tables in one statement: a `with` inserts the users, and the statement inserts the posts:

<Inferred>

```sql file="create_users_with_posts.sql" dialect="postgres"
with input as (
  select :users::jsonb('{
    "type": "array",
    "items": {
      "type": "object",
      "properties": {
        "name": { "type": "string" },
        "email": { "type": "string", "format": "email" },
        "posts": {
          "type": "array",
          "items": {
            "type": "object",
            "properties": { "title": { "type": "string" } },
            "required": ["title"]
          }
        }
      },
      "required": ["name", "email", "posts"]
    }
  }') as users
),
new_users as (
  insert into users (name, email)
  select u.name, u.email
  from input, jsonb_to_recordset(input.users) as u(name text, email text)
  returning id, email
)
insert into posts (user_id, title)
select n.id, p.title
from input
cross join jsonb_to_recordset(input.users) as u(email text, posts jsonb)
join new_users n on n.email = u.email
cross join jsonb_to_recordset(u.posts) as p(title text)
```

</Inferred>

</Dialect>
<Dialect value="MySQL">

On MySQL, a `with` only reads, so the users and the posts are two statements, run in one transaction:

### Discriminated unions with `oneOf` [#oneof]

A `oneOf` in a schema is a [union](#unions). Give each member a key with one value, and it is a discriminated union, which TypeScript narrows on that key:

<Inferred>

```sql schema dialect="postgres"
create extension if not exists pg_jsonschema;

create table events (
  id serial primary key,
  payload jsonb not null check (jsonb_matches_schema('{
    "type": "object",
    "oneOf": [{
      "properties": {
        "kind": { "const": "click" },
        "x": { "type": "integer" },
        "y": { "type": "integer" }
      },
      "required": ["kind", "x", "y"],
      "additionalProperties": false
    }, {
      "properties": {
        "kind": { "const": "key" },
        "code": { "type": "string" }
      },
      "required": ["kind", "code"],
      "additionalProperties": false
    }]
  }', payload))
);
```

```sql schema dialect="mysql"
-- MySQL checks JSON Schema draft 4, which has no const

      "properties": {
        "kind": { "enum": ["click"] },
```
