# Working on Reylo

This guide is for coding agents and contributors working in this repository: what is where, how to set up, how to make the usual changes, and what the checks expect. Read it whole before a change.

Reylo types SQL from the database itself. A project imports a `.sql` file, and TypeScript 7.1's content mapper gives back its parameters, columns, nullability, nested JSON shapes and cardinality, read from the server's own analysis; nothing is declared by hand. The analysis is a Rust engine, built into one native program, the `reylo` binary, which connects to the database itself and which the npm package `reylo` runs, from the platform package its install holds.

A maintainer may keep local notes beside this file, which are never committed; when they are present, read them too, and where the two differ they win: @AGENTS.local.md

## What is where

| Path | What it is |
| --- | --- |
| `src/` | The npm package `reylo`, TypeScript: the content mapper, the run time (`.run()`, `.runSync()`, `.with()`), the bundler adapters, the preload `reylo/register`, the `reylo` command's launcher (`src/cli.ts`), which runs the binary, and `reylo play`, `analyze()`, which returns a statement's type descriptor (`src/analyze-api.ts`), and the lookup of the engine binary each analysis runs (`src/native.ts`) |
| `npm/` | The platform packages `@reylosql/engine-<platform>`: `platforms.json`, the eight platforms the `reylo` binary is built and published for (each one's `os`, `cpu`, `libc`, Rust target, the CI runner and container it is built on, and the runner or Linux images it is installed and run on), and `engine/README.md`, the README each carries. `scripts/build.ts` writes each into `dist/engine-<platform>/`; no binary is committed |
| `engine/` | The analysis engine, Rust: `core/`, shared by every database, and one crate per database, none depending on another, each implementing core's `Database` trait ([engine/README.md](./engine/README.md)). Built into one native program, the `reylo` binary (`cli/`: the engine every frontend talks to, `reylo analyze`, which prints each statement's type descriptor, and the migrations of `migrate/`), linked natively by the oracle, and for the docs site's playground to one WebAssembly component of Postgres's engine (`wasip2/`) |
| `spec/` | The type descriptor format, Reylo Type Defs (RTD), in preview until 1.0.0: what introspecting a statement returns (`StatementDescriptor`) and the type of each parameter and column, for every relational database. `typedefs.schema.json` is the format as a JSON Schema, its source of truth, whose `$id` is the URL reylo.dev serves it at and every descriptor names in `$schema`; `index.ts` is the same types in TypeScript and `site/public/typedefs/preview.json` the published copy, both generated from it by `nub run typedefs` (`spec/generate.ts`); `README.md` holds the rules every descriptor follows; `examples.ts` holds descriptors from each database, each with the schema and statement it describes, and `examples.json` the same examples as JSON, generated by `nub run typedefs` for the engine's tests. The engines answer with it: `engine/core/src/types.rs` is the same format in Rust, and the loader reads it. A living document, but a settled one: a change to it is a design decision, agreed with a maintainer before it is written |
| `oracle/` | The soundness oracle (`reylo-oracle`) and `oracle/cases/`, the regression suite for everything the engine infers |
| `rust/` | Reylo for Rust: `reylo`, the crate a project depends on; `reylo-macros`, the attribute `#[reylo::query("…")] mod name {}`; `reylo-build`, a statement's analysis (from the database or `reylo/.cache/`) as its module's items, the generator `reylo generate rust-sqlx` runs, and that generator for a build script; and the demos, each built only with its `live` feature ([rust/README.md](./rust/README.md)) |
| `tests/` | The loader's node tests; `tests/helpers.ts` holds what they share: the test databases and a database of a test's own on each, the drivers, a statement written by hand compiled by the engine's lexer (`handWritten`), which a query a test defines by hand passes, since the run time takes one without a compiled text as written, and the content mapper's and the language server's clients |
| `site/` | The docs site, reylo.dev: Vite, React Router and MDX; its design is docs-kit, copied into `site/docs-kit/` |
| `examples/` | One complete project per setup the docs describe, the models to copy when setting Reylo up elsewhere ([examples/README.md](./examples/README.md)); each README has the commands that check it, and CI runs the Node one on Windows |
| `lab/` | End-to-end check projects: one per dialect, the bundlers, Jest, Next.js, the drivers and the driver matrix, and `lab/compare`, which runs other SQL typing tools on the same queries for the docs' comparison |
| `skills/reylo/` | The agent skill for projects that use Reylo; not instructions for work here, but kept current with what users see |
| `scripts/build.ts` | `nub run build`: writes every publishable package to `dist/`, `reylo` and the platform package of this machine (`--binaries <dir>` packages all eight) |
| `.github/workflows/` | `test.yml` (CI on every push to `main` and pull request, and by hand on a branch), `windows.yml` (the type check on Windows, which `test.yml` runs on each push to `main` and each release), `binaries.yml` (each platform's binary built, installed and run on that platform, on a pull request that changes how it is built or found, and within each release; one platform's binary alone, by hand), `channels.yml` (the `reylo` command installed and run through every channel that does without npm: `site/public/install.sh` and `install.ps1`, which reylo.dev serves, the Homebrew formula and Scoop manifest `.github/scripts/channels.sh` writes, and the container image `.github/docker/Dockerfile` builds; on a pull request that changes one, after `binaries.yml`'s builds, and by hand on a release's assets), `release.yml` (the staged npm release, which a maintainer dispatches, and then the tap, the bucket and the image, `.github/scripts/channels-publish.sh`, and the Rust crates on crates.io through trusted publishing, `.github/scripts/crates-publish.sh`, which a crate's first version runs from a maintainer's machine), `pullfrog.yml` |

The live tests in these files skip without both test databases ([JavaScript](#javascript)). A change a user of Reylo would notice also updates the docs and the skill, `skills/reylo/SKILL.md`, in the same pull request.

The engine, crate by crate:

- **Postgres**, `engine/postgres/src/`: `postgres.rs` (the analysis, round by round), `infer.rs` (expression columns' types and nullability), `cardinality.rs` (how many rows a statement returns), `jsonshape.rs` (nested JSON shapes), `levels.rs` (which query an aggregate belongs to), `returning.rs`, `analyze.rs` (parse-tree facts: the statement's kind, locking, the tables it reads and writes, and which parameters may be null, as through `coalesce`), `pgtypes.rs` (the type registry: each catalog type as a type descriptor), `stack.rs` (how deeply a statement may nest), `extension.rs` (the handshake with a server-side extension), `bodies.rs` (a statement with the bodies of the SQL functions it calls in place, whose analysis narrows the statement's own). The parser is `pg_query` (libpg_query, Postgres 18), patched from `engine/postgres/vendor/` into `engine/postgres/.patched/pg_query` by the prepare step, which makes it the crate `reylo-pg-query`.
- **MySQL**, `engine/mysql/src/`: `mysql.rs` (the analysis over the server's prepare metadata), `mysql_types.rs` (the prepare's type codes, flags, lengths and decimals as type descriptors, a table's column narrowed by its definition), `mysql_nulls.rs` (what a WHERE implies is not null), `mysql_derived.rs` (derived tables and WITH queries), `mysql_shape.rs` (JSON constructors), `mysql_params.rs` (which parameters may be null). It reads statements with its own copy of `sqlparser` 0.63, cut to the statements it needs (`engine/mysql/vendor/sqlparser`, the crate `reylo-sqlparser`, whose README lists the changes).
- **SQLite**, `engine/sqlite/`: `src/sqlite.rs` (the analysis over SQLite's resolved tree, and its function tables), `src/sqlite_tree.rs` (the tree as `csrc/reylo_sqlite.c` serializes it), and `csrc/patch-sqlite.py` (the hooks the prepare step applies to the amalgamation).
- **Core**, `engine/core/src/`: `database.rs` (the `Database` trait each database implements), `types.rs` (the type descriptor format: each parameter's and column's type, and the `StatementDescriptor` an analysis projects to), `comment.rs` (a statement's leading comment), `shape.rs` (the nested-JSON vocabulary every database plans with), `lex.rs`, `config.rs`, `structured.rs` (`row(…)` and `rows(…)` parameters), `schema_type.rs` (a JSON Schema CHECK to a type), `schema.rs` (a type to JSON Schema), `api.rs` (the request protocol), `host.rs` (the answers a host gave and the needs the engine records), `fresh.rs` (the tables a statement reads and writes), `fingerprint.rs`.

The engine's core never opens a connection: it replays an analysis, names the statements to describe and the catalog queries to run, and its host answers them. The host the `reylo` binary carries is Rust too: `reylo engine <database>` serves its database's program (`engine/native/`), which opens the connection itself, through tokio-postgres, mysql_async or rusqlite, and answers the core's needs, while a host that holds a connection of its own drives the core's replay itself (`src/engine-core.ts`). Postgres is the reference dialect; the docs' page for each dialect (`site/content/docs/<database>.mdx`) states what it can and cannot type.

## Setup

### JavaScript

Prefer nub over `node`, `bun`, npm, npx, pnpm and yarn: `nub install`, `nub add`, `nub run <script>`, `nub <file>` to run a file, `nubx <tool>` for a local CLI, and `nub --node <file>` for strict, unaugmented Node. It keeps the existing lockfiles. CI uses nub 0.9.6 on Node 24.

- `nub install` at the root, then `nub run typecheck` (`tsc --noEmit --runExternalCode`, about a second) and `nub run test` (`node --test 'tests/**/*.test.ts'`, about a minute) are the loader's checks.
- CI fails on any skipped test: a run must end with `ℹ skipped 0`, and `nub run test 2>&1 | grep -E '^﹣|ℹ skipped'` lists each skip with its reason. `REYLO_TEST_PG` and `REYLO_TEST_MYSQL` name the test databases, and `REYLO_TEST_PG_TLS` a Postgres that takes TLS and a password, for the test of channel binding ([Test databases](#test-databases)); the Postgres tests of structured parameters and the schema fingerprint also need `lab/drivers` installed; the spec's pgvector example needs pgvector in the test Postgres; the Jest, Vitest and SQLite-driver tests need `lab/drivers` and `lab/jest` installed. The loader's tests run the engine binary, which `REYLO_ENGINE_PATH` names, else the newer of `target/release/reylo` and `target/debug/reylo`: build it first with `cargo build --release -p reylo-cli` ([Rust](#rust)). The full setup, as CI makes it, from the repository's root:

  ```sh
  (cd lab/drivers && nub install) && (cd lab/jest && nub install)
  ln -sfn ../../.. lab/jest/node_modules/reylo
  ```

  Every lab reaches the package through a link, `node_modules/reylo`, to the repository root, and through it the engine the checkout built. `nub install` in a lab removes the link, so make it again after one.
- `nub run build` writes `dist/reylo` (the run time, the entry points and the build-time half, no engine) and `dist/engine-<platform>` for this machine (the `reylo` binary, built with cargo; `--binary <file>` takes one already built), links the second into `dist/reylo/node_modules` where an install would put it, and refuses versions that disagree: `package.json`'s and the Cargo workspace's. The examples link `dist/reylo` with `link:`, not the sources, so run it before `nub install` in an example and again after any change to `src/` or the engine. Never turn those links into `file:` dependencies: nub 0.9.6 never refreshes a `file:` directory it has installed once, so the example would run a stale build.
- `reylo` finds the engine binary through `REYLO_ENGINE_PATH`, else the platform package its install holds, else the newer of a checkout's `target/release/reylo` and `target/debug/reylo` (`src/native.ts`), and refuses one of another version. The root's install holds no platform package, so a checkout runs its own build.
- `site/` has its own install: `nub install` there before building or serving it. Its playground runs Postgres's engine as a WebAssembly component, which no commit holds: `nub run build` and `nub run dev` there first put it in `site/.playground/` (`site/scripts/playground-engine.ts`), from the checkout's own build in `target/playground/postgres/` where `engine/build.sh` made one, else from the GitHub release of `package.json`'s version (a version with no release takes the newest that carries it, and says so). `REYLO_PLAYGROUND_RELEASES` names a directory or URL laid out as the releases are, `<tag>/<asset>`, to stand in for them.

### Rust

One Cargo workspace at the root covers `engine/core`, `engine/postgres`, `engine/sqlite`, `engine/mysql`, `engine/build-support`, `engine/native` (`reylo-engine`, which a Rust host links: each database's engine behind a feature, with the answers to its needs over `tokio-postgres`, `rusqlite` or `mysql_async`, and the engine's program: the connection, TLS and the engine's requests), `engine/migrate` (`reylo-migrate`: the migrations, their shadow databases, the schema comparator and the diff engine that plans a change, behind its `cli` feature, which `reylo-cli` turns on; without it, only deploy and status, on a connection a Rust app holds), `engine/cli` (`reylo-cli`, the `reylo` binary: `reylo engine <database>`, which serves the engine's program, `reylo analyze`, `reylo generate`, the migrations' commands and `reylo run`), `oracle/`, and the Rust crate's in `rust/`: one `Cargo.lock` and one `target/`. `rust-toolchain.toml` pins the Rust release every build uses, which rustup installs on the first cargo command. The published crates declare an older floor, the workspace's `rust-version` (the parser copies write theirs in their own manifests), which `.github/scripts/rust-package-check.sh` builds its projects on. A demo in `rust/` has its statements typed against a database as it compiles, so it builds only with its `live` feature, and a build of the workspace needs no database. The playground's component crate, `engine/wasip2`, is a workspace of its own, so that the tokio-postgres patch it builds with reaches no native build. Building it needs a rustup toolchain with the `wasm32-wasip2` target (`rustup target add wasm32-wasip2`; a distribution's `rustc` without it fails with "can't find crate for `std`"), wasi-sdk 34, named by `WASI_SDK_PATH` or unpacked under `engine/.wasi-sdk/`, and jco from the root's install.

```sh
engine/build.sh --prepare     # once per checkout, before any cargo command: cargo cannot resolve the workspace without it
cargo build --release -p reylo-cli   # the binary the loader's tests and the labs run
cargo test -p reylo-engine-core -p reylo-engine-postgres -p reylo-engine-sqlite -p reylo-engine-mysql -p reylo-engine -p reylo-migrate -p reylo-cli -p reylo-oracle -p reylo-build -p reylo --features reylo/mysql,reylo/sqlite
engine/build.sh               # the docs site's playground engine, into target/playground/postgres/
```

- The prepare step fetches `pg_query` and libpg_query at pinned commits, checks their SHA-256 and applies the patch in `engine/postgres/vendor/` into `engine/postgres/.patched/pg_query`, the crate `reylo-pg-query`, which the Postgres engine and the migrations depend on; it fetches the SQLite amalgamation into `engine/sqlite/.sqlite/` and applies the engine's hooks; and it fetches tokio-postgres from crates.io into `engine/wasip2/.patched/` and applies the patch beside it, which builds its runtime for wasip2.
- On macOS, bindgen needs the SDK: `export SDKROOT="$(xcrun --show-sdk-path)"`, then in a second `export`, `BINDGEN_EXTRA_CLANG_ARGS="-isysroot $SDKROOT"` (on one line the shell expands `$SDKROOT` before it is set, and bindgen fails with an opaque `libclang error`).
- `.cargo/config.toml` builds the SQLite that rusqlite bundles with the math, percentile and geopoly functions, so every native build reads a statement that calls them as the binary does.
- `reylo-migrate`'s and `reylo-cli`'s tests build schemas on the test servers `REYLO_TEST_PG` and `REYLO_TEST_MYSQL` name ([Test databases](#test-databases)), and skip each database whose variable is unset; SQLite's always run.
- No engine artifact is committed. CI builds the binary (`test.yml`'s binary job) and hands it to the loader's tests; the release builds it on each platform's own runner (`binaries.yml`, `.github/scripts/build-binary.sh`; Linux on glibc in a manylinux_2_28 container, so that it starts on glibc 2.28, which the build checks) and stages one `@reylosql/engine-<platform>` package per platform, which `reylo` lists as optional dependencies at its version. The release also builds the playground's component and attaches it to the GitHub release, which the docs site's build fetches.
- The playground's component is built without LTO: the depth a statement may nest was measured on that code, and LTO's larger frames spend more of the JavaScript engine's stack at the bound. The build writes no path of the machine that built it into the component.

### Test databases

The tests and the oracle create and drop databases, so point them only at throwaway servers, never at one whose data matters; the oracle refuses ports 5432 and 3306 outright. CI's servers, on ports clear of the defaults and below the ephemeral range (32768 and up on Linux, 49152 and up on macOS and Windows), where an outgoing connection made just before a server starts can hold its port:

```sh
docker run -d --name reylo-pg -p 25432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust pgvector/pgvector:pg18     # postgres://postgres@127.0.0.1:25432/postgres
docker run -d --name reylo-mysql -p 23306:3306 -e MYSQL_ALLOW_EMPTY_PASSWORD=yes mysql:8.4     # mysql://root@127.0.0.1:23306
docker run -d --name reylo-pg-tls -p 25434:5432 -e POSTGRES_PASSWORD=reylo postgres:18 -c ssl=on -c ssl_cert_file=/etc/ssl/certs/ssl-cert-snakeoil.pem -c ssl_key_file=/etc/ssl/private/ssl-cert-snakeoil.key     # postgres://postgres:reylo@127.0.0.1:25434/postgres, as REYLO_TEST_PG_TLS
```

- The Postgres is pgvector's image of Postgres 18, with the extension installed, for the spec's example of a `vector` column, which `tests/spec-examples.test.ts` skips on a server without it.
- With a local Postgres install instead: `oracle/cluster.sh start <its bin directory> <port>` makes a throwaway cluster under `/tmp` and prints its URL, and `oracle/cluster.sh stop <port>` deletes it. On macOS a postmaster started with no locale in its environment stops at once ("postmaster became multithreaded during startup"), so set `LANG=en_US.UTF-8` for it.
- The oracle's `json_schema_*` cases call five JSON Schema validator extensions in Postgres 18. `.github/scripts/json-schema-validators.sh` builds them against a Postgres install's `pg_config`, as the oracle job in `test.yml` does.
- The oracle's `pgvector_types` and `postgis_types` cases need pgvector and PostGIS in that Postgres 18: on Debian and Ubuntu, PGDG's `postgresql-18-pgvector` and `postgresql-18-postgis-3`, as the oracle job installs them; with Homebrew's `postgresql@18`, `brew install pgvector postgis`.
- CI's Postgres cluster for the oracle is made with `initdb -E UTF8 --locale=C`, so a case that depends on collation can differ on a cluster with another locale.
- MySQL 9.7 and later start with GTIDs on, which refuses the oracle's MyISAM and MEMORY writes: start them with `--gtid-mode=OFF --enforce-gtid-consistency=OFF`. The `mysql_*` cases are blessed on MySQL 8.4.
- The oldest versions the docs claim, Postgres 14 and MySQL 8.0.38, run in the oracle job on `main` and in each release, never on a pull request ([Checks](#checks)). To run them by hand: PGDG's `postgresql-14` with its `postgresql-14-pgvector` and `postgresql-14-postgis-3`, the validators built against its `pg_config`, and the cluster started with `-c jit=off`, since JIT compiles each of the engine's catalog queries for seconds; and `docker run -d -p 53380:3306 -e MYSQL_ALLOW_EMPTY_PASSWORD=yes mysql:8.0.38`. A statement that needs a newer version names it in its case's `min_version`, and a case whose MySQL 8.0 answers differ, rightly, holds them in `expected-8.0.txt`; never bless a case's `expected.txt` on an older server.

## Recipes

### An inference fix in the engine

Most merged pull requests are this shape (reylosql/reylo#10, reylosql/reylo#29, reylosql/reylo#33): the rule in `engine/<database>/src/` and a new oracle case.

1. Prepare the workspace ([Rust](#rust)), and start a Postgres 18 server, plus MySQL 8.4 for a MySQL rule.
2. Write the failing case first: add statements to the closest existing case in `oracle/cases/`, or make a new directory when none covers the construct, with `setup.sql` (the tables), one statement per `<statement>.sql`, and a file named `dialect` holding `mysql` or `sqlite` for those dialects (none for Postgres). Copy the layout of a neighbouring case.
3. Run it: `cargo run -q -p reylo-oracle -- --url <pg url> --mysql-url <mysql url> oracle/cases/<name>` (`ORACLE_URL` and `ORACLE_MYSQL_URL` can stand for the flags; a run needs the MySQL one only for a MySQL case). The oracle also replays each database's own test suite, read from a checkout at the version of what runs it, and holds what each statement returns against what the engine infers for it: `--replay postgres <checkout>/src/test/regress` (with `--url`), `--replay sqlite <checkout>/test`, and `--replay mysql --mysqld <path to mysqld> <checkout>/mysql-test/t` (on a server of its own); `oracle/src/replay/` says which version each reads. Each line of `expected.txt` is a statement's analysis: `<file>: <cardinality> (<parameters>) -> { <columns> }`, each type in the short notation `Type::short` prints (`engine/core/src/types.rs`), a `?` marking a nullable one.
4. Fix the rule, then `--bless` the case to write its `expected.txt`, and read that file's diff: each changed line is a type change the pull request claims.
5. Run the whole oracle as CI does, `--strict-coverage oracle/cases`: a fix often changes other cases' `expected.txt`, and each of those changes must be right too. Then the engine's tests, `cargo build --workspace --all-targets` with no warning, and `cargo build --release -p reylo-cli`.
6. Run the loader's checks (`nub run typecheck`, `nub run test` with both test databases) on that binary.
7. Where the dialect's docs page states the rule (`site/content/docs/<database>.mdx`), correct it in the same pull request.

The oracle analyzes each statement through a live describe and catalog, then runs it in rolled-back transactions over seeded edge values, twice (with and without the values of extreme magnitude), and once more over tables emptied of every row, under a 5000 ms timeout (`--timeout <ms>`, or a case's `timeout` file). A value that contradicts a type, or a row count beyond the cardinality, fails the case, and so does a parameter's or a column's type that is no `Type` of `spec/typedefs.schema.json`, does not read and write back as the same JSON, or breaks the validity rules (`oracle/src/validity.rs`). Each Postgres and MySQL statement is also analyzed again under other session settings, and a case fails if its analysis changes. A statement that failed or timed out on every run was checked for nothing: it is listed under `UNCHECKED`, a case's `unchecked.txt` holds those lines (empty where every statement must run; compared and blessed like `expected.txt`), and `--strict-coverage` fails a case that has such a statement and no `unchecked.txt`, which is how to run statements from elsewhere. A directory with no `expected.txt` is checked for soundness alone. A case may also carry a `min_version` file, whose line with a version alone skips the case on an older server and whose `<file> <version>` lines skip a statement there (for syntax or a function the older version lacks), an `expected-<series>.txt` (`expected-8.0.txt`) that stands in for `expected.txt` on that series, where its server answers a statement differently and the analysis is right for it, and, for MySQL, a `sql_mode` file. The oracle creates and drops a database per case. MySQL statements run on sessions opened as mysql2 opens them, three ways: bound over the binary protocol as mysql2's `execute()` binds, through `SQL_BUFFER_RESULT`, and with their values written into the text as mariadb's `query()` and PlanetScale write them; a run that ends the transaction, writes a MyISAM or MEMORY table or moves an AUTO_INCREMENT counter far has the database built again (`oracle/src/mysql.rs`). `--dump <file>` writes every analysis and `--analyses <file>` checks another engine's.

`--mutate oracle/mutations.json` shows that each kind of check the oracle makes can fail. Each entry names a statement of a case, a JSON pointer into the engine's fresh analysis of it, a value to put there, and the text of the problem the oracle must then report; the oracle runs the changed analysis over the case's states, and the run fails unless every entry's problem is reported. CI runs it in each dialect's shard. A new kind of check gets an entry, on a statement whose runs contradict the changed analysis only through that check.

### A loader change

The run time, the mapper, the adapters and the CLI live in `src/` (the table above names the file and its tests). Run `nub run typecheck` and `nub run test` with both test databases. A change to how values are bound or decoded is measured on every driver by `lab/driver-matrix` (its README has the commands; `compare.ts` checks a run row for row against `RESULTS.md`, which `./run.sh` rewrites). A change to an adapter or the preload is checked in its example: `nub run build`, then `nub install` in `examples/<name>` and its README's commands. The docs site imports `src/analyze.ts`, `src/render.ts` and `src/doc-comment.ts`, and its capture (`nub run capture`) runs the analysis through them on the binary, so a change there also runs `nub run build` in `site/`; the build itself runs no analysis and needs no binary. A change users see goes into the docs ([A docs change](#a-docs-change)) and the skill in the same pull request.

### A docs change

The docs are `site/content/docs/`, one file per page: `index.mdx` is the intro, at `/`, and each dialect has a reference page (`postgres.mdx`, `mysql.mdx`, `sqlite.mdx`) with every rule and edge case of its database. The intro, Usage, Inference, Configuration, Observability and the FAQ go on in numbered files in `site/content/sections/`, listed in `site/lib/page-sections.ts`; those files share one schema and one namespace of statements (`site/lib/page-files.ts`). The sidebar is `pageGroups` in `site/lib/layout.shared.tsx`. Links from when the docs were one page keep working through `site/lib/moved-anchors.ts`, a script on `/` that sends each old `/#heading` to its page; a new heading needs no entry. Rust's content shows only while `SHOW_RUST` in `site/lib/languages.ts` is on: `rust.mdx` is built only then, and on every other page a passage only Rust needs goes inside `<Rust>…</Rust>`, a phrase within a line or blocks between tags on lines of their own, and the wording that stands in for it while Rust is off inside `<NoRust>…</NoRust>` (`site/lib/rust-content.ts`, which also drops each `<LanguagePanel value="Rust">`). reylo.dev serves the `release` branch, which each release moves to its tagged commit, so the docs describe what npm serves; a push to `main` builds a preview. A docs change that holds for the released version (a typo, a clearer sentence, a missing example) can go live before the next release: after it lands on `main`, cherry-pick its commit onto `release` and push, which only ever moves forward.

1. Every type and error shown on the page is captured, never typed by hand. After changing a `.sql` block or a page's schema, run `nub run capture` in `site/` with throwaway servers of both kinds: `REYLO_CAPTURE_POSTGRES=postgres://postgres@localhost:<pg port>/reylo_capture REYLO_CAPTURE_MYSQL=mysql://root@127.0.0.1:<mysql port>/reylo_capture` (the database is dropped and made again, so its name must start with `reylo_capture`). It rewrites `site/lib/sql-modules.json` and `site/lib/sql-errors.json`.
2. `nub run build` in `site/` type-checks and builds the site to `site/build/client`, and fails on a stale capture. `nub run dev --port <port> --strictPort` in `site/` serves it (3311 by default).
3. The voice is brief and instructive, as in Zod's docs: a sentence or two, then an example, and an example in every section; [Writing conventions](#writing-conventions) has the rest.

`site/docs-kit/` is a copy of a design shared with another site: change it at its source and sync it, never in place (`node docs-kit/src/sync.mjs . --check` in `site/` fails on a copy edited in place).

## Checks

`.github/workflows/test.yml` runs every check on each push to `main` and on each release, and on a pull request the checks its change reaches, its run for an older commit cancelled:

- **binary**, on every pull request: `cargo build --release -p reylo-cli` (without LTO), uploaded for the test job.
- **test**, on every pull request: on Node 24 with throwaway Postgres 18 (pgvector's image of it) and MySQL 8.4, `nub install` at the root, in `lab/drivers` and in `lab/jest`, the Jest lab's link, the binary from the binary job (`REYLO_ENGINE_PATH`), `nub run typecheck`, `nub run test` with none skipped, and the build around that binary.
- **engine**, on a pull request that changes `engine/`, `oracle/`, `rust/`, Cargo's files, `src/error-codes-*`, the format's JSON Schema or `spec/examples.json`, the JSON Schema validators' measurements the engine's tests read, or `.github/` (a renamed file at both its paths): `engine/build.sh --prepare`, `cargo build --workspace --all-targets` and `cargo check -p reylo-migrate --no-default-features` with no warning, and `cargo test` of the crates the change reaches (every one, `-p reylo-engine-core -p reylo-engine-postgres -p reylo-engine-sqlite -p reylo-engine-mysql -p reylo-engine -p reylo-migrate -p reylo-cli -p reylo-oracle -p reylo-build -p reylo --features reylo/mysql,reylo/sqlite`, where it changes core, `engine/native/`, `engine/wasip2/`, the oracle's code, the build or CI; else the engine of each database it changes, and `-p reylo-migrate -p reylo-cli` for `engine/cli/` or `engine/migrate/`, with `-p reylo-build -p reylo --features reylo/mysql,reylo/sqlite` for `rust/` and `engine/migrate/`), with throwaway Postgres 18 and MySQL 8.4 for the migrations' tests; then `.github/scripts/rust-demos.sh`, every Rust demo built and run on those servers.
- **package**, on the same pull requests: `.github/scripts/rust-package-check.sh`, every crate a Rust project builds from crates.io packed with `cargo package` and built from its own tarball, then new projects outside the workspace that depend on `reylo` (and one on `reylo-build`) by version, resolved to those tarballs, built and run, each also migrating a database of its own with `reylo::migrate!()`: on sqlx 0.9 and Postgres 18, and on sqlx 0.8 with Postgres 18 and with MySQL 8.4, which no workspace member can be, since a workspace builds `reylo` once with every member's features.
- **playground**, on a pull request that changes Postgres's engine or a file that runs every engine check: `.github/scripts/build-playground.sh`, the docs site's playground engine built as the release builds it, so a change that breaks the `wasm32-wasip2` build fails before a release does.
- **oracle**, on the same pull requests: `cargo run -q -p reylo-oracle -- --url <pg> --mysql-url <mysql> --strict-coverage <cases>`, then `--mutate oracle/mutations.json` on the same cases, in shards side by side (Postgres's cases, SQLite's, MySQL's in two, and `mysql_types`, the slowest, alone), each database's only where the change reaches it (`engine/<database>/` or one of its cases; everything for the files that run every engine check). Postgres 18 has pgvector, PostGIS and the five JSON Schema validators, which `.github/scripts/json-schema-validators.sh` builds and a cache keeps, with the packages of Postgres itself; MySQL is 8.4. On each push to `main`, each release and a dispatch with `scope=everything`, never on a pull request, two more shards run every case of a database on the oldest version the docs claim: `postgres-14`, on Postgres 14 with the same extensions and JIT off, and `mysql-8.0`, on MySQL 8.0.38; each skips what a case's `min_version` says that version lacks, and neither runs `--mutate`. A failure in the step that builds the validators is not the engine's.
- **postgres-19**, on the same pull requests as the oracle's Postgres shard: on Postgres 19 from PGDG, with pgvector, PostGIS and the five JSON Schema validators built against it and cached (`.github/scripts/postgres-19-extensions.sh`), since PGDG doesn't package them for 19 yet, the oracle's Postgres cases with `--strict-coverage` and then the loader's tests with none skipped, MySQL 8.4 beside it and a second Postgres 19 over TLS for the test of channel binding.
- **binaries** (`binaries.yml`), on a pull request that changes the binary's program (`engine/cli/`, `engine/native/`, `engine/migrate/`, `rust/reylo-build/`, whose generator `reylo generate` runs), its packaging (`npm/`, `scripts/build.ts`), how the loader and the `reylo` command find and run it (`src/native.ts`, `src/engine.ts`, `src/cli.ts`), `.cargo/`, `Cargo.lock`, `rust-toolchain.toml` or the workflow and its scripts, and within each release: the binary built for each of the eight platforms on its own runner, the nine packages packed, then on each platform (macOS on Intel on an Intel runner, Linux on glibc in Node 24's Debian 11 image, AlmaLinux 8, whose glibc 2.28 is the oldest the binary starts on, and Amazon Linux 2023, and on musl in Node 24's Alpine image) `.github/scripts/install-check.ts`, which publishes them to a registry of its own, installs `reylo` in a fresh project, checks that npm brought that platform's engine alone, types a query with `reylo analyze` through the installed command and runs it under the preload, and reads Postgres statements nested to the engine's bound.
- **channels** (`channels.yml`), on a pull request that changes an installer, the Dockerfile or the scripts that write and check them, against the newest release's assets, and from `binaries.yml` (a pull request that changes the binary, and each release, before anything is staged) against the binaries it built, served on each runner: on each platform's runner, `.github/scripts/channels-check.sh` installs through every channel the platform has (install.sh on macOS and in each Linux image, install.ps1 under PowerShell 7 and 5.1, the Homebrew formula on macOS and Linux on glibc, the Scoop manifest on Windows, the container image on Linux on musl) and runs what it installed: `reylo --version` and an analysis on SQLite. `gh workflow run channels.yml -R reylosql/reylo -f release=v<version>` checks a published release's own assets.
- **windows**, on each push to `main` and each release, never on a pull request (`windows.yml`, which can also be run by hand): on `windows-latest`, the loader's tests against the runner's Postgres 17 and MySQL, none skipped but those that say why Windows cannot run them, `nub run build`, and `.github/scripts/windows-check.ts`, which types a project installed from `dist/` with its database named every way a Windows path can be (relative, on another drive, on a `subst` drive, through a share, as a URL) and its Postgres TLS files and MySQL named pipe, then the Node example on Postgres.

A branch can get CI with no pull request, and so no review, by anyone with write access: `gh workflow run test.yml -R reylosql/reylo --ref <branch>` runs the checks its changes from `main` reach (`-f scope=everything` runs every check and the Windows job), and `gh workflow run binaries.yml -R reylosql/reylo --ref <branch> -f platform=darwin-arm64` builds that one platform's binary, an artifact of the run, `engine-darwin-arm64`, which `REYLO_ENGINE_PATH` can name once `gh run download` has fetched it and `chmod +x` has restored its mode.

Run what CI runs before you push. A failing check's log: `gh pr checks <number> -R reylosql/reylo` names the run, and `gh run view <run id> -R reylosql/reylo --log-failed` prints what failed. Pullfrog and Copilot review every pull request, and Vercel deploys a preview of the docs site.

## Pull requests and commits

- **One pull request per effort**: the changes a piece of work needs ride one branch, a commit each, rather than a chain of small pull requests. Open a second only for work that stands apart from the first. A pull request is squash-merged, so it lands as one commit whose subject is its title, which names the whole effort. Merge `main` into it when it conflicts, rather than rebasing, and leave it alone otherwise.
- **Commit messages and pull request titles are Conventional Commits**: `type(scope): subject`, at most 72 characters, the subject imperative and lowercase with no trailing period, as `fix(mysql): type left-joined columns as nullable`. The type is `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci` or `chore` (`chore(release): 0.2.0` for a release); the optional scope is `engine`, `postgres`, `mysql`, `sqlite`, `mapper`, `cli`, `site`, `docs-kit`, `examples`, `oracle`, `spec`, `readme` or `release`. A breaking change takes `!` after the scope. Only when the subject alone hides something, a blank line and a few short lines say why.
- **Committed text states rules, not people.** A code comment, a test's name, an error message, a README, a docs page, a commit message or a pull request never names or quotes a person, or gives a reason as someone's word: it states the rule and its reason itself.
- **Commit each finished, verified step** on the branch, rather than one commit for a session's work.

## Writing conventions

- Never hard-wrap Markdown or MDX: every paragraph, list item and table row is one line.
- A frontmatter `description:` carries no inline code.
- A docs page and each of its sections open with one short sentence, alone, to the point; what more it needs follows in its own paragraph or the example.
- Prose in the docs never opens a sentence with inline code, writes a method as `.run()` (never a bare `run`), says Reylo infers a type (never that it proves one), and says "cardinality" for how many rows a query returns.
